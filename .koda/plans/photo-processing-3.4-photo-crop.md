## 1. Цель и границы

**Цель.** Пользователь сам решает, что попадёт в архив: обрезает лишний фон,
поворачивает снимок. Оригинал при этом сохраняется целиком — кроп остаётся
инструкцией обработки (`crop_data`), а не новым файлом (инвариант № 4).

**Что входит:**

- Cropper.js 1.6.2 в `static/vendor/` с версией, лицензией и sha256;
- `static/js/photo-crop.js`: холст с нормализованной EXIF-ориентацией, кропер,
  кнопки «влево/вправо/сброс», сбор `crop_data` в скрытое поле при отправке;
- скрытое поле `crop_data` в `PhotoFileForm` и его серверная валидация;
- `processing.normalize_crop_data()` и `processing.scale_crop_data()` —
  одна точка правил «что считается кропом» и «как координаты пересчитать»;
- `services.process_photo()`: координаты браузера переводятся в систему рабочей копии;
- админка: рамка кропа поверх оригинала (CSS-оверлей, readonly-поле);
- прогрессивное улучшение: без JavaScript форма работает, `crop_data` пуст;
- тесты, локализация, документация, версия.

## 2. Решения

Решения 2.1–2.9 мастер-плана действуют без изменений. Ниже — то, что мастер-план
оставил на усмотрение подэтапа, и уточнения, найденные при планировании.

### 2.1 Дефект, найденный при планировании: координаты и рабочая копия

`services.process_photo()` делает `fit_max_side(working, WORK_COPY_MAX_SIDE)`
**до** `apply_crop()`. Браузер знает размер оригинала (например, 6000×4000)
и пришлёт координаты в нём, а сервер применит их к копии 2500×1667. Для любого
фото больше 2500 px кроп уедет, а клампинг по границам вырежет не тот участок.

Сейчас дефект не проявляется: в тестах картинки 200×200 и 400×400, масштаб 1.0.
С появлением кропа из браузера он станет массовым — телефон снимает 4000–8000 px.

**Решение.** Координаты пересчитываются на рабочую копию:

```
factor = рабочая_ширина / исходная_ширина_после_транспонирования
кроп_на_копии = кроп_браузера × factor
```

Порядок операций при этом не меняется (`exif_transpose` → поворот → кроп),
рабочая копия остаётся (иначе OOM на 60 Мпикс), а `crop_data` хранит координаты
в системе «как видит человек» — в полном размере кадра, не в размере копии.
Иначе смысл поля терялся бы: при смене `WORK_COPY_MAX_SIDE` все сохранённые
кропы поехали бы.

### 2.3 Уточнения, найденные при планировании

| # | Вопрос | Решение |
|---|---|---|
| 8 | Как нормализуется EXIF в браузере | `createImageBitmap(file, {imageOrientation: "from-image"})` → холст → Cropper с `checkOrientation: false`. Опция `checkOrientation: true` конфликтует с тем, что браузер сам применяет EXIF к `<img>`, и координаты уезжают на 90°. Нормализация своими руками даёт одну систему координат: «как видит человек» = система сервера |
| 9 | Большие фото и canvas | Холст ужимается до `CROP_CANVAS_MAX_SIDE = 2000` px: мобильные браузеры ограничивают canvas ~16 Мпикс, а 48 Мпикс в память телефона не влезут. Координаты пересчитываются обратно в полный размер по коэффициенту холста |
| 10 | Что отправлять, если кроп не менялся | Если рамка совпадает с полным кадром и поворот 0 — отправляем пустой `crop_data` (`{}`): `display` = нормализованный оригинал, лишний пересчёт не нужен |
| 11 | Где живёт правило валидации | `processing.normalize_crop_data()` — одна функция для формы и сервиса: форма отдаёт её результат в `cleaned_data`, сервис применяет к сохранённому `crop_data` (данные могли прийти из админки или из старой версии) |
| 12 | Единица поворота в браузере | Кнопки «влево/вправо» крутят холст на 90° для показа; суммарный угол нормализуется в 0/90/180/270 и уходит в `rotate`. Сервер получает уже нормализованное число (`apply_rotation` мусор игнорирует) |
| 13 | Без JavaScript | Скрытое поле остаётся пустым, форма отправляется как раньше: кроп необязателен. `<noscript>`-подпись объясняет, что обрезать кадр можно только с JavaScript, — иначе человек искал бы кнопку |
| 14 | HEIC и canvas | `createImageBitmap` HEIC не декодирует в большинстве браузеров. Ошибка декодирования → показываем прежнее превью с пояснением «обрезать кадр в этом браузере нельзя, файл загрузится целиком» и не блокируем отправку |
| 15 | Тесты фронтенда | Не пишем. Проверяется серверная часть (координаты, масштаб, мусор) и ручной прогон в браузере — правило проекта: JS не покрывается unit-тестами |
| 16 | Пересчёт `display` после смены `crop_data` | Уже работает: `process_photo()` читает `crop_data` при каждом вызове, действие админки «Обработать заново» пересчитывает. Новый код только добавляет масштаб координат |

### 3.2 Формат `crop_data`

```json
{
  "version": 1,
  "x": 1200, "y": 300, "width": 3600, "height": 2400,
  "rotate": 90,
  "source_width": 6000, "source_height": 4000
}
```

- координаты — в системе «как видит человек» (после EXIF-ориентации)
  и в **полном** размере кадра, не в размере холста и не в размере рабочей копии;
- `source_width`/`source_height` — тот же полный размер. Сервер их не использует
  для расчётов (берёт реальный размер файла) — они для рамки в админке;
- пустой словарь `{}` — «без кропа»; это нормальный путь, а не ошибка;
- чужая `version`, не словарь, отсутствующие или нечисловые координаты,
  кроп меньше `MIN_CROP_SIDE` — «без кропа» с предупреждением в лог.

### 3.3 Поток

```
браузер                                      Django                Celery worker
  │ выбрать файл                              │                       │
  │  createImageBitmap(from-image)            │                       │
  │  → холст ≤2000 px                         │                       │
  │  → Cropper (кроп, поворот 0/90/180/270)   │                       │
  │ submit: файл + crop_data (JSON)           │                       │
  ├──────────────────────────────────────────►│ PhotoFileForm         │
  │                                           │  файл: размер, формат,│
  │                                           │  стороны, пиксели,    │
  │                                           │  декодирование, EXIF  │
  │                                           │  crop_data: normalize │
  │                                           │  по размеру после EXIF│
  │                                           │ Photo(draft, uploaded)│
  │                                           │ enqueue ──────────────┼──► process_photo_task
  │ ◄── 302 на шаг 2                          │                       │  exif_transpose
  │                                           │                       │  рабочая копия ≤2500
  │                                           │                       │  поворот
  │                                           │                       │  кроп × factor
  │                                           │                       │  display, phash
```

### 3.4 Что проверяет каждая сторона

| Проверка | Браузер | Форма | Сервис |
|---|---|---|---|
| Кроп внутри кадра | да (Cropper ограничивает) | клампинг | клампинг |
| Минимальный размер | нет (Cropper даёт любую рамку) | `MIN_CROP_SIDE` | `MIN_CROP_SIDE` |
| Формат и версия JSON | — | `normalize_crop_data()` | `normalize_crop_data()` |
| Поворот 0/90/180/270 | да (кнопки) | нормализация | `apply_rotation` игнорирует прочее |
| Размер кадра | да (холст) | реальный размер файла после EXIF | реальный размер файла |

Форма — первая линия с понятным сообщением; сервис — страховка, потому что
`crop_data` мог прийти из админки или из старой версии записи.

### 3. [ ] Чистые функции: размер после EXIF, нормализация и масштаб координат

- Навыки: koda-coder.
- Файлы: `apps/photos/processing.py`, `tests/test_photo_crop.py` (новый).
- Содержание:
  - `oriented_size(image) -> tuple[int, int]` — размер кадра «как видит человек»:
    для Orientation 5/6/7/8 стороны меняются местами, для остальных — как есть.
    Реализация через `exif_transpose` на копии дешевле и надёжнее ручной таблицы,

    клампинг по `size` (если передан), отказ при стороне меньше `MIN_CROP_SIDE`.
    Возвращает `{}` для мусора с `logger.warning`; `source_width`/`source_height`
    сохраняет, если они числа;
  - `scale_crop_data(crop_data, factor) -> dict` — умножить координаты на `factor`
    с округлением и повторным клампингом;
  - `apply_crop()` переписать поверх `normalize_crop_data()`: поведение то же
    (тесты `test_photo_processing.py` зелёные), второго набора правил нет.
- Критерий: unit-тесты на `oriented_size` (Orientation 1, 3, 6, 8, битый тег),
  `normalize_crop_data` (валидные, мусор, чужая версия, отрицательные, за границей,
  меньше `MIN_CROP_SIDE`, поворот 45 и «abc»), `scale_crop_data` (0.4166 на
  6000→2500, клампинг после масштаба). Старые тесты `apply_crop` не менялись
  и проходят.

### 7. [ ] Админка: рамка кропа поверх оригинала

## 5. Открытые вопросы

1. **Перекроп загруженного фото (P3-18).** Нужен эндпоинт оригинала для автора
   (`/photos/<pk>/original/`, `login_required`, `can_edit_photo`, отдача
   `FileResponse` без GPS — иначе утечка). Решение по доступу за владельцем:
   отдавать оригинал только автору и модератору, без публичной раздачи.
2. **Кроп и пакетная загрузка (3.7).** При десяти файлах нужен один кропер
   на файл или отказ от кропа в пакетном режиме. Решается в 3.7.
3. **Кадрирование по сетке/пропорциям.** Сейчас свободная рамка. Пропорции
   1:1, 4:3, 3:2 — появятся, если владелец попросит; `aspectRatio` у Cropper
   переключается одной кнопкой.
