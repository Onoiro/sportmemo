## 1. Цель и границы

**Цель.** Человек с бумажным альбомом загружает снимок, заполняет данные
и видит его в личном кабинете со статусом «На проверке». Публикует фото
модератор — как и команды.

**Что входит:**

- форма загрузки с лимитами и валидацией файла;
- выбор команды и события по названию (`<datalist>`) с резолвом на сервере;
- подсказка года из EXIF в браузере (exifr), без записи в базу за спиной
  пользователя;
- правило статуса `initial_status_for(user)` → `draft`;
- личный кабинет `/photos/mine/` с шестью плашками состояния;
- страница правил `/rules/`;
- ссылки «Загрузить фото» и «Мои фото» в интерфейсе;
- возврат в форму фото после создания команды;
- тесты, локализация, документация.

**Что не входит (по мастер-плану):**

| Отложено | Куда |
|---|---|
| Celery-задачи, ретраи, статус «в обработке» из воркера | 3.3 |
| Cropper.js, валидация координат из браузера, оверлей в админке | 3.4 |
| Поиск похожих, пороги, страница в админке | 3.5 |
| `MergeableModel`, `merged_into`, редирект на канон | 3.6 |
| Пакетная загрузка (несколько файлов) | 3.7 |
| Правка загруженного фото автором | **P3-14** (новая, бэклог) |
| Автозаполнение команды, города, события из EXIF | P3-8 (в 3.2 — только год) |
| nginx `client_max_body_size` | этап 4 (конфига пока нет) |

## 2. Решения

Решения 2.1–2.9 мастер-плана действуют без изменений. Ниже — то, что
мастер-план оставил на усмотрение подэтапа, и уточнения, найденные при
планировании.

### 2.1 Решения, утверждённые владельцем 2026-10-23

| # | Вопрос | Решение |
|---|---|---|
| 1 | Выбор команды и события | **Текстовое поле + нативный `<datalist>`**: автодополнение даёт браузер, сервер резолвит введённое в объект. Без JavaScript поле работает как обычный текст. `Select` без поиска и htmx-автокомплит отклонены |
| 2 | Подсказка года из EXIF | **`exifr` 7.1.3 в `static/vendor/exifr/`** (MIT, ~76 КБ, уже минифицирован). Читает только `DateTimeOriginal` из локального файла и заполняет пустое поле года |
| 3 | Плашка «Удалено» | **Отдельное состояние.** Удаление — признак (`deleted_at`), а не статус публикации; фото не должно исчезать из кабинета молча |
| 4 | Правка фото автором | В 3.2 **не делается**, записывается в бэклог как **P3-14** |

### 2.2 Уточнения, найденные при планировании

| # | Вопрос | Решение |
|---|---|---|
| 5 | Обработка после сохранения | В 3.2 — **синхронный** вызов `services.process_photo()` в представлении. В 3.3 он станет Celery-задачей; точка вызова одна, пайплайн не дублируется |
| 6 | Сколько состояний у плашки | **Шесть** из решения 3 плюс `hidden` — честный показ `Status.HIDDEN`. Без него скрытое модератором фото показывалось бы как «Опубликовано», то есть плашка врала бы. Итого: `processing`, `review`, `failed`, `published`, `hidden`, `rejected`, `deleted` |
| 7 | Лимит 50 фото в сутки | Скользящие **24 часа** от текущего момента (`created_at__gte=now-24h`), а не календарные сутки: «в сутки» для человека означает «за последние сутки». Удалённые фото квоту не возвращают |
| 8 | Проверка формата файла | **По содержимому** (`Image.open().format` ∈ JPEG/PNG/WEBP/HEIF), расширение игнорируется: переименованный `.pdf` не пройдёт, HEIC без расширения — пройдёт |
| 9 | Проверка размера в пикселях | `Image.MAX_IMAGE_PIXELS` (60 Мпикс) превращает `DecompressionBombWarning` в ошибку формы, `DecompressionBombError` — в отдельное сообщение. Предупреждение, а не только исключение: Pillow бросает `Error` лишь при превышении вдвое |
| 10 | Поля формы | `original`, `title`, `caption`, `year`, `taken_date`, `team_name`, `event_name`. Источник (`Source`) в форме не выбирается: его заводит модератор, а список источников в форме из одного поля превратился бы в справочник |
| 11 | Пагинация кабинета | `PHOTO_PAGE_SIZE` (24) через общий `paginate()` — как в галереях |
| 12 | Возврат в форму после создания команды | `team_create` получает необязательный `next` с проверкой `url_has_allowed_host_and_scheme`; форма фото принимает `?team=<pk>` |
| 13 | Обновление статуса в кабинете | Без htmx: кнопка «Обновить» — обычная ссылка на тот же адрес, представление закрыто `@never_cache`. Автообновление — при возврате на страницу |
| 14 | Письма модераторам о новых фото | Не отправляются (мастер-план): поток фото — это поток писем, очередь смотрят в админке |

### 2.3 Vendor-зависимость

`exifr` 7.1.3, лицензия MIT, автор Mike Kovařík.

```
https://cdn.jsdelivr.net/npm/exifr@7.1.3/dist/full.umd.js
sha256 2bd05117781c12ddd965dee846de3b3f986b5ecb4c7f6a78f2d2ec1db7c65ae7
```

Файл уже минифицирован (jsDelivr это подтверждает в шапке), поэтому
`full.umd.min.js` не нужен: он больше исходного и содержит предупреждение
про SRI. Сохраняется как `static/vendor/exifr/exifr.min.js`.

### 3.2 Поток загрузки

```
браузер                          Django
   │                               │
   │ выбор файла                   │
   │ ├─ URL.createObjectURL → превью│
   │ └─ exifr → подсказка года      │
   │                               │
   │ POST: файл + поля             │
   ├──────────────────────────────►│ PhotoUploadForm.is_valid()
   │                               │   размер, формат, стороны, пиксели,
   │                               │   декодирование, лимит суток,
   │                               │   резолв team/event, год
   │                               │ Photo(status=initial_status_for(user),
   │                               │       processing_status=uploaded)
   │                               │ process_photo() — синхронно
   │                               │   → display, width, height, phash
   │ ◄── редирект /photos/mine/    │
   │ «Спасибо! …после быстрой      │
   │  проверки модератором»        │
```

### 3.3 Состояния плашки

Порядок проверок в `Photo.upload_state` — от самого сильного признака:

| # | Условие | Ключ | Подпись |
|---|---|---|---|
| 1 | `deleted_at` заполнено | `deleted` | Удалено |
| 2 | `processing_status == FAILED` | `failed` | Ошибка обработки |
| 3 | `processing_status` ∈ {`UPLOADED`, `PROCESSING`} | `processing` | Обрабатывается |
| 4 | `status == PUBLISHED` | `published` | Опубликовано |
| 5 | `status == HIDDEN` | `hidden` | Скрыто модератором |
| 6 | `status == REJECTED` | `rejected` | Отклонено |
| 7 | иначе (`DRAFT`) | `review` | На проверке |

`moderation_reason` выводится рядом с плашками `hidden`, `rejected`, `deleted`;
`processing_error` — рядом с `failed`.

Порядок именно такой: удалённое фото с `published` показывает «Удалено»,
а не «Опубликовано».

### 2. [ ] Правила загрузки в сервисе

- Навыки: koda-coder.
- Файлы: `apps/photos/services.py`.
- Содержание:
  - `initial_status_for(user) -> Status` → `Status.DRAFT`. Одна точка правила,
    готовая к P3-10 (`User.is_trusted`): менять её будет один подэтап, а не форма
    и представление по отдельности;
  - `DAILY_UPLOAD_LIMIT = 50`;
  - `uploads_today(user)` — число фото автора за последние 24 часа по
    `created_at__gte=now-timedelta(hours=24)`; менеджер по умолчанию, чтобы
    удалённые фото тоже считались;
  - `upload_limit_reached(user)` — `uploads_today(user) >= DAILY_UPLOAD_LIMIT`;
  - `resolve_by_name(model, value, queryset, label)` — общий резолв названия:
    пустое значение → `None`; точное совпадение по `name__iexact`; если
    вхождений несколько — сравнение с `label(obj)` (для команды `full_name`,
    для события `str(event)`); иначе `None`.
- Критерий: юнит-тесты на границу лимита (50 — можно, 51 — нельзя), на сироту
  (`uploaded_by=None` не попадает в чужой лимит), на резолв (точное имя,
  имя с городом, неоднозначное имя, пустое значение).

### 4. [ ] Форма загрузки

- Навыки: koda-coder.
- Файлы: `apps/photos/forms.py`, `apps/photos/processing.py`.
- Содержание:
  - `ALLOWED_UPLOAD_FORMATS = ("JPEG", "PNG", "WEBP", "HEIF")` в `processing.py`
    рядом с остальными лимитами: их проверяют форма и (позже) воркер;
  - `PhotoUploadForm(BootstrapFormMixin, forms.Form)` с полями из решения 10;
  - `clean_original` — по порядку: размер файла ≤ `MAX_UPLOAD_BYTES`; открытие
    через `PIL.Image.open`; формат по содержимому; `warnings.catch_warnings`
    с `simplefilter("error", Image.DecompressionBombWarning)`; стороны
    ≤ `MAX_SIDE_PX` и ≥ `MIN_SIDE_PX`; полное декодирование (`load()`), чтобы
    обрезанный файл не прошёл проверку заголовка; `seek(0)` в конце — иначе
    сохранение получит пустой файл;
  - `DecompressionBombError` и `UnidentifiedImageError` → сообщение «не удалось
    прочитать изображение»; ошибки Pillow — отдельными ветками, чтобы человек
    понимал, что именно не так;
  - `clean` — лимит суток, резолв `team_name`/`event_name`, проверка года
    (1850 — текущий) и согласованности года с `taken_date`;
  - все сообщения — на русском, через `gettext`.
- Критерий: тесты на каждый отказ с проверкой текста; HEIC принимается;
  файл после проверки читается (сохранение не падает на пустом файле).

    `original_filename` без пути, `display`/`width`/`height`/`phash` заполнены
    синхронной обработкой;
  - невидимость: нет в `visible_photos()`, в карте сайта, в поиске,
    в списке года; чужая прямая ссылка → 404, своя → 200 с плашкой;
  - отказы с текстом: больше 25 МБ, не-картинка, сторона меньше 300 px,
    51-е фото за сутки; лимиты по стороне и пикселям — через `monkeypatch`
    константы и маленькую картинку: реальные 20000×20000 в тесте заняли бы
    больше гигабайта памяти, а проверяется логика, а не число (само число
    проверяется отдельным assert-ом константы);
  - HEIC: файл создаётся через `pillow_heif` в тесте и принимается;
  - год из EXIF: не попадает в базу, если пользователь его не подтвердил
    (проверяется, что форма без поля года даёт `year=None`);
  - резолв: своя команда, опубликованная чужая, чужая черновая (не находится),
    неоднозначное название, событие, пустое значение;
  - кабинет: только свои фото, все статусы включая удалённые, семь плашек,
    причина решения, кнопка «Обновить», пагинация;
  - `/rules/` анонимно; `noindex` у формы и кабинета;
  - `next` без открытого редиректа.
- Критерий: новые тесты зелёные, существующие не сломаны.
