## 1. Цель и границы

**Цель.** Доверенный автор (`User.is_trusted`) публикует своё сразу: фото,
команда и событие получают `status=published` без модератора. Правило
статуса живёт в **одной** функции, а тексты интерфейса перестают обещать
проверку каждому автору.

**Почему это не «одна строка в фото».** Правило сейчас есть только для фото
(`initial_status_for` в `apps/photos/services.py`), а `team_create`
и `event_create` жёстко пишут `Status.DRAFT` и про доверенных авторов
не знают. Три представления в двух приложениях — это три места, которые
разойдутся: один путь загрузки публиковал бы сразу, а другой нет. Поэтому
функция переезжает в общий слой `apps/moderation`, где в 4.3 появится
сервис решений.

**Что входит в подэтап:**

- `initial_status_for(user)` в `apps/moderation/services.py`
  (переезд из `apps/photos/services.py`);
- три точки вызова: `_create_photo` (`apps/photos/views.py`), `team_create`
  и `event_create` (`apps/catalog/views.py`);
- признак «опубликовано без проверки»: `StatusModel.is_auto_published`
  (`status=published` и `moderated_by IS NULL`);
- сообщения после создания и тексты кабинетов, форм и `/rules/` — без
  безусловного обещания проверки;
- письма модераторам о новой команде и событии: текст честно говорит,
  ждёт объект проверки или уже опубликован;
- тесты: доверенный и обычный автор во всех трёх точках, две независимые
  способности, тексты;
- локализация, документация, версия.

**Что не входит:**

| Отложено | Куда / почему |
|---|---|
| Квота «первые N фото через премодерацию, затем сразу» (P3-10 в бэклоге) | Решение владельца: на старте флаг ставится вручную суперадмином; счётчик первых фото — отдельная задача, если понадобится |
| Отдельная вкладка «опубликовано без проверки» | Мастер-план: на старте хватает истории; очередь — 4.4 |
| Сервис решений и запись `ModerationAction` | 4.3; здесь объект публикуется при создании, решения как такового нет |
| Понижение доверия, отзыв флага, уведомление автора о решении | 4.3–4.5 |
| `is_trusted` для комментариев | Премодерация комментариев управляется `CommentSettings`, доверие автора её не касается |
| Персональные тексты «вам доверяют» в кабинетах | См. 2.5: одна честная формулировка вместо ветвления шаблонов |

## 2. Решения

### 2.1 Сигнатура `initial_status_for(user)` — без вида спорта

```python
def initial_status_for(user) -> Status:
    """Статус, с которым новый объект попадает в архив.

    Доверенный автор (`User.is_trusted`) публикует своё сразу, остальные
    ждут модератора. Вид спорта не участвует: доверие выдаётся человеку,
    а не области, и `is_moderator` — другая способность.
    """
    if user is not None and getattr(user, "is_trusted", False):
        return Status.PUBLISHED
    return Status.DRAFT
```

**Отличие от мастер-плана:** там сигнатура `(user, sport=None)`. Параметр
` sport` не вводим, пока правило от вида спорта не зависит: неиспользуемый
аргумент создаёт иллюзию, что доверие бывает «по виду спорта», и его начнут
передавать «на всякий случай». Появится правило по области — добавим
параметр вместе с правилом. Решение утверждено владельцем (раздел 5).

`getattr` вместо прямого `user.is_trusted`: `shortcuts` и сервисы уже
вызывают проверки с заглушками в тестах, и падение на отсутствующем
атрибуте было бы шумом, а не находкой.

### 2.2 Публикация без проверки: `moderated_by` и `moderated_at` пусты

`status=published`, `moderated_by=NULL`, `moderated_at=NULL` — признак
«опубликовано без проверки» (решение владельца). `publish()` **не
вызывается**: метод ставит `moderated_at=now()` и `moderation_reason`,
и получилась бы «дата решения» без решения. Статус присваивается при
создании объекта — как сейчас присваивается `DRAFT`.

В историю (`django-simple-history`) попадает обычная запись о создании
со статусом `published`: отдельного кода для аудита не нужно.

### 2.3 Признак `is_auto_published` живёт в `StatusModel`

```python
@property
def is_auto_published(self) -> bool:
    """Опубликовано без решения модератора.

    Признак пост-модерации: доверенный автор публикует своё сразу,
    и `moderated_by` остаётся пустым.
    """
    return self.status == Status.PUBLISHED and self.moderated_by_id is None
```

Почему в `core`, а не в `moderation`: свойство нужно шаблонам писем
и будущему фильтру очереди (4.4), а `StatusModel` — единственное место,
где статус публикации уже описан. Свойство не миграция: схема не меняется.

Признак читается по `moderated_by_id`, а не по `moderated_at`: дата может
появиться от ручной правки в админке, а поле «модератор» — источник решения.

### 2.4 Письма модераторам уходят всегда, но текст честный

Шаблон письма (`templates/catalog/email/new_team_notification.txt`,
`new_event_notification.txt`) сейчас заканчивается строкой «создана
в статусе «черновик» и ждёт проверки». Для доверенного автора это ложь,
а модератору полезно знать, что объект уже в архиве.

Решение: письмо отправляется в обоих случаях, а последняя строка ветвится
по готовому признаку:

```
{% if team.is_auto_published %}{% trans "Команда опубликована сразу: автор — доверенный." %}{% else %}{% trans "Команда создана в статусе «черновик» и ждёт проверки." %}{% endif %}
```

Шаблон не сравнивает статусы сам — читает `is_auto_published`, поэтому
правило остаётся в модели. Тема письма не меняется.

### 2.5 Тексты: одна честная формулировка вместо ветвления

Мастер-план требует, чтобы кабинет «перестал обещать «публикует модератор»
безусловно». Ветвить каждый шаблон на `{% if user.is_trusted %}` не будем:
шесть шаблонов, шесть пар строк, и половина текстов дублируется. Вместо
этого формулировки говорят о выборочной проверке — они верны и для
доверенного, и для обычного автора:

- кабинет: «…публикуется после проверки — обычно в течение дня; авторам,
  которым мы доверяем, — сразу. До публикации … видите только вы
  и модератор.»;
- формы: «…публикуется после проверки модератором или сразу, если вы
  доверенный автор.»;
- `/rules/`: «Обычно … проверяет модератор. Проверка выборочная: авторам,
  которым мы доверяем, снимки публикуются сразу.»;
- пустые состояния кабинетов: «попадёт в архив — сразу или после проверки
  модератором».

Плашку кабинета менять не нужно: `UPLOAD_STATE_LABELS["published"]` уже
равен «Опубликовано», слова «проверено» в ней нет.

Сообщения после создания — в представлениях, а не в сервисе: склонение
своё у каждой модели («команда создана», «событие создано»), а общая
функция с подстановкой слова дала бы кривой русский. Правило статуса
от этого не страдает: оно одно, а текст — это текст.

### 2.6 Что `is_trusted` не даёт

| Проверка | Доверенный автор |
|---|---|
| Видит чужой черновик | **Нет** (`get_visible_or_404` → 404) |
| Правит чужую команду, событие, фото | **Нет** (`can_edit`, `can_edit_photo` → 404) |
| Решает по чужому объекту | **Нет** (`can_moderate` смотрит `role`) |
| Публикует своё сразу | **Да** |

Обратное тоже верно: модератор и админ **без** `is_trusted` создают
черновик. Две способности независимы (решение владельца), и это
проверяется тестами — иначе через полгода кто-то «упростит» правило
до `is_moderator or is_trusted`.

## 5. Решённые вопросы

Все три вопроса утверждены владельцем 2026-10-31. Менять эти решения
без нового согласования нельзя: они объясняют, почему код выглядит
именно так.

1. **`sport` в сигнатуре — не вводим.** Правило от вида спорта не зависит,
   а неиспользуемый параметр создаёт иллюзию обратного. Сигнатура —
   `initial_status_for(user)`. Появится правило по области — параметр
   добавится вместе с правилом.
2. **Письмо модераторам при авто-публикации отправляется всегда**, но
   с текстом «опубликована сразу: автор — доверенный». Пост-модерация
   работает, только если модератор знает, что объект уже в архиве.
3. **Персональных текстов в кабинетах нет** («вам доверяют, публикуем
   сразу»). Шесть шаблонов и шесть пар строк ради одной фразы — дороже,
   чем одна честная формулировка про выборочную проверку. Вернуться, если
   владелец захочет явно говорить доверенному автору о его статусе.
