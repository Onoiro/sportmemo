## 1. Проблема

Схема данных готова к богатой карточке фото: `Source` (тип, издание, страница,
владелец оригинала) и `PhotoPerson` (человек, роль, позиция на кадре) существуют
с этапа 1 и выводятся на `/photos/<pk>/`. Но заполняются они **только в админке**.

Демо-архив выглядит богато, потому что `seed_demo` создаёт источники и раскладывает
людей по фото. Реальные пользовательские фото приходят «слепыми»: ни источника,
ни имён.

**Почему это нельзя оставить как есть.** Владелец — единственный админ и работает
на другой работе. Если источник и люди заполняются только им, после запуска будет
одно из двух: архив из безымянных снимков либо владелец в роли оператора ввода
данных. Оба исхода убивают проект.

**Причина, по которой источник не давали автору.** В `PhotoDetailsForm` записано:
«Источник (`Source`) в форму не входит: его заводит модератор». Это неверно
по существу: откуда снимок, знает только автор, модератор угадать не может.
Отдельной задачи в бэклоге на это не заводилось — решение просто не пересматривалось.

## 2. Решения владельца (2026-11-10)

| # | Вопрос | Решение |
|---|---|---|
| 1 | Создавать `Source` автоматически | **Нет, никогда.** Свободный текст остаётся текстом, справочник — справочником. Автосоздание по совпадению строки и есть генератор «каши» |
| 2 | Что видит автор вместо справочника | Два поля: выбор происхождения (`source_origin`) и строка уточнения (`source_note`) |
| 3 | Хранить имя владельца личного архива текстом | **Нет.** Имя берётся из `uploaded_by`; после анонимизации аккаунта (P5-12) — нейтральная подпись |
| 4 | `initial` для источника | Из последнего фото **автора фото** (не текущего пользователя): человек, оцифровывающий альбом, вводит источник один раз |
| 5 | Кто подтверждает предложенных людей | Автор фото, доверенный автор или модератор — кто первый |
| 6 | Таймер эскалации (7–14 дней) | **Не делаем.** Предложенные связи сразу видны и автору, и модераторам |
| 7 | Публикация людей вместе с фото | **Чекбокс** на карточке фото в `/moderation/queue/`, по умолчанию включён; через `publish_object()` в цикле, по записи в журнал на каждого |
| 8 | Очередь черновиков людей | **Отдельная страница** `/moderation/people/`: у `Person` нет `sport`, карточка другая |
| 9 | Где живёт редактор «Люди на фото» | Только `/photos/<pk>/edit/`. Инвариант «кнопок модерации на публичных страницах нет» сохраняется; на `/photos/<pk>/` — ссылка на правку |
| 10 | Кнопка «Знаете, кто здесь?» для всех вошедших | После стейджинга (5.3), отдельной задачей |

### 2.1 Почему имя не дублируется текстом

`Photo.uploaded_by` — `SET_NULL`, а политика P5-12 — анонимизация аккаунта
по 152-ФЗ. Имя, положенное текстом в `source_note`, переживёт «удаление аккаунта»
на сотнях фото, и требование P5-12 не выполнится. Это не лишнее поле, а юридическая
дыра.

Побочные плюсы: нет рассинхрона при смене `display_name`; `source_note` остаётся
для настоящего уточнения происхождения («архив тренера Сидорова»), которое законно
остаётся после анонимизации. Минус — атрибуция исчезает молча; записывается
в правила явно, чтобы через год это не «починили» сохранением имени.

### 2.2 Почему `Source` не создаётся автоматически

`Source` задуман как переиспользуемый справочник: одна газетная страница = много фото.
Запись на каждое фото обессмысливает её. Плюс свободный текст нельзя нормализовать:
«Советский спорт» и «советский спорт 1994» дадут две записи, и разбирать их
придётся владельцу.

Два уровня источника — то же устройство, что в Wikimedia Commons (`source` / `credit
line`): свободная строка происхождения у автора, структура у библиотекаря.

## 4. Логика: кто что заполняет

Принцип: **спрашиваем только то, что человек знает, и не блокируем публикацию
из-за пустого поля.** Новых обязательных полей не появляется ни одного.

| Поле | Кто заполняет | Когда | Обязательно |
|---|---|---|---|
| Файл, кроп | автор | шаг 1 | файл — да |
| Заголовок, подпись | автор | шаг 2, правка | нет |
| Год | автор | шаг 2, подсказка из EXIF | нет |
| Дата съёмки | автор | шаг 2 | нет |
| Команда, событие | автор | шаг 2, текст + подсказки | нет |
| Источник | автор (упрощённо) → модератор (структурно) | шаг 2 / админка | нет |
| Люди на фото | автор 2–3 → сообщество → модератор | шаг 2, `/edit/`, страница фото | нет |
| Вид спорта | система (`default_sport`) | создание | — |
| Статус, модератор, даты | сервис `moderation/services.py` | решение | — |
| Обработка, размеры, хеш, EXIF | пайплайн | фоном | — |

### 4.1 Правило вывода источника

Одно правило, в одном месте — `apps/photos/source.py`, а не шаблон и не свойство
модели: подпись владельца требует `uploaded_by`, и свойство дало бы скрытый запрос
в списках.

1. Есть привязанный `Source` → выводим его факты.
2. Иначе есть `source_origin` → подпись происхождения; при `personal` — имя
   из `uploaded_by`, при его отсутствии — «Из личного архива автора».
3. Иначе `source_note` — как есть.
4. Ничего нет → блока «Источник» на странице нет.

### 4.2 Люди на фото: три слоя

- **Слой 1 — автор** (3.9): 2–3 человека, кого знает. Поиск с контекстом
  («Иванов Сергей, 1971, Русстар»), первыми — состав команды фото и года.
- **Слой 2 — сообщество** (3.11): кнопка «Знаете, кто здесь?» для вошедших,
  по образцу формы комментария.
- **Слой 3 — подтверждение** (3.11): автор фото, доверенный или модератор.
  Публично видны только подтверждённые.

### 4.3 Не заводить человека — законный выбор

Не узнали или не хотят — имя остаётся текстом в `caption`. Позже его оттуда
вытащит модератор или сообщество. Это снижает и нагрузку, и число дублей.

## 5. Что нельзя нарушить

- **Инвариант № 1:** `Person` не привязан к виду спорта, и поле `sport` ему
  не добавляется. Очередь людей строится без фильтра по области.
- **Инвариант № 6:** журнал пишет только `log_action()` через сервисные функции.
  Публикация людей «вместе с фото» — цикл по `publish_object()`, а не молчаливая
  запись статуса.
- **Инвариант № 8:** фамилии несовершеннолетних не публикуются. Создание человека
  из формы обязано давать выбор `name_visibility`.
- **Инвариант № 9:** soft-delete. Ничего не удаляется физически.
- **`PersonName` заполняется при создании человека.** Иначе «Алеша Петров»
  и «Алексей Петров» не найдут друг друга ни поиском, ни триграммами.
- **Правило видимости имени живёт в представлении/сервисе,** а не в шаблоне.
- **Право на правку людей проверяет одна функция** рядом с `can_edit_photo`,
  а не представления по отдельности.
- **Посторонним 404, а не 403** — то же правило, что у `can_edit_photo`.
