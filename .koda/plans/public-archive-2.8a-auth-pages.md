## 1. Зачем это и что именно делаем

**Цель.** Зарегистрироваться, подтвердить email, войти и восстановить пароль можно уже сейчас
(`django-allauth` настроен с этапа 1), но страницы выглядят как голый HTML из пакета: без
navbar, футера, темы и Bootstrap. Эта часть закрывает разрыв — все страницы входа становятся
частью сайта, и полный цикл регистрации проходится в браузере.

**Почему подэтап 2.8 разделён на две части.** Изначально 2.8 планировался одним куском:
16+ новых шаблонов, переопределение 8 форм чужого пакета, локализация писем и сценарные тесты.
Это две разные пользовательские истории — «войти в аккаунт» и «мой аккаунт», — и каждая
проверяется в браузере отдельно. Разрез по сценариям даёт две проверяемые точки и два
небольших диффа. Часть A закрывает пункт бэклога P2-7 целиком.

**Что входит:**

- каркас: блок `main_inner` в `base.html` и layout allauth, который в него встраивается;
- элементы allauth в стиле Bootstrap (поля, кнопки, панели, плашки);
- Bootstrap-классы полей через миксин и переопределение 8 форм;
- шаблоны: вход, регистрация, выход, «проверьте почту», неактивный аккаунт;
- шаблоны пароля: сброс, «письмо отправлено», новый пароль, смена пароля;
- шаблон подтверждения адреса;
- тексты писем: каркас и два письма (подтверждение, сброс пароля);
- стили страниц аккаунта;
- локализация ru/en;
- тесты на подхват шаблонов, доступ и полный цикл.

**Что не входит:**

| Не делаем | Куда |
|---|---|
| Страница профиля, меню пользователя в navbar | часть B (2.8б) |
| Создание команды пользователем, «мои команды» | 2.9 |
| Заявка «это я» (`User.person` через модерацию) | отложено — см. решение Р-11 и бэклог |
| Социальный вход (Google, VK и т. п.) | не планируется: вход по email + пароль |
| Двухфакторная аутентификация, passkeys, вход по коду | не нужны: архив, а не банк |
| Юридические страницы (соглашение, политика) | этап 4 (P4-2); в форме регистрации — только галочки согласий |
| SMTP (Yandex Cloud Postbox) | этап 4 (P4-5); в dev — console backend |
| `noindex` для страниц входа | 2.10 |

## 2. Принятые решения

### 2.1 Решения мастер-плана (действуют)

- Все строки интерфейса — через `gettext`, каталоги `locale/ru` и `locale/en`.
- Свой шаблон наследуется от `base.html`; проверяем в тестах код ответа и ключевые элементы,
  а не вёрстку.
- Письма оформляются под общий layout (мастер-план, раздел 2, решение «Письма»).

### 2.2 Решения владельца (2026-10-11)

| # | Вопрос | Решение |
|---|---|---|
| Р-11 | Заявка «это я» | **Не делать в 2.8.** Полный сценарий — новая модель (`PersonClaim`), миграция, форма со страницы человека, список заявок и действие модератора. Записано в бэклог отдельной задачей; в части B в профиле будет только ссылка на уже связанного человека |
| Р-12 | Тексты писем | Переопределяем каркас письма и два письма — подтверждение email и сброс пароля. Остальные уведомления (`password_changed`, `email_changed`) остаются штатными и наследуют наш каркас |
| Р-13 | Ссылка «Регистрация» в navbar | Не добавляем: она есть на странице входа. Шапку не перегружаем |

### 2.3 Решения по умолчанию (приняты при составлении плана)

| # | Вопрос | Решение |
|---|---|---|
| Р-1 | Как оформлять страницы allauth | Переопределяем **layout** (`templates/allauth/layouts/base.html`) и **элементы** (`templates/allauth/elements/*.html`). Штатные шаблоны страниц остаются рабочими — копировать их целиком не нужно, переписываем только те, где текст должен быть своим |
| Р-2 | Как layout попадает внутрь общего каркаса | В `templates/base.html` добавляется один блок `main_inner` **внутри** `<main>` (охватывает крошки и `content`). Layout allauth переопределяет `main_inner` и оборачивает контент в `.auth-shell`. Проверено экспериментально на реальных шаблонах пакета: дочерние шаблоны, переопределяющие `content`, обёртку **не** перетирают |
| Р-3 | Bootstrap-классы полей | Штатные формы allauth рендерят «голые» `<input>`. Добавляем миксин `BootstrapFormMixin` (`apps/accounts/forms.py`) и переопределяем 8 форм через `ACCOUNT_FORMS`. В шаблонах остаётся `{{ field }}` — классы уже проставлены |
| Р-4 | Язык строк в наших шаблонах | msgid — **русские**, как принято в проекте (`{% trans "Войти" %}`). Штатные переводы allauth не дублируем: у наших каталогов и каталогов пакета **0 общих msgid** (проверено), и это надо сохранить — английские msgid из шаблонов allauth перетёрли бы переводы пакета |
| Р-5 | `ACCOUNT_CHANGE_EMAIL` | Оставляем `False`: страница `/accounts/email/` показывает список адресов. Менять email «на месте» — лишний сценарий для архива |
| Р-6 | Выход | `ACCOUNT_LOGOUT_ON_GET = True` уже включён: в меню будет обычная ссылка (это часть B). Страница `logout.html` всё равно оформляется — на случай смены режима |
| Р-7 | Ссылки в письмах | Строятся по домену `django.contrib.sites` (`sportmemo.ru`, миграция `core/0003`). `ACCOUNT_DEFAULT_HTTP_PROTOCOL` **не** трогаем: в dev это `http`, а на боевом домене ссылки и так абсолютные из запроса |
| Р-8 | Профиль | В части B меняется только «как к вам обращаться» (`display_name`). Email и пароль — отдельными страницами allauth |
| Р-9 | Профиль: URL | `/accounts/profile/`, имя `accounts:profile`. Наш `include` ставится **перед** `allauth.urls` (часть B) |
| Р-10 | Путь шаблонов | `templates/account/` — шаблоны allauth (без «s»), `templates/accounts/` — наши (профиль в части B). Так указано в мастер-плане |

## 3. Что должно получиться на экране

**`/accounts/login/`.** Обычная страница сайта: navbar, футер, тёплая сепия. Заголовок «Вход»,
поля «Email» и «Пароль» в Bootstrap-стиле, кнопка «Войти», ссылки «Забыли пароль?»
и «Зарегистрироваться». Ошибка «Неверный email или пароль» — красной плашкой над формой.

**`/accounts/signup/`.** Заголовок «Регистрация». Поля: email, «Как к вам обращаться», пароль,
повтор пароля, три обязательные галочки согласий (пользовательское соглашение, политика
конфиденциальности, обработка персональных данных) и кнопка «Зарегистрироваться». После
отправки — страница «Проверьте почту», письмо печатается в консоль `runserver`.

**Письмо.** Тема `[SportMemo] Подтвердите адрес электронной почты`. Текст: приветствие, одно
предложение зачем, ссылка, срок действия (3 дня), подпись с адресом сайта.

**`/accounts/confirm-email/<key>/`.** «Подтверждение адреса», кнопка «Подтвердить». После
подтверждения пользователь сразу входит (`ACCOUNT_LOGIN_ON_EMAIL_CONFIRMATION` уже включён)
и видит сообщение об успехе. Просроченная ссылка объясняет, что делать дальше.

**`/accounts/password/reset/`.** «Сброс пароля»: поле email, кнопка, пояснение.
**`/accounts/password/reset/key/<uid>-<key>/`.** «Новый пароль»: два поля и кнопка.
**`/accounts/password/change/`.** «Смена пароля» для вошедших.

**Анонимный вход без подтверждения.** После верного пароля уводит на `/accounts/confirm-email/`
с напоминанием проверить почту — это штатное поведение `ACCOUNT_EMAIL_VERIFICATION = "mandatory"`,
его надо сохранить.

**Чего в части A ещё нет.** Профиля (`/accounts/profile/`) и меню пользователя в navbar —
это часть B. В navbar остаётся «Войти».

### 2. [x] Каркас: блок `main_inner` и layout allauth

- Навыки: koda-coder
- Файлы:
  - `templates/base.html`
  - `templates/allauth/layouts/base.html` (новый)
- Содержание:

  `templates/base.html` — один новый блок внутри `<main>`:

  ```django
  <main id="main">
      {% block main_inner %}
          {% block breadcrumbs %}{% include "partials/breadcrumbs.html" %}{% endblock %}
          {% include "partials/messages.html" %}
          {% block content %}{% endblock %}
      {% endblock %}
  </main>
  ```

  Ничего другого в `base.html` не меняется: блок по умолчанию выводит прежнее содержимое,
  поэтому существующие страницы рендерятся как раньше.

  `templates/allauth/layouts/base.html`:

  ```django
  {% extends "base.html" %}
  {% load i18n %}

  {% block title %}{% block head_title %}{% endblock %} — {{ SPORTMEMO_SITE_NAME }}{% endblock %}

  {% block main_inner %}
      <div class="auth-shell container">
          {% block content %}{% endblock %}
      </div>
  {% endblock %}

  {% block extra_js %}{% block extra_body %}{% endblock %}{% endblock %}
  ```

  Почему так, а не «layout переопределяет `content`»: если родитель переопределяет `content`,
  дочерний `{% block content %}` — а его переопределяют **все** штатные шаблоны allauth —
  затирает обёртку целиком. Обёртка в `main_inner` работает и со штатными шаблонами, которые
  мы не копируем. Проверено экспериментом: navbar и футер на месте, поля в Bootstrap-классах,
  `head_title` и `extra_body` работают.

  Штатные `allauth/layouts/entrance.html` и `manage.html` переопределяют только `content`
  и наследуются от нашего `base.html` — копировать их не нужно.

- Проверка: `uv run python manage.py check`; `uv run pytest -q` — существующие тесты публичных
  страниц зелёные (блок по умолчанию ничего не меняет); вручную — в HTML страницы входа есть
  `site-header` и `site-footer`.

### 3. [x] Элементы allauth в стиле Bootstrap

- Навыки: koda-coder
- Файлы (новые):
  - `templates/allauth/elements/fields.html` — форма целиком: `non_field_errors`, цикл по полям,
    `form-label`, `form-text`, ошибки; галочки — `form-check`
  - `templates/allauth/elements/field.html` — одиночное поле (нужно на странице адресов email):
    `attrs.type`, `attrs.id`, `attrs.name`, `attrs.value`, `attrs.checked`, `attrs.required`,
    `attrs.disabled`, `attrs.placeholder`, `attrs.autocomplete`, слоты `label` и `help_text`,
    `attrs.errors`
  - `templates/allauth/elements/button.html` — `btn btn-primary` для тега `prominent`,
    `btn btn-outline-secondary` для остальных; `attrs.href` → `<a>`, иначе `<button>`;
    сохраняются `form`, `id`, `name`, `value`, `type`
  - `templates/allauth/elements/button_group.html`, `alert.html`, `badge.html`, `panel.html`,
    `h1.html`, `h2.html`, `p.html`, `hr.html`
- Содержание: элементы — точка, через которую allauth рендерит разметку. Оформляем её один раз
  здесь, а страницы остаются почти штатными (`{% element h1 %}`, `{% element form %}`,
  `{% element fields form=form %}`).

  Список элементов не случайный: он собран по шаблонам, которые реально встречаются
  на страницах части A (`login`, `signup`, `logout`, `password_reset*`, `password_change`,
  `email_confirm`, `verification_sent`, `account_inactive`). `table`, `details`, `img`,
  `provider*` не переопределяем — на этих страницах они не используются.

  Ловушка, которую нельзя повторить: штатный `fields.html` — это `{{ attrs.form.as_p }}`, то
  есть `non_field_errors` выводятся. Если писать цикл по полям вручную, их легко потерять,
  а ошибка «Неверный email или пароль» приходит именно как `non_field_errors`.

- Проверка: ручная — страница входа в сепии и тёмной теме, ~375 px; ошибка неверного пароля
  видна; галочки согласий выровнены с подписями.

### 4. [x] Bootstrap-классы полей: миксин и формы

- Навыки: koda-coder
- Файлы:
  - `apps/accounts/forms.py`
  - `config/settings.py` (`ACCOUNT_FORMS`)
- Содержание:

  ```python
  def apply_bootstrap_classes(fields):
      """Bootstrap-классы виджетам: шаблоны allauth рендерят поля как есть."""


  class BootstrapFormMixin:
      def __init__(self, *args, **kwargs):
          super().__init__(*args, **kwargs)
          apply_bootstrap_classes(self.fields)
  ```

  Классы: `form-control` для текстовых полей и пароля, `form-select` для селектов,
  `form-check-input` для галочек и радио.

  Переопределяем восемь форм (каждая — `class X(BootstrapFormMixin, AllauthX)`):
  `LoginForm`, `ResetPasswordForm`, `ResetPasswordKeyForm`, `ChangePasswordForm`,
  `SetPasswordForm`, `AddEmailForm`, `ReauthenticateForm` и уже существующая `SignupForm`
  (добавляем миксин).

  `ACCOUNT_FORMS` расширяется ключами `login`, `reset_password`, `reset_password_from_key`,
  `change_password`, `set_password`, `add_email`, `reauthenticate`.

  Почему миксин, а не разметка в шаблоне: в Django нельзя добавить класс виджету из шаблона,
  а `{{ field.as_widget }}` с аргументами недоступен.

- Проверка: `manage.py shell` — у `LoginForm()` поля имеют `form-control`; `make test` —
  `tests/test_accounts.py` зелёные.

  пояснения, тексты писем). Для `ru` — выравнивание `msgstr = msgid`.

  **Грабли проекта (повторяются в каждом подэтапе):** `makemessages` помечает новые строки
  `fuzzy`, если нашёл похожую старую, а `msgfmt` пропускает fuzzy — после извлечения снять флаги
  и проверить пустые `msgstr`.

  Отдельно проверить, что строки allauth, которые мы **не** переопределяли (сообщения
  `account/messages/*`), продолжают переводиться каталогом пакета.

- Проверка: `msgfmt` не ругается; при `LANGUAGE_CODE=en` страницы аккаунта английские,
  при `ru` — русские.

## 5. Критерии готовности подэтапа

1. Все страницы входа, регистрации, выхода, подтверждения email и работы с паролем

2. Полный цикл проходится в браузере: регистрация → письмо в консоли → подтверждение → вход →

6. Внешний вид совпадает с остальным сайтом в обеих темах и не разъезжается на ~375 px.
7. Ошибки формы видны, включая общую ошибку входа (не только ошибки отдельных полей).
8. `make lint && make test` зелёные, `makemigrations --check` чист.
9. README, KODA.md, AGENTS.md описывают новое состояние; мастер-план и бэклог поправлены;
   версия 0.8.0, `uv.lock` синхронизирован.

## 6. Риски и заметки

| # | Риск | Как учитываем |
|---|---|---|
| R-1 | Дочерний `{% block content %}` перетирает обёртку layout | Обёртка живёт в блоке `main_inner`, а не в `content` (решение Р-2, проверено экспериментом) |
| R-2 | `non_field_errors` теряются при своей разметке `fields.html` | Выводятся первой строкой формы; тест на неверный пароль проверяет текст ошибки в HTML |
| R-3 | Штатные шаблоны allauth, которые мы не копировали, «выпадают» из оформления | Layout и элементы переопределены глобально, поэтому они тоже получают navbar, футер и Bootstrap-поля |
| R-4 | Обновление allauth меняет имена блоков/элементов | Мы зависим от публичного API шаблонов (`content`, `head_title`, `extra_body`, элементы). При обновлении — прогон тестов подхвата шаблонов |
| R-5 | `makemessages` ставит `fuzzy` и пустые `msgstr` | Проверка fuzzy-блоков и выравнивание для `ru` после `make i18n` |
| R-6 | Английские msgid из шаблонов allauth перетрут переводы пакета | Свои строки пишем по-русски (решение Р-4); тест на английскую локаль |
| R-7 | Переопределение форм ломает логику allauth (динамические поля входа) | Миксин вызывает `super().__init__()` и только после этого ставит классы |
| R-8 | Rate limit allauth мешает тестам при повторных запусках | `cleared_cache` в `conftest.py` чистит кэш до и после каждого теста |
| R-9 | `messages` allauth печатаются по-английски | Проверить вручную; при необходимости переопределить `templates/account/messages/*.txt` — отдельным решением, не в этом подэтапе |
| R-10 | Правка `base.html` затрагивает все страницы | Блок `main_inner` по умолчанию выводит прежнее содержимое; прогон всего набора тестов после шага 2 |
| R-11 | Переписывание `password_reset_from_key.html` ломает выход со страницы сброса | Служебная форма `#logout-from-stage` сохраняется; проверяется ручным прогоном сброса |
| R-12 | Ссылки в письмах ведут на `example.com` | Домен уже задан миграцией `core/0003`; тест проверяет абсолютную ссылку |
