## 1. Цель подэтапа

Дать возможность поправить и дополнить архив: комментарии с ответами к фото,
командам и событиям, а также жалоба на ошибку в данных.

Модели готовы с этапа 1 (задача F-10) и не меняются:

- `apps/comments/models.py` — `Comment` (generic FK, `parent` для ответов,
  `StatusModel` + `SoftDeleteModel`, история);
- `apps/moderation/models.py` — `Report` (причины `ReportReason`, статусы
  `ReportStatus`, `reporter` может быть пустым) и `ModerationAction`.

Админка комментариев (`CommentAdmin`) уже умеет всё, что нужно модератору:
действия `MODERATION_ACTIONS` (опубликовать / скрыть / отклонить / мягко
удалить / восстановить), правка текста в форме, фильтры по статусу и типу
объекта. Кнопок модерации на публичных страницах **не делаем**: админка —
одно место для решений, и каждое попадает в `ModerationAction` и в историю.

Значит, в этом подэтапе работы только про UI: формы, представления, шаблоны,
письмо модераторам и переключатель премодерации.

## 2. Решения, согласованные с владельцем (2026-10-17)

| # | Вопрос | Решение |
|---|---|---|
| 1 | Премодерация комментариев | **Выключена по умолчанию.** Комментарий публикуется сразу, модератор убирает плохое (скрыть / отклонить / удалить в админке). Премодерация включается переключателем в админке — singleton-настройка `CommentSettings`. Обоснование: премодерация всех комментариев — редкость, её держат на чувствительных ресурсах; для архива спортивных фото правильнее реактивная модерация |
| 2 | Где переключатель | Админка, отдельная страница «Настройки комментариев» (`CommentSettingsAdmin`): одна строка, без права добавить и удалить. Список сразу ведёт на форму правки — иначе модератор увидит список из одной записи и не поймёт, что делать |
| 3 | Правка текста модератором | Разрешена в админке (поле уже редактируемое, изменение попадает в `simple-history`) |
| 4 | Письма | **Только о жалобах.** О новых комментариях не пишем: при выключенной премодерации это поток писем |
| 5 | Форма жалобы | **Отдельная страница** `/reports/add/`, без модального окна: работает без JavaScript, ссылку можно переслать |
| 6 | Троттлинг | В этом подэтапе не делаем (премодерация + защита от дублей). Лимиты по IP — бэклог, **P2-17** |
| 7 | Комментарии на странице человека | Не делаем (следуем мастер-плану: фото, команда, событие) |
| 8 | Правка и удаление своего комментария | Не делаем, отложено в бэклог как **P2-16** |
| 9 | Модерация на публичных страницах | Кнопок «скрыть / отклонить» нет. Единственное действие на странице — ссылка «Сообщить об ошибке» |

### Что меняется по сравнению с мастер-планом

Мастер-план предполагал премодерацию всех комментариев («на старте»). Решение
владельца её отменяет: статус комментария выставляет представление, глядя на
`CommentSettings.load().premoderation`.

Открытый вопрос № 2 мастер-плана («премодерация всех или доверие активным
авторам») этим закрыт: выбран третий вариант — публикация сразу, переключатель
для будущих ситуаций.

### Видимость комментариев

| Кто | Что видит |
|---|---|
| Аноним | `status=published`, без удалённых |
| Вошедший | то же |
| Автор | дополнительно свой комментарий в `draft` — с плашкой «на проверке» (только когда премодерация включена) |
| Никто | `hidden`, `rejected`, мягко удалённые — даже автор: это решение модератора, а не черновик |

Свой комментарий, скрытый модератором, автору **не показывается**: иначе
модерация не имеет смысла. Плашка «на проверке» — только для `draft`.

## 3. Архитектура решения

|---|---|

| Настройка премодерации | `apps/comments/models.py` (`CommentSettings`), миграция `comments/0002` |
| Админка настройки | `apps/comments/admin.py` |
| Выборка видимых комментариев | `apps/comments/services.py` |
| Форма и представление комментария | `apps/comments/forms.py`, `apps/comments/views.py`, `apps/comments/urls.py` |
| Форма и представление жалобы | `apps/moderation/forms.py`, `apps/moderation/views.py`, `apps/moderation/urls.py` |
| Общая отправка писем модераторам | `apps/core/emails.py` |
| Шаблоны | `templates/comments/partials/*`, `templates/moderation/report_form.html` |
| Стили и скрипт | `static/css/sportmemo.css`, `static/js/comments.js` |
| Тесты | `tests/test_comments_ui.py`, `tests/test_reports_ui.py` |

### 3.2 Белый список объектов (`targets.py`)

Комментировать и жаловаться можно только на три сущности. Любой другой
`ContentType` — 404.

```
TARGET_MODELS = {"photo": "photos.Photo", "team": "catalog.Team", "event": "catalog.Event"}
```

- модели берутся через `django.apps.apps.get_model()` **внутри функции**, а не
  импортом на уровне модуля: `comments` не должен зависеть от `photos` и
  `catalog` на этапе загрузки (то же правило, что в `apps/core/shortcuts.py`);
- `resolve_target(key, object_id, request)` → объект через
  `get_visible_or_404`: черновик и неопубликованное постороннему дают 404, то
  есть комментарий нельзя «прицепить» к тому, чего пользователь не видит;
- `target_key(obj)` → `"photo"` / `"team"` / `"event"` (по `_meta.label_lower`);
- без белого списка через форму можно было бы создать комментарий к `User`,
  `Comment` или `Report`: generic FK сам по себе ничего не ограничивает.

### 3.3 Настройка премодерации (`CommentSettings`)

Singleton: одна строка, `premoderation = BooleanField(default=False)`.

- строка создаётся data-миграцией (`comments/0002`), по образцу
  `core/0002_seed_sports`; повторный запуск миграции дублей не создаёт;
- `CommentSettings.load()` читает настройку и кеширует её в `django.core.cache`
  (ключ `comments:settings`), чтобы каждый комментарий не делал лишний запрос;
- `save()` сбрасывает кеш — переключатель действует сразу;
- настройки нет в базе (например, тестовая база без миграции) — `load()`
  возвращает объект с дефолтом и не падает;
- админка: `has_add_permission` → `False`, `has_delete_permission` → `False`,
  `changelist_view` ведёт на форму единственной записи.

### 3.4 Выборка комментариев (`services.py`)

`comments_for(target_obj, user)` → список корневых комментариев, у каждого
готовый список ответов.

Почему сервис, а не `{% for %}` в шаблоне: правило видимости (публичное +
свой черновик) и правило «ответ без видимого корня не показываем» должны жить
в одном месте — их используют три страницы и htmx-ответ.

- корни: `Comment.public` + `Q(status=published) | Q(status=draft, author=user)`;
- ответы: то же правило, привязаны к видимым корням; висячий ответ (корень
  скрыт) не показывается;
- порядок: `created_at` (хронология обсуждения, как в `Comment.Meta.ordering`).

### 3.5 Представление комментария

`/comments/add/` — `POST`, `login_required`, `require_POST`.

Поля формы: `target` (ключ), `object_id`, `parent` (необязательно), `next`.

- ответы — **один уровень**: если `parent` сам является ответом, он
  поднимается до корневого комментария. Плоский список ответов вместо дерева —
  осознанно: дерево требует рекурсии в шаблоне и в разметке не читается;
- `parent` обязан принадлежать той же цели, что `target`/`object_id`;
- статус: `draft`, если `CommentSettings.load().premoderation`, иначе
  `published`;
- защита от дублей: тот же автор, та же цель и тот же текст в пределах
  `DUPLICATE_WINDOW` (10 минут) → сообщение, запись не создаётся (двойной клик
  и «отправил, обновил страницу» — частый случай);
- htmx (`HX-Request`) → в ответ уходит обновлённый партиал списка;
- без JS → `messages.success` + редирект на `next` (или на страницу цели);
- аноним → `login_required` уводит на вход с возвратом.

### 3.6 Представление жалобы

`/reports/add/` — GET отдаёт страницу с формой, POST создаёт `Report`.

- доступна анонимно: `reporter` — `request.user` или `None`;
- форма: `reason` (из `ReportReason`), `comment` (необязательный),
  honeypot-поле `website` (скрыто стилем, `required=False`): заполнено —
  считаем ботом, показываем благодарность и ничего не создаём;
- повторная жалоба того же вошедшего пользователя на тот же объект с той же
  причиной в пределах суток → сообщение «жалоба уже отправлена», без записи;
  анонимов не проверяем (троттлинг по IP — P2-17);
- после отправки: `messages.success` («Спасибо, модератор проверит») и
  редирект на `next`;
- письмо модераторам; ошибка SMTP логируется и **не отменяет** создание
  жалобы — то же правило, что в 2.9;
- страница закрыта от индексации (`noindex`), `/reports/add/` добавляется
  в `Disallow` файла `robots.txt`.

### 3.7 Письма модераторам

`moderator_emails()` переезжает из `apps/catalog/emails.py` в
`apps/core/emails.py`: адресаты нужны и каталогу, и модерации. Там же —
общий `notify_moderators(subject, template, context)`, который никогда не
поднимает исключение (падение почты не отменяет действие пользователя).

`apps/catalog/emails.py` остаётся тонкой обёрткой (`notify_moderators_new_team`),
чтобы вызов в `catalog/views.py` не менялся. `apps/moderation/emails.py` —
`notify_moderators_new_report(report)` и шаблон
`templates/moderation/email/new_report_notification.txt`.
