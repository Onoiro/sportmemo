## 1. Цель и границы

**Цель.** Модератор, открыв фото в админке, видит, что такой снимок уже есть в архиве,
и решает, дубликат это или нет. Автоматического слияния нет — только подсказка
с расстоянием Хэмминга.

**Что уже сделано в 3.1 и переделывается в этом подэтапе:**

- `processing.perceptual_hash()` — DCT-II 32×32 → блок 8×8 → **64 бита** → hex 16 символов.
  В 3.5 переводится на **256 бит** (решение владельца 2026-10-27): замеры показали, что
  при 64 битах однотонное красное и однотонное синее дают расстояние **6 из 64**, то есть
  попадают в «вероятный дубликат»;
- `processing.hamming_distance()` — расстояние в битах, нечитаемый хеш даёт 64.
  В 3.5 получает правило для хешей **разной длины** (см. 2.9);
- `Photo.phash` (`CharField(64)`, `db_index`) — **миграция не нужна**, см. 2.9;
- `photos_backfill` берёт фото с пустым `display` **или** пустым `phash`;
- тесты стабильности хеша (масштаб, JPEG-качество, разные картинки) — в
  `tests/test_photo_processing.py`, пороги в них пересчитываются под 256 бит.

**Что входит в подэтап:**

- 256-битный хеш: `perceptual_hash()` на DCT 64×64 → блок 16×16 → hex 64 символа;
- `hamming_distance()`: хеши разной длины считаются максимально далёкими;
- модуль `apps/photos/similar.py`: отбор кандидатов, расчёт расстояния, ранжирование,
  подписи «вероятный дубликат» / «похоже»;
- пороги как константы с обоснованием по замерам;
- страница админки «Похожие фото» (`/admin/photos/photo/<pk>/similar/`) с миниатюрами,
  расстоянием, статусом и ссылкой на карточку кандидата;
- ссылка на эту страницу с карточки фото (readonly-поле в fieldset «Производные»);
- флаг `--rehash` у `photos_backfill` — пересчёт хешей у всех фото. После смены битности
  он **обязателен**, а не опционален: старые 16-символьные хеши с новыми несравнимы;
- тесты, локализация, документация, версия.

**Что не входит:**

| Отложено | Куда |
|---|---|
| Кнопка «Слить в это фото» и само слияние | **3.6** (в 3.5 `Photo` ещё не `MergeableModel`) |
| Поиск дубликатов, повёрнутых на 90/180/270 | **P3-19**, новая (решение владельца 2026-10-27) |
| Проверка похожих при загрузке и показ автору | не делаем: автора дубликатами не грузим, это работа модератора в админке |
| Автоматическая проверка новых загрузок и письмо модератору | не планируется: очередь смотрят в админке (решение 2.7 мастер-плана) |
| Счётчик похожих в списке фото | лишние запросы на каждую строку списка |
| Слияние по расстоянию без человека | инвариант № 5: решает человек |

## 2. Решения

### 2.1 Замеры: 64 против 256 бит (2026-10-27)

Замер на демо-архиве (`media/photos/display`, 12 файлов от `seed_demo`, у 11 из 12
тысячи цветов — это не однотонные заглушки) и на синтетике. Числа — расстояние Хэмминга.

| Пара | 64 бита | 256 бит |
|---|---|---|
| То же фото, масштаб ×0.5 | 0 | ≤ 4 |
| То же фото, масштаб ×2 | 0 | ≤ 4 |
| То же фото, JPEG q30 | 0–12 | ≤ 40 (медиана 2) |
| То же фото, JPEG q10 | 2–14 | ≤ 38 (медиана 5) |
| То же фото, кроп 1 % по краям | 0–6 | ≤ 16 |
| То же фото, кроп 2 % по краям | 0–8 | медиана 33, макс 50 |
| То же фото, яркость +15 % | до 16 | ≤ 34 (медиана 5) |
| То же фото, контраст +15 % | — | ≤ 4 |
| **Разные** фото демо-архива (66 пар) | мин 6, медиана 24 | мин 16, **медиана 104**, p5 = 78 |
| Разные синтетические картинки (шум) | 30–32 | 126–128 |
| Однотонная красная против однотонной синей | **6** | **16** |
| Однотонная серая против серой +1 | — | 52 |

**Вывод.** 256 бит разделяют классы заметно лучше: медиана «разных» выросла с 24/64 (37 %)
до 104/256 (41 %), доля ложных пар упала с 3 из 15 до 1 из 66. Цена — DCT 64×64 вместо
32×32 (вчетверо больше умножений, на фото это доли миллисекунды) и 64 символа в поле
вместо 16. Решение владельца: переходим сразу, база пока пустая.

**Ограничение, которое порогом не лечится (принято владельцем 2026-10-27).**
Монотонные цветовые заливки алгоритм не различает: у однотонной картинки энергия DCT есть
только в нулевой частоте, остальные 255 бит получаются из шума округления, поэтому красная
и синяя заливки дают **16 из 256** при любом размере и сжатии — меньше порога «вероятный
дубликат» (32). Снижать порог нельзя: пережатый JPEG того же снимка даёт до 40 из 256
и перестал бы находиться. Для домена это не дефект: заливок в фотоархиве нет, а подпись
«вероятный дубликат» — **подсказка, а не решение**, страница всегда показывает расстояние
числом. Поведение зафиксировано тестом `test_flat_colours_are_not_distinguished`
и описано в README и в docstring `perceptual_hash()`.

### 2.2 Пороги и подписи (шкала 256 бит)

| Константа | Значение | Доля | Подпись |
|---|---|---|---|
| `LIKELY_DUPLICATE_DISTANCE` | **32** | 12,5 % | «вероятный дубликат» |
| `SIMILAR_DISTANCE_MAX` | **48** | 18,8 % | «похоже» |
| `SIMILAR_LIMIT` | **20** | — | сколько кандидатов показываем |
| `CANDIDATE_POOL_LIMIT` | **5000** | — | сколько фото просматриваем в Python |

Откуда числа: то же фото при масштабе, повторе JPEG, яркости и контрасте укладывается
в 40 из 256, кроп 1 % — в 16. Порог 48 накрывает все варианты «того же снимка», кроме
заметного перекропа (2 % и больше), а «разные» фото начинаются с медианы 104 —
запас почти двукратный. Замер 2.1: при 64 битах 3 пары из 15 разных фото попадали
в «дубликат», при 256 битах и пороге 32 — 1 пара из 66 (и та, судя по размерам и числу
цветов, действительно близкие кадры демо-набора).

Функция `similarity_label(distance)` живёт в `similar.py` рядом с порогами: шаблон
не сравнивает числа, он печатает готовую подпись (то же правило, что `upload_state`
и `Event.date_label`).

### 2.3 Отбор кандидатов: сужение до расчёта

Расстояние Хэмминга не выразить в SQL: hex-строка в базе, XOR в Python. Значит выборку
надо сузить заранее — иначе на 10 000 фото страница тянула бы весь архив.

| Шаг отбора | Правило |
|---|---|
| Вид спорта | тот же, что у фото (`sport_id`) |
| Удалённые | исключены (`deleted_at__isnull=True`) |
| Слитые | отдельного фильтра не нужно: `merge_into()` делает `soft_delete()`, а в 3.5 поля `merged_into` ещё нет |
| Само фото | исключено (`exclude(pk=...)`) |
| Без хеша | исключены (`exclude(phash="")`) |
| Чужой формат хеша | исключены: длина `phash` не равна 64 (см. 2.9) |
| Год | если у фото он есть — окно `±5 лет` **плюс фото без года** (год заполнен далеко не у всех, и дубликат без года иначе не нашёлся бы) |
| Предел | `CANDIDATE_POOL_LIMIT` последних по `-created_at`; превышение пишется в лог |

`Photo.public` не используется: черновик и скрытое фото — законные кандидаты
(дубликат могли загрузить дважды, и оба черновики). Публичность тут не про выдачу,
а про модерацию. Статус каждого кандидата показывается на странице.

### 2.4 Где живёт логика

`apps/photos/similar.py` — новый модуль по образцу `roster.py` и `catalog/filters.py`:
выборка, расчёт, ранжирование и подписи в одном месте, шаблон получает готовый список.
В `admin.py` — только страница и ссылка; в модели — ничего (модель не знает про поиск);
в `processing.py` — только пиксели и биты, без базы.

Модуль импортирует `Photo` — это нормально: `photos` владеет моделью. Обратной
зависимости (`core` → `photos`) не возникает.

### 2.5 Страница в админке: показ без кнопки слияния

Мастер-план 3.5 упоминает кнопку «Слить в это фото», но слияние — подэтап 3.6:
`Photo` ещё не наследует `MergeableModel`, `merge_into()` не существует. В 3.5 страница
**только показывает**; кнопка появится в 3.6 на этой же странице. Разметка строится так,
чтобы её добавление было одним блоком в шаблоне, а не переделкой.

Отдельная страница, а не inline: миниатюры в inline растянули бы карточку фото,
а модератору нужен список с сортировкой и расстояниями. Реализация — как
`MergeActionsMixin.merge_view`: `get_urls()` + `admin_view`, имя
`admin:photos_photo_similar`. Права — `has_view_permission` (страница ничего не меняет).

### 2.6 Ссылка на карточке фото — без счётчика

Readonly-поле `similar_photos` в fieldset «Производные» рядом с `phash` выводит ссылку
«Показать похожие фото». Счётчик («найдено N») не выводится: он стоил бы прохода
по пулу при каждом открытии карточки, а карточку модератор открывает часто.
Хочет узнать — нажимает ссылку.

### 2.7 Второй команды не заводим

Мастер-план упоминает `photos_phash` «если не вошло в бэкфилл» — не вошло: `photos_backfill`
уже берёт фото с пустым `phash`. Нужен только пересчёт **непустых** хешей. Поэтому
в `photos_backfill` добавляется флаг `--rehash`: обработать все фото с `display`, даже если
`phash` уже есть. Второй команды с той же логикой не будет (DRY, пайплайн остаётся один).

### 2.8 Чего страница не делает

- Не показывает кандидатов с расстоянием больше `SIMILAR_DISTANCE_MAX`: список
  «похожих» из далёких фото бесполезен.
- Не сливает, не скрывает, не меняет статусы.
- Не пишет в `ModerationAction`: просмотр — не решение модератора.
- Не показывает `original`: только `thumbnail` от `display` (правило 3.1: оригинал
  не отдаётся никому).

### 2.9 Миграция не нужна, но нужен пересчёт

Поле уже `CharField(max_length=64)`, а 256 бит — это ровно 64 hex-символа: **миграции нет**.
Расширять нечего, `db_index` остаётся.

Но появляется проблема смеси форматов: в базе могут лежать 16-символьные хеши
от старого алгоритма, и сравнение с 64-символьным даёт бессмысленный результат
(проверено: `hamming_distance("9191cece3b393686", "9191…" + "0"*48)` возвращает 64 —
это не «64 бита из 256», а случайная величина). Поэтому:

- `hamming_distance()` при **разной длине** хешей возвращает «бесконечно далеко» —
  длину большего хеша в битах (256), а не случайное число. Правило живёт в одной функции:
  иначе страница похожих показывала бы мусор, а тест это не поймал бы;
- `candidate_pool()` отсекает кандидатов, у которых длина `phash` не равна
  `PHASH_HEX_LENGTH` (64);
- после смены алгоритма обязателен `make photos-backfill --rehash` (шаг 5), иначе
  ни одно старое фото не найдёт себе дубликат. Для демо-архива это одна команда,
  для боевой базы — пункт чек-листа деплоя.

### 2. [x] Хеш 256 бит

- Навыки: koda-coder.
- Файлы: `apps/photos/processing.py`, `tests/test_photo_processing.py`,
  `tests/test_photo_upload.py`, `README.md`.
- Содержание:
  - `_PHASH_DCT_SIZE = 64`, `_PHASH_GRID = 16`, матрица DCT 64×64 считается один раз
    на уровне модуля (как сейчас `_DCT`); `_dct_matrix()` не меняется;
  - `PHASH_HEX_LENGTH = 64` — константа формата, её используют `similar.py`
    и валидация в админке;
  - `perceptual_hash()`: ресайз до 64×64, DCT, блок 16×16, медиана, hex 64 символа;
    docstring — почему 256 бит (замер 2.1) и что хеш считается от `display`;
  - `hamming_distance()`: если `len(first) != len(second)` — вернуть
    `max(len(first), len(second)) * 4` (в битах), с предупреждением в лог;
    иначе прежнее поведение; нечитаемый хеш по-прежнему даёт «далеко»;
  - в `test_photo_processing.py`: `len(result) == 64`, пороги пересчитать
    под 256 бит («то же фото в другом масштабе» ≤ 32, «другой JPEG» ≤ 48,
    «разные картинки» > 48), тест «хеши разной длины максимально далеки»
    и тест `test_flat_colours_are_not_distinguished`, который фиксирует
    фактическое поведение на монотонных заливках (16 < 32), а не желаемое.
- Критерий: `perceptual_hash()` даёт 64 hex-символа; то же фото в другом масштабе
  ≤ 32; разные фото > 48; смешанные длины дают 256; `make test` зелёный.

**Итог шага (2026-10-27).** Сделано: 256-битный хеш, `PHASH_HEX_LENGTH`, правило
«хеши разной длины максимально далеки», пересчитанные пороги в тестах, проверка длины
в `test_photo_upload.py` через константу, раздел README про хеш. `make test` — 1286
тестов зелёные, `ruff` чист.

**Противоречие в плане, решённое владельцем.** Критерий шага требовал тест
«однотонное красное и синее не считаются дубликатом» (> 32), но фактический замер
на новом коде даёт **16 из 256** при любом размере и сжатии: у однотонной картинки
энергия DCT есть только в нулевой частоте, остальные биты — шум округления. Вывод 2.1
сравнивал доли (9 % → 6 %), а не биты, и потому звучал оптимистичнее факта.

Решение владельца (вариант 1): пороги **не снижаем** (иначе пережатый JPEG того же
снимка, дающий до 40 из 256, перестал бы находиться), тест переписан на честное
ожидание 16, ограничение описано в docstring, README и разделе 2.1.

## 5. Открытые вопросы

1. **Порог после набора реального архива.** 32/48 из 256 взяты по замерам на 12 демо-файлах
   и синтетике. Когда появится 200–300 реальных фото, калибровку стоит повторить: числа
   в константах, менять — одна строка, а `--rehash` для смены порога не нужен (порог
   применяется при поиске, а не при записи).
2. **Четыре хеша для поворотов (P3-19).** Заведено в бэклог решением владельца
   2026-10-27. Понадобится, если пойдёт поток сканов одного снимка с разной ориентацией.
3. **Проверка при загрузке.** Решено не делать: автора дубликатами не грузим, это работа
   модератора. Вернуться, если модерация утонет в дублях.
