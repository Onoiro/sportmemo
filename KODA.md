# SportMemo — правила проекта

> **Этот файл синхронизируется с [`AGENTS.md`](AGENTS.md).** Оба содержат один и тот же набор правил:
> `KODA.md` — на русском (для сессий Koda CLI), `AGENTS.md` — на английском (для внешних агентов и
> контрибьюторов). При изменении правил обновляйте **оба** файла.

## Что это за проект

SportMemo — публичный архив спортивных фотографий. На старте — бейсбол в России: детские, юношеские
и ветеранские команды, личные бумажные архивы игроков, тренеров и болельщиков. Пользователи
оцифровывают свои архивы и публикуют их в общий архив с атрибуцией: кто на фото, команда, событие,
год, источник.

- Домен: sportmemo.ru
- Репозиторий: github.com/Onoiro/sportmemo
- Владелец: Андрей Богатырёв (бывший профессиональный бейсболист, личный бумажный архив)

## Архитектурные правила (инварианты)

Нарушение любого из этих правил — дефект, а не стилистическая разница.

1. **Архитектура мультиспортная, продукт одномспортный.** В схеме есть `Sport`, в UI выбора вида
   спорта нет. Появится, когда найдётся евангелист по другому виду спорта.
2. **Никакой бейсбольной специфики в структуре таблиц.** Общие сущности (Team/Event/Person),
   специфика вида спорта — в `attributes` (JSONB). Амплуа питчера хранится как текст в
   `TeamMembership.position`, а не отдельной колонкой под бейсбол.
3. **`Person` ≠ `User`.** Человек на фото — публичная сущность, не требующая аккаунта. Пользователь —
   приватный аккаунт, опционально связанный с `Person` («это я»).
4. **Оригинал фото никогда не перезаписывается.** Обработанная версия — производная, хранится
   в отдельном поле.
5. **Дубликаты не удаляются, а сливаются.** `merged_into` + `merge_into(target)`: перенос связей,
   пометка источника. Операция идемпотентна.
6. **Всё значимое логируется.** `django-simple-history` на всех содержательных моделях + журнал
   модераторских решений (`ModerationAction`).
7. **Уникальность slug — в пределах вида спорта** для `Team`/`Event`. Для `Person` — глобальная
   уникальность с числовым суффиксом при коллизии.
8. **Фамилии несовершеннолетних не публикуются.** Управляется полем `Person.name_visibility`;
   публичный контекст использует `Person.public_name`, а не `display_name`.
9. **Soft-delete, не физическое удаление.** Объект с `deleted_at` исчезает из публичных выборок,
   но сохраняет связи и историю.
10. **Команда создаётся пользователем в статусе `draft`** и публикуется только модератором.

## Стек

Python 3.12, Django 5.2 LTS, Django templates + Bootstrap 5 + htmx + Alpine.js, PostgreSQL 17,
MinIO через `django-storages`, `django-imagekit` (превью), `django-simple-history` (аудит),
`django-allauth` (email + пароль с обязательным подтверждением email), Celery + Redis,
`uv` (пакеты), `ruff` (лингер), `pytest` + `pytest-django` + `factory_boy` (тесты),
Docker Compose + Nginx (инфраструктура).

Публичный UI — серверный рендеринг (Django templates) ради SEO. SPA и API не вводим, пока клиент
один и это сайт.

## Соглашения разработки

- **Пакеты — только `uv`.** `uv sync`, `uv run`, `uv lock` после изменения зависимостей.
  Не добавляйте poetry/pip-требования.
- **Версия проекта живёт в `pyproject.toml`** (`[project] version`). После изменения версии
  выполните `uv lock` (версия проекта попадает в `uv.lock`).
- **Semver.** Перед коммитом применяйте навык `semver-checker`
  (`.agents/skills/semver-checker/SKILL.md`): определить тип бампа по `git diff`, обновить версию,
  добавить строку `Bump version: X → Y (type)` в сообщение коммита.
  Правила: minor — новые возможности и миграции схемы; patch — исправления, UX, переводы;
  none — документация, тесты, CI.
- **Линтер — `ruff`** (`make lint`). Конфигурация в `pyproject.toml`, миграции исключены.
  `make lint` проверяет и линт, и форматирование (`ruff format --check`).
- **Длина строк:** код — 88 символов, комментарии и docstrings — 79. Это стиль Django
  (88 — как в black) с соблюдением PEP 8 для документации. Проверяется правилами `E501`
  и `W505`, обходить их нельзя. Для форматирования — `make format`.
- **Перед коммитом запускайте `make lint` и `make test`.** Это обязательно для любых изменений,
  включая Makefile и конфиги.
- **Тесты — `pytest`** (`make test`), тесты лежат в `tests/`, фабрики — в `tests/factories.py`.
- **Миграции:** `make migrations` / `make migrate`. В тестах используется PostgreSQL (CI) или
  SQLite; файловое хранилище вместо MinIO.
- **Настройки — только через env** (`django-environ`), значения по умолчанию годятся для dev.
  Никаких секретов в коде и в git.
- **Комментарии** — редко и по делу (объясняют «почему», а не «что»). Код и идентификаторы —
  на английском, тексты интерфейса — через i18n.
- **Локализация:** строки UI — в шаблонах и коде через `gettext`, каталоги в `locale/` (ru, en).
  `make i18n` извлекает и компилирует.

## Язык общения

Владелец проекта русскоязычный. Документация, обсуждение и ответы агента — **на русском**.
Идентификаторы кода, имена файлов и технические термины — как принято.

**Сообщения коммитов — на простом английском.** Правило: писать так, чтобы понял человек, для
которого английский не родной.

- Короткие предложения. Одна мысль — одно предложение.
- Простые и частые слова. Без идиом, сленга и игры слов.
- Заголовок — не длиннее 72 символов, в повелительном наклонении: `add`, `fix`, `remove`.
- Тело коммита объясняет **почему**, а не **что**: причина важнее списка изменений.
- Строка версии — по навыку semver-checker: `Bump version: 0.1.0 → 0.2.0 (minor)`.

Пример заголовка: `feat: add photo model and admin page`.
Так нельзя: `feat: flesh out the photo bits` — непонятно, что именно сделано.

## Рабочий процесс

1. Задача берётся из `.koda/backlog.md` → ветка `feature/<короткое-имя>` → коммиты →
   `make lint && make test` → squash-merge в `master` → ветка удаляется.
   PR и GitHub issues не используются: проект ведёт один человек, а бэклог и планы живут
   в репозитории и версионируются вместе с кодом. Issues имеет смысл завести, когда
   появится второй участник.
2. Планы этапов лежат в `.koda/plans/`. Шаги плана отмечаются `[ ]` → `[x]` по мере выполнения.
3. Перед началом крупной работы составляется план и утверждается владельцем.

Мелкие правки — документация, тексты, комментарии, конфиги — можно коммитить прямо
в `master`, без ветки. Ветка нужна, когда меняется код или схема данных.

При squash-merge `git branch -d` не сработает: git не считает такие ветки слитыми.
Сначала проверьте `git diff --stat <ветка> master` (пусто — деревья совпадают),
затем удаляйте через `git branch -D`.

### Публичный интерфейс

- `templates/base.html` и партиалы (`navbar.html`, `footer.html`, `breadcrumbs.html`,
  `messages.html`), партиалы галереи (`templates/photos/partials/grid.html` и `grid_items.html`),
  страницы ошибок `templates/404.html` и `templates/500.html`.
- Тема: `static/css/sportmemo.css` и `static/js/theme.js` — светлая сепия по умолчанию
  и тёмный вариант; выбор в `localStorage`. Инлайн-скрипт в `<head>` ставит тему
  до отрисовки, поэтому мигания при загрузке нет.
- Галерея: `static/js/gallery.js` добавляет `aria-busy` и сообщения в `aria-live` к кнопке
  «показать ещё». Скрипт подключается после htmx; без JavaScript кнопка остаётся обычной
  ссылкой.
- Фронтенд-библиотеки лежат в репозитории (`static/vendor/`: Bootstrap 5, Bootstrap Icons,
  htmx, Alpine.js). CDN не используем: версии, лицензии и контрольные суммы —
  в `static/vendor/README.md`.
- Публичные выборки: `SoftDeleteQuerySet.published()` (фильтр `status=Status.PUBLISHED`),
  `.visible()` (дополнительно `rights_confirmed=True` — для фото). Публичные страницы
  строят цепочку `Model.public.published().visible()`.
- Общие точки входа в публичные выборки — `apps/core/shortcuts.py`: `visible_photos()`,
  `archive_stats()`, `paginate(request, queryset, per_page)` и
  `get_visible_or_404(model, *, request=None, **lookup)`. Хелпер принимает модель параметром
  и не импортирует модели приложений — иначе легко получить цикл `core` ↔ `catalog`/`photos`.
- `get_visible_or_404`: объект из `public`; неопубликованный отдаётся только автору
  (`created_by` / `uploaded_by`) и модератору, остальным — 404; удалённый и слитый —
  404 всем. Автор и модератор видят плашку «не опубликовано»
  (`templates/partials/moderation_notice.html`).
- Списки `/teams/` (24 на страницу), `/events/` (20), `/years/` и `/years/<год>/` (24 фото)
  отдают только видимое. Список годов считается из видимых фото — тот же источник, что
  и счётчик «лет в архиве» на главной.
- Сетка фото — один компонент (`templates/photos/partials/grid.html` + `grid_items.html`),
  общий для главной, страницы года и htmx-фрагмента. «Показать ещё» дописывает следующую
  порцию в конец сетки без перезагрузки: фрагмент `photos:grid` отдаёт только карточки
  и контейнер кнопки, а на последней странице — пустой контейнер с `hx-swap-oob`, и кнопка
  исчезает. Без JavaScript та же кнопка работает обычной ссылкой `?page=N`.
- Размер порции (24) и порядок карточек общие для страницы года и фрагмента
  (`PHOTO_PAGE_SIZE`, `PHOTO_ORDERING` в `apps/core/shortcuts.py`): разойдутся — «показать
  ещё» начнёт пропускать или повторять фото. Страницы, где фильтр не лежит в `request.GET`
  (страница года), передают его в галерею явно — задел для фильтров каталога в 2.15.
- `/photos/<pk>/` открывается анонимно для опубликованного фото с подтверждёнными правами.
  Черновик и фото без подтверждённых прав видит только автор (`uploaded_by`) и модератор —
  отсев делает `get_visible_or_404`. Ссылки на команду и событие появляются, только если те
  опубликованы. В блоке «Люди на фото» имя человека — ссылка на его страницу, если человек
  опубликован; имя черновика выводится текстом. Счётчик просмотров растёт при каждом открытии
  атомарным `update(views_count=F("views_count") + 1)`, а не `save()`, — иначе каждое
  открытие страницы писало бы запись в историю.
- `/teams/<slug>/` и `/events/<slug>/` — «страницы-визитки»: шапка с фактами, описание,
  атрибуты, галерея и связи. Команда показывает свои события и состав с фильтром по годам
  (`?year=1994`).
- `/people/<slug>/` — страница человека: главное фото, публичное имя, годы жизни, биография,
  атрибуты, «Команды и роли», «Фотографии» и «Также известен как». Список `/people/`
  намеренно не создаётся: попасть на страницу можно только с фото или из состава команды.
- Заголовок, `<title>`, описание и крошки страницы человека строятся только из
  `Person.public_name`: `display_name` содержит полную фамилию и в разметку не попадает.
  При `hidden` выводится нейтральная подпись «Имя не указано», но страница открывается —
  иначе фото и команды потеряли бы связь с человеком.
- Варианты имён (`PersonName`) показываются только при `name_visibility = full`
  (свойство `Person.is_full_name_public`) и скрываются в представлении, а не в шаблоне:
  прозвище или фамилия при рождении раскрыли бы скрытую фамилию. При скрытии
  `context["name_variants"]` — пустой список.
- Главное фото страницы человека — `Person.avatar`, если он видим (`Photo.is_public`);
  иначе самое свежее видимое фото с этим человеком (`PHOTO_ORDERING`). Ничего не нашлось —
  заглушка-иконка. Аватар-черновик или аватар без подтверждённых прав игнорируется.
- Биография выводится как есть: ответственность за упоминание фамилий в тексте — на авторе
  и модераторе. Проверки текста нет — это известное ограничение подэтапа.
- Ссылка на команду или событие создаётся, только если объект опубликован
  (`is_published`); иначе название выводится текстом. Правило действует в списках,
  на странице фото, среди команд-участников и в блоке «События года».
- Атрибуты (`Team.attributes`, `Event.attributes`) выводятся парами «подпись, значение»
  через `attribute_items()` (`apps/catalog/views.py`): служебный ключ `demo` скрыт,
  известные ключи переведены, неизвестные выводятся как есть, списки склеены запятыми.
- `Event.date_label` — подпись дат события из месяцев и годов: «Июль 1980»,
  «Июнь — Июль 1988», «Июль 1988 — Август 1989», «1980» или «дата не указана».
  Название месяца берётся из активной локали через `date_format`, отдельных строк
  для месяцев нет.
- Slug'и хранятся с `allow_unicode=True`, поэтому в маршрутах используется свой конвертер
  `<uslug:slug>` (`apps/core/converters.py`, регистрация в `CoreConfig.ready()`): стандартный
  `<slug:...>` пропускает только ASCII и уронил бы `reverse()` на кириллице.
- Блок «События года» на `/years/<год>/` выводит опубликованные события года без пагинации;
  счётчик фото в карточке — общая аннотация `photos_count()` из `apps/core/shortcuts.py`.
- Разделы, которых ещё нет (`/search/`), отдают общий шаблон-заглушку; настоящий поиск
  появится в подэтапе 2.13.
- `apps/core/migrations/0003_site_domain.py` задаёт домен `django.contrib.sites` —
  `sportmemo.ru`. Иначе абсолютные ссылки в письмах и sitemap вели бы на `example.com`.

### Страницы аккаунта

- Вход, регистрация, подтверждение адреса и работа с паролем идут через `django-allauth`
  и живут внутри общего каркаса сайта: navbar, футер, тема. Штатные шаблоны пакета
  **не копируются** — переопределены layout (`templates/allauth/layouts/base.html`)
  и элементы (`templates/allauth/elements/*`), поэтому и наши шаблоны, и непереопределённые
  страницы пакета (список адресов email, повторная аутентификация) получают оформление.
- Обёртка страниц аккаунта — блок `main_inner` в `base.html`, а не `content`: дочерние
  шаблоны allauth переопределяют `content` и затёрли бы обёртку целиком.
- Bootstrap-классы полям ставит миксин `BootstrapFormMixin` (`apps/accounts/forms.py`):
  шаблоны allauth рендерят виджеты как есть, из разметки класс не добавить. Формы
  подключаются через `ACCOUNT_FORMS`; миксин вызывает `super().__init__()` первым, потому
  что allauth добавляет и удаляет поля в своём `__init__`.
- `non_field_errors` в `templates/allauth/elements/fields.html` выводятся первой строкой
  формы: ошибка «Неверный email или пароль» приходит именно так, а не ошибкой поля.
- Тексты писем — в `templates/account/email/` (каркас, подтверждение адреса, сброс пароля);
  в dev письма печатает console email backend. Тема получает префикс `[SportMemo]`
  из имени сайта автоматически.
- msgid наших шаблонов — **русские**: у наших каталогов и каталогов пакета нет общих строк,
  и английские msgid из шаблонов allauth не должны перетирать переводы пакета.
- Ссылки в письмах строятся по домену `django.contrib.sites`; подтверждение адреса
  обязательно (`ACCOUNT_EMAIL_VERIFICATION = "mandatory"`), без него вход уводит
  на «Проверьте почту», а после подтверждения пользователь сразу входит
  (`ACCOUNT_LOGIN_ON_EMAIL_CONFIRMATION`).
- В форме регистрации три обязательных согласия с датами и версией — это юридическая
  защита проекта, поэтому галочки обязательные и без значений по умолчанию.
- Заявка «это я» (`User.person` через модерацию) отложена: без модерации любой мог бы
  «присвоить» чужую страницу. В профиле (2.8б) есть только ссылка на уже связанного человека.

### Профиль пользователя

- `/accounts/profile/` — наша страница (`apps/accounts/views.py`, `accounts:profile`),
  а не шаблон allauth: наследуется от `base.html` и получает крошки. От layout allauth
  наследоваться нельзя — он даёт узкую колонку `.auth-shell`, рассчитанную на одну форму.
- Маршрут подключается **перед** `allauth.urls`: адреса не пересекаются, но порядок делает
  приоритет наших страниц явным.
- В профиле меняется только `display_name` («как к вам обращаться»). Email и пароль правятся
  на своих страницах allauth, рядом с ними стоят ссылки: два места для одного значения
  разошлись бы.
- Сохранение — POST-redirect-GET с `messages.success`. Без редиректа обновление страницы
  повторяло бы отправку формы.
- Роль выводится только модератору и администратору (`user.is_moderator`): обычному
  пользователю строка «пользователь» ничего не сообщает.
- Блок «Мой профиль в архиве» показывает ссылку только при существующей связи `User.person`.
  Кнопки «Это я» нет осознанно: заявка не реализована, обещать несуществующее нельзя.
- Меню пользователя в navbar собирается только из существующих маршрутов — иначе
  `NoReverseMatch` уронил бы каждую страницу. Имя в кнопке обрезается CSS
  (`.account-menu__name`), а не в представлении: длинное значение иначе растянуло бы шапку.
- Страницы `account_email` и `account_reauthenticate` **не переопределяются**: каркас 2.8а
  оформляет их сам, а скрипты allauth приходят через блок `extra_body` → `extra_js`.
  Проверять их нужно после обновления пакета: без этих скриптов кнопки управления адресом
  не работают.

### Создание и правка команды

- Команда создаётся пользователем **черновиком** (`status=draft`) с `created_by`:
  публикует её модератор. До публикации команду видят автор и модератор, остальным
  страница отдаёт 404 — правило `get_visible_or_404` уже это обеспечивает.
- Правит команду автор и модератор, остальным — **404, а не 403**: не раскрываем
  существование чужого черновика. Проверка живёт в `can_edit_team()` и применяется одинаково
  к GET и POST; удалённую команду не правит даже автор (объект берётся из `Team.public`).
- Правка опубликованной команды **не сбрасывает статус**: изменения автора не должны ждать
  модератора, но всё пишется в историю (`django-simple-history`). К повторной модерации
  вернёмся, если появится вандализм.
- **Вид спорта в форме не показывается** — продукт односпортный (инвариант № 1). Значение
  берёт `default_sport()` (`apps/core/shortcuts.py`): первый активный вид спорта по порядку
  сортировки. Активных нет — форма недоступна с сообщением, а не 500-й ошибкой.
- **Дубликаты названий не блокируются.** «Соколы» есть в разных городах, и решение
  «дубликат или одноимённая команда» принимает человек. Форма (`TeamForm.find_duplicates()`)
  ищет команды с тем же названием (`iexact`) в том же виде спорта **включая чужие черновики**
  — иначе за время модерации появятся три одинаковые. Найдено — требуется чекбокс
  «Я проверил(а), это другая команда». Чужой черновик показывается только названием
  и статусом, без ссылки; на опубликованную команду ссылка даётся. Настоящие дубликаты
  сливает модератор.
- **Slug команды уникален в пределах вида спорта**, поэтому генерируется через `_unique_slug()`
  с числовым суффиксом (`динамо`, `динамо-2`). Область поиска — `Team.objects`, а не `public`:
  `UniqueConstraint` про `deleted_at` не знает, и «свободный» по мнению `public` slug всё
  равно упал бы на уровне базы. Правка названия существующий slug не меняет — URL не должен
  ломаться.
- **Клуб с несколькими командами** заводится отдельными записями: «Русстар», «Русстар-2»,
  «Русстар (юноши 1992 г. р.)». Подсказка об этом — help-текст поля названия. Отдельная
  сущность «клуб» с полем `parent` отложена (идея I-9 в бэклоге): навигация в архиве идёт
  по годам и людям, а «все фото клуба» соберёт поиск.
- Письмо модераторам (`apps/catalog/emails.py`) уходит адресатам из базы (роль модератор
  или админ, активные), а не из настройки: список модераторов меняется. Ошибка SMTP
  логируется и **не отменяет** создание команды; нет модераторов — письмо не отправляется,
  в лог пишется предупреждение.
- Маршруты `teams/new/` и `teams/mine/` объявляются **до** `teams/<uslug:slug>/`:
  конвертер `uslug` пропускает любые буквы и дефисы и иначе перехватил бы оба адреса.
- `BootstrapFormMixin` живёт в `apps/core/forms.py`, а не в `accounts`: формы команд тоже
  должны получать оформленные поля, а импорт из `accounts` в `catalog` — лишняя связь
  между приложениями.

### Правила работы с админкой

- Модерация (опубликовать / скрыть / отклонить / мягко удалить / восстановить) — действия
  списка; каждое решение пишется в `ModerationAction`.
- Слияние дубликатов — действие «Слить дубликаты в один объект»: открывает отдельную страницу
  выбора цели (`admin/core/merge_form.html`), потому что цель не должна совпадать с источниками.
- `ModerationAction` доступен только для чтения: журнал заполняется действиями, а не вручную.

### Правила для кода

- Модели, у которых есть `deleted_at`, обязаны иметь `objects` (всё, включая удалённое) и
  `public` (без удалённого). Публичные выборки — только через `public`.
- Поля с `auto_now_add` нельзя заполнять из JSON-фикстур — начальные данные задаются
  data-миграцией.
- Новые поля FK на `User` в `catalog`/`photos` не создают цикла: `accounts` мигрирует первым,
  а обратные связи на `catalog` идут отдельной миграцией (`accounts/0002_...`).
- Демо-данные создаются командой `seed_demo` (`make seed-demo`) и помечаются
  `attributes={"demo": true}`; удаляются `make seed-demo-flush`. Это инструмент разработки:
  на боевую базу их не переносим, в чек-лист деплоя входит «демо-данные не переносить».
- Публичные страницы отдают только опубликованное и не удалённое:
  `Model.public.published()` (и `.visible()` для фото). Черновики в публичную выдачу
  не попадают ни на одной странице.
- Новая публичная страница берёт выборку через `apps/core/shortcuts.py`, а не собирает
  цепочку `public.published()` вручную: правило отсева должно быть в одном месте.
- Ссылка на неопубликованную сущность не создаётся нигде: перед ссылкой проверяется
  `is_published`, иначе название выводится текстом. Черновик не должен утекать по прямой
  ссылке и попадать в индекс поисковиков.
- Люди в публичном контексте выводятся через `Person.public_name`, а состав команды
  фильтруется по `Person.public.published()`: человек-черновик не попадает в публичную
  выдачу, даже если записан в команду. Фильтр публичности применяется до фильтра по годам
  и до среза превью.
- Состав команды фильтруется по годам (`?year=1994`), а не показывается отдельной страницей:
  архив наполняется по чужим альбомам, и «состав года» читался бы как полный список.
  Формулировки не обещают полноты — «Люди в команде, 1994 год» и подпись «В архиве указаны
  не все, кто играл». Отдельная страница с группировкой по годам отложена (идея I-8).
- Логика периодов состава живёт в `apps/catalog/roster.py` и не делает запросов к базе:
  её проверяют unit-тесты. Незакрытый период (`year_to` пуст) заканчивается последним годом,
  известным по команде, — без этой границы человек «размазался» бы на все годы до сегодняшнего.
  Один `year_to` без `year_from` даёт единственный год.
- Подпись годов членства — свойство `TeamMembership.years_label`, а не разметка шаблона:
  тем же свойством пользуются страница человека и состав команды, и форматов не должно быть два.
- Правило приватности имени живёт в представлении, а не в шаблоне: варианты имён
  (`PersonName`) кладутся в контекст только при `Person.is_full_name_public`. Смена
  шаблона не должна раскрывать скрытую фамилию.
- `display_name` в публичную разметку не попадает никогда — только `public_name`:
  `display_name` заполняется в `Person.save()` полным именем с фамилией.
- Главное фото страницы человека выбирается правилом «аватар, если видим, иначе первое
  видимое фото»: проверка видимости — через `Photo.is_public`, не сравнением статусов
  в шаблоне.
- Счётчик фото в карточках команд и событий берётся из общей аннотации `photos_count()`
  (`apps/core/shortcuts.py`): своя копия аннотации в представлении дала бы другой ответ
  на той же странице.
- Slug'и кириллические, поэтому для маршрутов с `SlugModel` используется конвертер `uslug`
  (`apps/core/converters.py`), а не стандартный `<slug:...>`. `QueryDict` для ссылок галереи
  собирается из словаря, а не из строки: кириллица и `&` в slug'е сломали бы адрес.
- Счётчик просмотров фото растёт через `QuerySet.update()`, а не `save()`: `save()` писал бы
  запись в историю при каждом открытии страницы и засорил бы журнал.
- SEO-метатеги (`title`, `description`, `canonical`, `og:*`) собираются во вьюхах через
  `page_meta()` (`apps/core/seo.py`), а не в шаблонах: картинка карточки зависит от данных
  страницы, а правило приватности имени должно жить в одном месте. Партиал
  `templates/partials/meta.html` только выводит готовый словарь `meta`. `noindex` — дефолт
  процессора `seo_meta` для страниц, которые не задали свой `meta`: новая страница не попадёт
  в поисковики, пока автор не опишет её явно. Контекст представления перекрывает процессор,
  поэтому `meta` из `page_meta()` должен быть полным, а не частичным.
- Строки интерфейса — только через `gettext`. После добавления строк выполняется `make i18n`;
  `makemessages` помечает новые строки `fuzzy`, если нашёл похожую старую, а `msgfmt`
  пропускает fuzzy — после извлечения проверяйте fuzzy-блоки и снимайте флаги. Для русского
  каталога fuzzy-записи и пустые `msgstr` выравниваются по `msgid`; для английского каталога
  переводы новых строк заполняются вручную (автоперевод не используем).
- Комментарии в шаблонах — только `{% comment %}...{% endcomment %}`. `{# ... #}` в Django
  работает в пределах **одной строки**: закрывающая `#}` на следующей строке не распознаётся,
  и текст комментария попадает в HTML.
- `django-imagekit` кэширует факт «превью существует» в Django-кэше. В тестах `MEDIA_ROOT`
  у каждого теста свой, поэтому в `tests/conftest.py` есть фикстура `cleared_cache` —
  без неё тесты превью падают на чтении чужого файла.
