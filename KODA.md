# SportMemo — правила проекта

> **Этот файл синхронизируется с [`AGENTS.md`](AGENTS.md).** Оба содержат один и тот же набор правил:
> `KODA.md` — на русском (для сессий Koda CLI), `AGENTS.md` — на английском (для внешних агентов и
> контрибьюторов). При изменении правил обновляйте **оба** файла.

## Что это за проект

SportMemo — публичный архив спортивных фотографий. На старте — бейсбол в России: детские, юношеские
и ветеранские команды, личные бумажные архивы игроков, тренеров и болельщиков. Пользователи
оцифровывают свои архивы и публикуют их в общий архив с атрибуцией: кто на фото, команда, событие,
год, источник.

- Домен: sportmemo.ru
- Репозиторий: github.com/Onoiro/sportmemo
- Владелец: Андрей Богатырёв (бывший профессиональный бейсболист, личный бумажный архив)

## Архитектурные правила (инварианты)

Нарушение любого из этих правил — дефект, а не стилистическая разница.

1. **Архитектура мультиспортная, продукт одномспортный.** В схеме есть `Sport`, в UI выбора вида
   спорта нет. Появится, когда найдётся евангелист по другому виду спорта.
2. **Никакой бейсбольной специфики в структуре таблиц.** Общие сущности (Team/Event/Person),
   специфика вида спорта — в `attributes` (JSONB). Амплуа питчера хранится как текст в
   `TeamMembership.position`, а не отдельной колонкой под бейсбол.
3. **`Person` ≠ `User`.** Человек на фото — публичная сущность, не требующая аккаунта. Пользователь —
   приватный аккаунт, опционально связанный с `Person` («это я»).
4. **Оригинал фото никогда не перезаписывается.** Обработанная версия — производная, хранится
   в отдельном поле.
5. **Дубликаты не удаляются, а сливаются.** `merged_into` + `merge_into(target)`: перенос связей,
   пометка источника. Операция идемпотентна.
6. **Всё значимое логируется.** `django-simple-history` на всех содержательных моделях + журнал
   модераторских решений (`ModerationAction`).
7. **Уникальность slug — в пределах вида спорта** для `Team`/`Event`. Для `Person` — глобальная
   уникальность с числовым суффиксом при коллизии.
8. **Фамилии несовершеннолетних не публикуются.** Управляется полем `Person.name_visibility`;
   публичный контекст использует `Person.public_name`, а не `display_name`.
9. **Soft-delete, не физическое удаление.** Объект с `deleted_at` исчезает из публичных выборок,
   но сохраняет связи и историю.
10. **Команда создаётся пользователем в статусе `draft`** и публикуется только модератором.

## Стек

Python 3.12, Django 5.2 LTS, Django templates + Bootstrap 5 + htmx + Alpine.js, PostgreSQL 17,
MinIO через `django-storages`, `django-imagekit` (превью), `django-simple-history` (аудит),
`django-allauth` (email + пароль с обязательным подтверждением email), Celery + Redis,
`uv` (пакеты), `ruff` (лингер), `pytest` + `pytest-django` + `factory_boy` (тесты),
Docker Compose + Nginx (инфраструктура).

Публичный UI — серверный рендеринг (Django templates) ради SEO. SPA и API не вводим, пока клиент
один и это сайт.

## Соглашения разработки

- **Пакеты — только `uv`.** `uv sync`, `uv run`, `uv lock` после изменения зависимостей.
  Не добавляйте poetry/pip-требования.
- **Версия проекта живёт в `pyproject.toml`** (`[project] version`). После изменения версии
  выполните `uv lock` (версия проекта попадает в `uv.lock`).
- **Semver.** Перед коммитом применяйте навык `semver-checker`
  (`.agents/skills/semver-checker/SKILL.md`): определить тип бампа по `git diff`, обновить версию,
  добавить строку `Bump version: X → Y (type)` в сообщение коммита.
  Правила: minor — новые возможности и миграции схемы; patch — исправления, UX, переводы;
  none — документация, тесты, CI.
- **Линтер — `ruff`** (`make lint`). Конфигурация в `pyproject.toml`, миграции исключены.
  `make lint` проверяет и линт, и форматирование (`ruff format --check`).
- **Длина строк:** код — 88 символов, комментарии и docstrings — 79. Это стиль Django
  (88 — как в black) с соблюдением PEP 8 для документации. Проверяется правилами `E501`
  и `W505`, обходить их нельзя. Для форматирования — `make format`.
- **Перед коммитом запускайте `make lint` и `make test`.** Это обязательно для любых изменений,
  включая Makefile и конфиги.
- **Тесты — `pytest`** (`make test`), тесты лежат в `tests/`, фабрики — в `tests/factories.py`.
- **Миграции:** `make migrations` / `make migrate`. В тестах используется PostgreSQL (CI) или
  SQLite; файловое хранилище вместо MinIO.
- **Настройки — только через env** (`django-environ`), значения по умолчанию годятся для dev.
  Никаких секретов в коде и в git.
- **Комментарии** — редко и по делу (объясняют «почему», а не «что»). Код и идентификаторы —
  на английском, тексты интерфейса — через i18n.
- **Локализация:** строки UI — в шаблонах и коде через `gettext`, каталоги в `locale/` (ru, en).
  `make i18n` извлекает и компилирует.

## Язык общения

Владелец проекта русскоязычный. Документация, обсуждение и ответы агента — **на русском**.
Идентификаторы кода, имена файлов и технические термины — как принято.

**Сообщения коммитов — на простом английском.** Правило: писать так, чтобы понял человек, для
которого английский не родной.

- Короткие предложения. Одна мысль — одно предложение.
- Простые и частые слова. Без идиом, сленга и игры слов.
- Заголовок — не длиннее 72 символов, в повелительном наклонении: `add`, `fix`, `remove`.
- Тело коммита объясняет **почему**, а не **что**: причина важнее списка изменений.
- Строка версии — по навыку semver-checker: `Bump version: 0.1.0 → 0.2.0 (minor)`.

Пример заголовка: `feat: add photo model and admin page`.
Так нельзя: `feat: flesh out the photo bits` — непонятно, что именно сделано.

## Рабочий процесс

1. Задача берётся из `.koda/backlog.md` → ветка `feature/<короткое-имя>` → коммиты →
   `make lint && make test` → squash-merge в `master` → ветка удаляется.
   PR и GitHub issues не используются: проект ведёт один человек, а бэклог и планы живут
   в репозитории и версионируются вместе с кодом. Issues имеет смысл завести, когда
   появится второй участник.
2. Планы этапов лежат в `.koda/plans/`. Шаги плана отмечаются `[ ]` → `[x]` по мере выполнения.
3. Перед началом крупной работы составляется план и утверждается владельцем.

Мелкие правки — документация, тексты, комментарии, конфиги — можно коммитить прямо
в `master`, без ветки. Ветка нужна, когда меняется код или схема данных.

При squash-merge `git branch -d` не сработает: git не считает такие ветки слитыми.
Сначала проверьте `git diff --stat <ветка> master` (пусто — деревья совпадают),
затем удаляйте через `git branch -D`.

**Решения этапа 3, которые нельзя нарушать:**

- **Права на фото — «Упрощённый UGC».** Отдельных полей заявленных прав и выбора лицензии
  нет: ответственность за контент переносится в Пользовательское соглашение, под кнопкой
  загрузки стоит приписка про Правила сервиса. Модератор проверяет только релевантность
  и качество заполнения, не права. `rights_confirmed` больше не участвует в условии
  видимости — это исторический флаг для админки. Претензии правообладателя и жалобы
  «это я» идут через готовый механизм жалоб (`COPYRIGHT` и `PRIVACY`).
- **Оригинал неприкосновенен.** Кроп — это `crop_data` (JSON с версией), а не новый файл.
  Публичные версии (`thumbnail`, `preview`) строятся от `display`, а не от `original`.
  Оригинал не попадает ни в публичную разметку, ни в `og:image`.
- **Порядок обработки:** `exif_transpose` → поворот пользователя (только 0/90/180/270) →
  кроп → подготовка `display`. Нарушение порядка даёт сдвиг кадра на телефонах.
- **Слитое фото отдаёт 301 на канон**, если канон публичный, иначе 404. Цепочки слияний
  запрещены: цель слияния всегда каноничная (`merged_into__isnull=True`).
- **EXIF хранится по белому списку**, GPS не хранится нигде. `Artist` и `Copyright`
  остаются подсказкой модератору. Год из `DateTimeOriginal` — только предзаполнение формы,
  не запись в базу.
- **`Photo.uploaded_by` — `SET_NULL`:** архив важнее аккаунта, фото остаются анонимными.
  Удаление аккаунта — анонимизация, а не `DELETE`.

### Публичный интерфейс

Компоненты и страницы. Правила отсева, приватности и обоснования — в «Правилах для кода».

- Каркас: `templates/base.html` и партиалы (`navbar`, `footer`, `breadcrumbs`, `messages`),
  страницы ошибок `templates/404.html` и `templates/500.html`. Тема — `static/css/sportmemo.css`
  и `static/js/theme.js`: светлая сепия по умолчанию и тёмный вариант, выбор в `localStorage`;
  инлайн-скрипт в `<head>` ставит тему до отрисовки, поэтому мигания при загрузке нет.
  Фронтенд-библиотеки лежат в репозитории (`static/vendor/`: Bootstrap 5, Bootstrap Icons,
  htmx, Alpine.js). CDN не используем: версии, лицензии и контрольные суммы —
  в `static/vendor/README.md`.
- Прогрессивное улучшение: `static/js/gallery.js` и `static/js/comments.js` добавляют
  `aria-busy` и сообщения в `aria-live`. Без JavaScript кнопка «показать ещё» остаётся обычной
  ссылкой `?page=N`, а форма комментария отправляется обычным POST с редиректом назад.
- Галерея — один компонент (`templates/photos/partials/grid.html` + `grid_items.html`), общий
  для главной, страницы года и htmx-фрагмента `photos:grid`. «Показать ещё» дописывает
  следующую порцию без перезагрузки: фрагмент отдаёт только карточки и контейнер кнопки,
  а на последней странице — пустой контейнер с `hx-swap-oob`, и кнопка исчезает.
- Страницы: `/teams/` (24 на страницу) и `/events/` (20) — списки; `/years/` и `/years/<год>/`
  (24 фото) — по годам, плюс блок «События года»; `/photos/<pk>/` — фото; `/teams/<slug>/`
  и `/events/<slug>/` — «визитки» (шапка с фактами, описание, атрибуты, галерея, связи);
  `/people/<slug>/` — человек (главное фото, публичное имя, годы жизни, биография, атрибуты,
  «Команды и роли», «Фотографии», «Также известен как»). Списка `/people/` намеренно нет:
  попасть на страницу можно только с фото или из состава команды.
- Атрибуты (`Team.attributes`, `Event.attributes`) выводятся парами «подпись, значение»
  через `attribute_items()` (`apps/catalog/views.py`): служебный ключ `demo` скрыт, известные
  ключи переведены, неизвестные выводятся как есть, списки склеены запятыми.
- `Event.date_label` — подпись дат события из месяцев и годов («Июль 1980»,
  «Июнь — Июль 1988», «Июль 1988 — Август 1989», «1980», «дата не указана»): название месяца
  берётся из активной локали через `date_format`, отдельных строк для месяцев нет.
- `/search/` (`search:index`, приложение `apps/search`): инфраструктура — подэтап 2.12,
  интерфейс — 2.13.
- `/photos/upload/`, `/photos/mine/` (3.2) и `/rules/` (`core:rules`) — загрузка фото,
  кабинет автора и правила сервиса. Форма и кабинет закрыты `noindex`; `/rules/`
  индексируется.
- Публичные выборки: `SoftDeleteQuerySet.published()` (фильтр `status=Status.PUBLISHED`).
  Метод `.visible()` **удалён** в 3.1: после решения 2.1 он не фильтровал ничего, а пустая
  обёртка соврала бы читателю. Общие точки входа —
  `apps/core/shortcuts.py`: `visible_photos()`, `archive_stats()`, `paginate()`,
  `photos_count()` и `get_visible_or_404(model, *, request=None, **lookup)`. Хелпер принимает
  модель параметром и не импортирует модели приложений — иначе легко получить цикл
  `core` ↔ `catalog`/`photos`. `get_visible_or_404`: объект из `public`; неопубликованный
  отдаётся только автору (`created_by` / `uploaded_by`) и модератору, остальным — 404;
  удалённый и слитый — 404 всем; автор и модератор видят плашку «не опубликовано»
  (`templates/partials/moderation_notice.html`).
- Размер порции (24) и порядок карточек общие для страницы года и htmx-фрагмента
  (`PHOTO_PAGE_SIZE`, `PHOTO_ORDERING` в `apps/core/shortcuts.py`): разойдутся — «показать
  ещё» начнёт пропускать или повторять фото. Страницы, где фильтр не лежит в `request.GET`
  (страница года), передают его в галерею явно.
- Фильтры каталога живут в `apps/catalog/filters.py`: справочники вариантов, разбор
  параметров и адрес `canonical` собираются там, а шаблон получает готовую панель
  (`FilterPanel` → `SelectField`) и ничего не сравнивает с `request.GET`. Справочники
  считаются по всей публичной выборке, а не по отфильтрованной: иначе выбранный город исчез
  бы из списка после выбора десятилетия. Невалидное значение параметра считается
  неприменённым фильтром — опечатка в ссылке не должна давать «ничего не найдено».
  `canonical` собирается по нормализованным параметрам (`page_meta(..., canonical_query=)`):
  мусор и номер страницы в него не попадают.
- Список годов на `/years/` считается из видимых фото — тот же источник, что и счётчик
  «лет в архиве» на главной.
- Инфраструктура: `Dockerfile` + `docker-compose.yml` (db, redis, minio, web, worker),
  CI (`.github/workflows/ci.yml`: ruff, проверка миграций, pytest на 3.12 и 3.13
  с PostgreSQL 17), навык `.agents/skills/semver-checker/`.
- Домен `django.contrib.sites` задаёт data-миграция `apps/core/migrations/0003_site_domain.py`
  (`sportmemo.ru`): иначе абсолютные ссылки в письмах и sitemap вели бы на `example.com`.

### Аккаунты, команды, комментарии

**Аккаунты (2.8а).** Вход, регистрация, подтверждение адреса и пароль идут через
`django-allauth` внутри общего каркаса сайта. Штатные шаблоны пакета **не копируются**:
переопределены layout (`templates/allauth/layouts/base.html`) и элементы
(`templates/allauth/elements/*`), поэтому и наши шаблоны, и непереопределённые страницы пакета
получают оформление. Обёртка страниц аккаунта — блок `main_inner` в `base.html`, а не
`content`: дочерние шаблоны allauth переопределяют `content` и затёрли бы обёртку целиком.
Bootstrap-классы полям ставит `BootstrapFormMixin` (`apps/accounts/forms.py`); формы
подключаются через `ACCOUNT_FORMS`, миксин вызывает `super().__init__()` первым, потому что
allauth добавляет и удаляет поля в своём `__init__`. `non_field_errors` выводятся первой
строкой формы (так приходит «Неверный email или пароль»). Тексты писем —
`templates/account/email/` (каркас, подтверждение адреса, сброс пароля), в dev письма печатает
console backend, тема получает префикс `[SportMemo]` из имени сайта. msgid наших шаблонов —
**русские**: у наших каталогов и каталогов пакета нет общих строк, и английские msgid
из шаблонов allauth не должны перетирать переводы пакета. Подтверждение адреса обязательно
(`ACCOUNT_EMAIL_VERIFICATION = "mandatory"`), после подтверждения пользователь сразу входит
(`ACCOUNT_LOGIN_ON_EMAIL_CONFIRMATION`). В регистрации три обязательных согласия с датами
и версией — юридическая защита проекта, галочки без значений по умолчанию. Заявка «это я»
(`User.person` через модерацию) отложена: без модерации любой мог бы «присвоить» чужую страницу.

**Профиль (2.8б).** `/accounts/profile/` — наша страница (`apps/accounts/views.py`,
`accounts:profile`), наследуется от `base.html` и получает крошки; от layout allauth
наследоваться нельзя — он даёт узкую колонку `.auth-shell` под одну форму. Маршрут
подключается **перед** `allauth.urls` (адреса не пересекаются, но порядок делает приоритет
наших страниц явным). Меняется только `display_name` («как к вам обращаться»); email и пароль
правятся на своих страницах allauth, рядом стоят ссылки — два места для одного значения
разошлись бы. Сохранение — POST-redirect-GET с `messages.success`: без редиректа обновление
страницы повторяло бы отправку. Роль выводится только модератору и администратору
(`user.is_moderator`). Блок «Мой профиль в архиве» показывает ссылку только при существующей
связи `User.person`; кнопки «Это я» нет осознанно — заявка не реализована. Меню пользователя
в navbar собирается только из существующих маршрутов (иначе `NoReverseMatch` уронил бы каждую
страницу), имя обрезается CSS (`.account-menu__name`). Страницы `account_email`
и `account_reauthenticate` **не переопределяются**: каркас 2.8а оформляет их сам, скрипты
приходят через `extra_body` → `extra_js`; проверять их после обновления пакета — без скриптов
кнопки управления адресом не работают.

**Создание и правка команды (2.9).** Команда создаётся **черновиком** (`status=draft`)
с `created_by`, публикует её модератор; до публикации команду видят автор и модератор,
остальным 404. Правит автор и модератор, остальным — **404, а не 403**: не раскрываем
существование чужого черновика; проверка живёт в `can_edit_team()` и применяется одинаково
к GET и POST, объект берётся из `Team.public` (удалённую не правит даже автор). Правка
опубликованной команды **не сбрасывает статус** — изменения автора не должны ждать
модератора, но всё пишется в историю. **Вид спорта в форме не показывается** — продукт
односпортный (инвариант № 1), значение берёт `default_sport()`; активных видов нет — форма
недоступна с сообщением, а не 500-й ошибкой. **Дубликаты названий не блокируются** («Соколы»
есть в разных городах, решение принимает человек): `TeamForm.find_duplicates()` ищет команды
с тем же названием (`iexact`) в том же виде спорта **включая чужие черновики** — иначе за время
модерации появятся три одинаковые; найдено — требуется чекбокс «Я проверил(а), это другая
команда», чужой черновик показывается только названием и статусом, без ссылки. **Slug команды
уникален в пределах вида спорта** (`_unique_slug()` с числовым суффиксом), область поиска —
`Team.objects`, а не `public`: `UniqueConstraint` про `deleted_at` не знает. Правка названия
существующий slug не меняет — URL не должен ломаться. **Клуб с несколькими командами**
заводится отдельными записями («Русстар», «Русстар-2», «Русстар (юноши 1992 г. р.)»), подсказка
об этом — help-текст поля названия; отдельная сущность «клуб» с полем `parent` отложена
(идея I-9). Письмо модераторам (`apps/catalog/emails.py`) уходит адресатам из базы (роль
модератор или админ, активные), а не из настройки; ошибка SMTP логируется и **не отменяет**
создание команды, нет модераторов — письмо не отправляется. Маршруты `teams/new/` и
`teams/mine/` объявляются **до** `teams/<uslug:slug>/`: конвертер `uslug` пропускает любые
буквы и дефисы и иначе перехватил бы оба адреса. `BootstrapFormMixin` живёт в
`apps/core/forms.py`, а не в `accounts`: формы команд тоже должны получать оформленные поля,
а импорт из `accounts` в `catalog` — лишняя связь между приложениями.

**Комментарии и жалобы (2.14).** Комментарий **публикуется сразу**: премодерация выключена
по умолчанию — архив наполняется по чужим альбомам, и уточнение «это не Иванов, а Петров»
должно появляться сразу, а не после модератора. Включается переключателем, а не правкой кода:
`CommentSettings` — singleton-настройка в админке (одна строка, создаётся data-миграцией;
добавление и удаление записей запрещены, список ведёт на форму правки), читается через кеш
и сбрасывает его при сохранении — переключатель действует сразу. **Видимость комментариев
живёт в `apps/comments/services.py`** (`comments_context()`, `visible_comments_q()`), а не
в шаблонах: три страницы лежат в разных приложениях, и своя выборка в каждой дала бы разные
правила. Что кто видит: аноним и вошедший — опубликованное; автор — дополнительно свой
комментарий в `draft` с плашкой «на проверке»; скрытое, отклонённое и удалённое не видит никто,
включая автора (это решение модератора, а не черновик), и ответ скрытого корневого
комментария не показывается. **Ответы одноуровневые**: ответ на ответ форма поднимает
к корневому комментарию — дерево требует рекурсии в шаблоне и в разметке читается хуже.
**Белый список целей — `apps/comments/targets.py`** (фото, команда, событие): generic FK сам
цель не ограничивает, без списка через форму можно было бы создать комментарий к пользователю
или к жалобе; объект берётся через `get_visible_or_404`. **Защита от дублей** — тот же автор,
та же цель и тот же текст в пределах 10 минут; троттлинг по IP отложен (P2-17), правка
и удаление своего комментария — тоже (P2-16). Форма работает без JavaScript; с htmx блок
перерисовывается целиком (`hx-swap="outerHTML"`), `next` проверяется от открытого редиректа.
**Жалоба — отдельная страница** `/reports/add/`, доступная анонимно: модальное окно требует
JavaScript, а ссылку на жалобу хочется переслать. **Кнопок модерации на публичных страницах
нет**: админка — одно место для решений, и каждое попадает в `ModerationAction` и в историю.
**Письма модераторам уходят только о жалобах** (о новых комментариях при выключенной
премодерации это поток писем); общая часть — `apps/core/emails.py` (`moderator_emails()`,
`notify_moderators()`), обёртки с текстом — в `catalog` и `moderation`; `notify_moderators()`
никогда не поднимает исключение. **Защита формы жалобы** — honeypot-поле `website`: заполнено —
показываем благодарность и ничего не записываем (отвечать ботом отказом значит подсказывать,
что его раскусили). Повторная жалоба того же вошедшего на тот же объект с той же причиной
в пределах суток не создаётся; анонимов не проверяем. `/reports/add/` закрыт от индексации
(`noindex`) и добавлен в `robots.txt`.

**Загрузка фото (3.2).** Форма `/photos/upload/` (только вошедшим) и кабинет
`/photos/mine/`. **Правило статуса — одна точка:** `initial_status_for(user)`
в `apps/photos/services.py` отдаёт `draft`; функция существует ради P3-10
(доверенный автор), тогда правило поменяется в одном месте, а не в форме
и представлении по отдельности. **Команда и событие вводятся текстом**
с подсказкой из нативного `<datalist>`, сервер резолвит введённое через
`resolve_by_name()`: без JavaScript поле работает как обычный текст.
Неоднозначное название (два «Соколы» в разных городах) не угадывается,
а просит уточнить — фото не на той команде хуже пустого поля; выборка
резолва включает свой черновик (команду заводят прямо перед загрузкой фото
в неё). **Лимит суток — скользящие 24 часа** (`uploads_today()`, менеджер
`objects`, а не `public`: удалённое фото квоту не возвращает).
**Состояния плашки — `Photo.upload_state`** (семь ключей: `deleted`,
`failed`, `processing`, `published`, `hidden`, `rejected`, `review`)
и `upload_state_label` в модели: шаблон печатает готовое, а не сравнивает
статусы. Порядок проверок от самого сильного признака — удалённое фото
с `published` читается как «Удалено». **Обработка пока синхронная** —
`process_photo()` вызывается из представления сразу после сохранения;
в 3.3 это станет задачей Celery, и точка вызова одна. **`/rules/`**
(`core:rules`) открыта анонимно и индексируется, ссылка стоит под кнопкой
загрузки и в футере; в тексте отдельно авторское право (`COPYRIGHT`)
и право на изображение (`PRIVACY`). **Возврат в форму после создания
команды** — `next` в `team_create` с проверкой
`url_has_allowed_host_and_scheme`, форма фото принимает `?team=<pk>`.
**Выбранный файл можно снять** кнопкой «Убрать фото» под превью: у поля
файла нет нативной очистки, а без неё человек, выбравший не тот снимок,
ищет нужный заново. Кнопка живёт в `photo-form.js` вместе с превью
и обнуляет поле, `objectURL` и подсказку года из EXIF. Ошибка резолва
названия ведёт к ссылке «Создать команду «…»» (`?name=` в `team_create`
подставляет название в форму): текст ошибки экранируется, ссылку
в него не вставить, поэтому `PhotoUploadForm.unresolved` отдаёт шаблону
ненайденные названия.

**Админка.** Модерация (опубликовать / скрыть / отклонить / мягко удалить / восстановить) —
действия списка; каждое решение пишется в `ModerationAction`. Слияние дубликатов — действие
«Слить дубликаты в один объект», открывает отдельную страницу выбора цели
(`admin/core/merge_form.html`), потому что цель не должна совпадать с источниками.
`ModerationAction` доступен только для чтения: журнал заполняется действиями, а не вручную.

### Правила для кода

- Модели, у которых есть `deleted_at`, обязаны иметь `objects` (всё, включая удалённое) и
  `public` (без удалённого). Публичные выборки — только через `public`.
- Поля с `auto_now_add` нельзя заполнять из JSON-фикстур — начальные данные задаются
  data-миграцией.
- Новые поля FK на `User` в `catalog`/`photos` не создают цикла: `accounts` мигрирует первым,
  а обратные связи на `catalog` идут отдельной миграцией (`accounts/0002_...`).
- Демо-данные создаются командой `seed_demo` (`make seed-demo`) и помечаются
  `attributes={"demo": true}`; удаляются `make seed-demo-flush`. Это инструмент разработки:
  на боевую базу их не переносим, в чек-лист деплоя входит «демо-данные не переносить».
- Публичные страницы отдают только опубликованное и не удалённое:
  `Model.public.published()`. Черновики в публичную выдачу
  не попадают ни на одной странице.
- Новая публичная страница берёт выборку через `apps/core/shortcuts.py`, а не собирает
  цепочку `public.published()` вручную: правило отсева должно быть в одном месте.
- **Чистые функции обработки фото живут в `apps/photos/processing.py`** и не импортируют
  модели, настройки хранилища и Celery: PIL in → PIL out. Пайплайн и запись полей —
  в `apps/photos/services.py`. Второй реализации пайплайна быть не должно: команда
  бэкфилла и воркер вызывают тот же `process_photo()`.
- **Порядок операций фиксирован:** `exif_transpose` → поворот пользователя → кроп →
  подготовка `display`. Координаты кропа приходят в системе «как видит пользователь»
  (после EXIF-ориентации); применённые к «сырым» пикселям, они вырежут не тот участок.
- **`display` — единственный источник превью.** `thumbnail` и `preview` — `ImageSpecField`
  с `source="display"`. Откат на `original` запрещён и в превью, и в `og:image`,
  и в JSON-LD: оригинал хранит EXIF и GPS. Фото без `display` показывает заглушку.
- **`Photo.rights_confirmed` не влияет на видимость.** Права проверяет автор, а не сервер
  (решение 2.1); поле осталось историческим флагом для админки. Фото видно по статусу
  `published` и отсутствию `deleted_at`.
- **EXIF хранится по белому списку** (`apps/photos/exif.py`), GPS IFD не читается вовсе.
  `Artist` и `Copyright` остаются подсказкой модератору. Год из `DateTimeOriginal` —
  только значение для формы, не запись в базу.
- **Кроп — это `crop_data`, а не новый файл.** Мусор в данных (не словарь, чужая версия,
  координаты вне границ, кроп меньше 100 px) обрабатывается как «без кропа»
  с предупреждением в лог: сервис не падает на вводе из браузера.
- **Ошибка обработки не выходит наружу:** `processing_status=failed` и короткий текст
  в `processing_error`, стек — в лог. Иначе один битый файл уронил бы весь бэкфилл.
- **Статус нового фото решает `initial_status_for(user)`**
  (`apps/photos/services.py`), и только она: правило понадобится менять для
  доверенных авторов (P3-10), и разойдись оно по форме и представлению — один
  путь загрузки публиковал бы сразу, а другой нет. Сейчас отдаёт `draft`.
- **Лимиты загрузки — константы в `apps/photos/processing.py`**
  (`MAX_UPLOAD_BYTES`, `MIN_SIDE_PX`, `MAX_SIDE_PX`, `ALLOWED_UPLOAD_FORMATS`):
  их проверяют форма и (позже) воркер, вторых чисел в проекте быть не должно.
  Правила, которым нужна модель (`DAILY_UPLOAD_LIMIT`, `uploads_today()`,
  `upload_limit_reached()`, `resolve_by_name()`), живут в сервисе.
- **Суточная квота — скользящие 24 часа и менеджер `objects`.** «В сутки» для человека
  значит «за последние сутки», а удалённое модератором фото не возвращает квоту: иначе
  лимит обходился бы удалением.
- **Состояние плашки кабинета считает модель** (`Photo.upload_state`,
  `upload_state_label`), а не шаблон: удаление — признак `deleted_at`, а не статус
  публикации, и порядок проверок (удалено → ошибка → обработка → опубликовано → скрыто →
  отклонено → на проверке) должен жить в одном месте. Шаблон печатает готовую подпись.
- **Название команды или события резолвит сервис** (`resolve_by_name()`), а не форма:
  одно правило для формы загрузки и будущей правки фото. Неоднозначное название
  не угадывается — человек получает ошибку и уточняет город.
- Фильтры списков живут в `apps/catalog/filters.py`, а не в шаблонах и не в представлениях:
  справочники вариантов, разбор параметров и адрес `canonical` — в одном месте, шаблон
  получает готовую панель. Невалидное значение параметра считается неприменённым фильтром.
- Ссылка на неопубликованную сущность не создаётся нигде: перед ссылкой проверяется
  `is_published`, иначе название выводится текстом. Черновик не должен утекать по прямой
  ссылке и попадать в индекс поисковиков.
- Люди в публичном контексте выводятся через `Person.public_name`, а состав команды
  фильтруется по `Person.public.published()`: человек-черновик не попадает в публичную
  выдачу, даже если записан в команду. Фильтр публичности применяется до фильтра по годам
  и до среза превью.
- Состав команды фильтруется по годам (`?year=1994`), а не показывается отдельной страницей:
  архив наполняется по чужим альбомам, и «состав года» читался бы как полный список.
  Формулировки не обещают полноты — «Люди в команде, 1994 год» и подпись «В архиве указаны
  не все, кто играл». Отдельная страница с группировкой по годам отложена (идея I-8).
- Логика периодов состава живёт в `apps/catalog/roster.py` и не делает запросов к базе:
  её проверяют unit-тесты. Незакрытый период (`year_to` пуст) заканчивается последним годом,
  известным по команде, — без этой границы человек «размазался» бы на все годы до сегодняшнего.
  Один `year_to` без `year_from` даёт единственный год.
- Подпись годов членства — свойство `TeamMembership.years_label`, а не разметка шаблона:
  тем же свойством пользуются страница человека и состав команды, и форматов не должно быть два.
- Правило приватности имени живёт в представлении, а не в шаблоне: варианты имён
  (`PersonName`) кладутся в контекст только при `Person.is_full_name_public`. Смена
  шаблона не должна раскрывать скрытую фамилию.
- `display_name` в публичную разметку не попадает никогда — только `public_name`:
  `display_name` заполняется в `Person.save()` полным именем с фамилией.
- Главное фото страницы человека выбирается правилом «аватар, если видим, иначе первое
  видимое фото»: проверка видимости — через `Photo.is_public`, не сравнением статусов
  в шаблоне.
- Счётчик фото в карточках команд и событий берётся из общей аннотации `photos_count()`
  (`apps/core/shortcuts.py`): своя копия аннотации в представлении дала бы другой ответ
  на той же странице.
- Slug'и кириллические, поэтому для маршрутов с `SlugModel` используется конвертер `uslug`
  (`apps/core/converters.py`), а не стандартный `<slug:...>`. `QueryDict` для ссылок галереи
  собирается из словаря, а не из строки: кириллица и `&` в slug'е сломали бы адрес.
- Счётчик просмотров фото растёт через `QuerySet.update()`, а не `save()`: `save()` писал бы
  запись в историю при каждом открытии страницы и засорил бы журнал.
- SEO-метатеги (`title`, `description`, `canonical`, `og:*`) собираются во вьюхах через
  `page_meta()` (`apps/core/seo.py`), а не в шаблонах: картинка карточки зависит от данных
  страницы, а правило приватности имени должно жить в одном месте. Партиал
  `templates/partials/meta.html` только выводит готовый словарь `meta`. `noindex` — дефолт
  процессора `seo_meta` для страниц, которые не задали свой `meta`: новая страница не попадёт
  в поисковики, пока автор не опишет её явно. Контекст представления перекрывает процессор,
  поэтому `meta` из `page_meta()` должен быть полным, а не частичным.
- Микроразметка Schema.org собирается в `apps/core/schema.py`, а не в шаблонах, — по тому же
  правилу, что метатеги: правило приватности имени и выбор картинки живут в одном месте.
  Тег `{% jsonld %}` (`apps/core/templatetags/jsonld.py`) сериализует словарь и экранирует
  `<`, `>`, `&`, U+2028 и U+2029: без этого название вида `</script>` разорвало бы страницу.
  Партиал `templates/partials/jsonld.html` выводит блоки из контекста `jsonld_blocks`; страница
  без разметки переменную не задаёт, и партиал пуст. `Person` в разметку попадает при `full`
  и `first_name_only`, при `hidden` блока нет: фамилия не должна попадать в машинное описание
  ни при каком варианте.
- Карта сайта (`apps/core/sitemaps.py`) отдаёт только публичное и берёт выборки из
  `apps/core/shortcuts.py`, а не собирает цепочку `public.published()` заново: список адресов
  в карте и список на странице обязаны совпадать. Домен карты и `robots.txt` берётся
  из `django.contrib.sites`, а не из `request.get_host()`: за сайтом стоит nginx, и адрес
  зависел бы от настроек прокси. Имена маршрутов sitemap — штатные Django, `views.index`
  строит ссылки на секции по ним; переименование дало бы битые ссылки в индексе. `i18n = False`
  обязателен: языковых префиксов в адресах нет, и `i18n = True` продублировал бы каждый адрес
  по числу языков в `LANGUAGES`.
- `/robots.txt` и `/sitemap.xml` обслуживает Django, а не nginx: адрес карты и список закрытых
  разделов должны лежать рядом с кодом и попадать в репозиторий. `robots.txt` — вежливая
  просьба, а не защита; черновики защищает `get_visible_or_404`, который отдаёт посторонним 404.
- Строки интерфейса — только через `gettext`. После добавления строк выполняется `make i18n`;
  `makemessages` помечает новые строки `fuzzy`, если нашёл похожую старую, а `msgfmt`
  пропускает fuzzy — после извлечения проверяйте fuzzy-блоки и снимайте флаги. Для русского
  каталога fuzzy-записи и пустые `msgstr` выравниваются по `msgid`; для английского каталога
  переводы новых строк заполняются вручную (автоперевод не используем).
- Комментарии в шаблонах — только `{% comment %}...{% endcomment %}`. `{# ... #}` в Django
  работает в пределах **одной строки**: закрывающая `#}` на следующей строке не распознаётся,
  и текст комментария попадает в HTML.
- `django-imagekit` кэширует факт «превью существует» в Django-кэше. В тестах `MEDIA_ROOT`
  у каждого теста свой, поэтому в `tests/conftest.py` есть фикстура `cleared_cache` —
  без неё тесты превью падают на чтении чужого файла.
- Поисковый индекс — производное поле, и пересчитывает его код: сигналы
  (`apps/search/signals.py`) при сохранении объекта и команда `make search-reindex`
  для полного прохода. Пишем через `queryset.update()`, а не `save()`: `save()` писал бы
  запись в `django-simple-history` и сдвигал `updated_at` (а он попадает в `lastmod`
  карты сайта) при каждом пересчёте.
- Текст индекса собирает одна функция `build_search_text()` (`apps/search/indexing.py`):
  правило приватности имени должно жить в одном месте. При `first_name_only` фамилия
  и варианты имён в текст не попадают, при `hidden` текст пустой, `display_name`
  не индексируется никогда. Триграммный индекс хранит «сырые» поля, поэтому скрытие
  там обеспечивает фильтр запроса: публичная выдача поиска обязана идти через
  `public.published()` и учитывать `name_visibility`.
- Черновики индексируются как обычно: публичность отсекает
  выборка, а не индекс. Пересчёт индекса при каждой смене статуса — лишние запросы.
- Ввод пользователя превращает `build_search_query()`: слова чистятся регулярным выражением
  (символы `&`, `|`, `!`, `:` — часть языка `tsquery`), к каждому слову добавляется префикс
  `:*`. Без префикса частичное слово не находится: русский словарь приводит «Громовцы»
  к «громовц», а запрос «гром» — к «гром».
- Поля поиска живут в моделях каталога и фото, а не в `apps/search`: `makemigrations` пишет
  `AddField` только в приложение владельца модели. Приложение `search` владеет расширением
  `pg_trgm`, сборкой текста, сигналами и командой переиндексации.
- Поиск работает только на PostgreSQL (`tsvector`, `pg_trgm`); тесты поиска помечены
  `skipif` по вендору базы. `CREATE EXTENSION` требует прав суперпользователя — на боевом
  сервере это отдельный пункт чек-листа деплоя.
- Страница поиска живёт в `apps/search` (`search:index`), а не в `core`: `core` в проекте —
  нижний слой, и ссылка из него на модели каталога дала бы обратную зависимость.
  Выдачу собирает `apps/search/services.py` (`search_page()`, `suggestions()`), представление
  только разбирает ввод: `SearchGroup` знает имя шаблона карточки, поэтому партиал группы
  не ветвится по типу объекта, а `Suggestion` несёт готовые подпись, адрес и тип — шаблон
  не знает, из какой модели пришла подсказка.
- Поиск — публичная выдача: черновик не показывается никому, включая автора и модератора.
  `get_visible_or_404` здесь не применяется: автор увидел бы свой черновик по случайному
  запросу и не понял бы, почему у остальных его нет.
- Подсказки «возможно, вы искали» сравнивают только безопасные поля: у команды и события —
  название и город, у человека — `first_name` всегда, `last_name` и варианты имён
  (`PersonName.value`) только при `name_visibility=full` (условие `Case/When`, а не фильтр:
  человек с `first_name_only` должен остаться в подсказках по имени), а люди со скрытым именем
  исключены вовсе. Триграммный индекс хранит «сырую» фамилию, поэтому правило живёт
  в `services.py` и проверяется тестами.
- Подсказки считаются только при полностью пустой выдаче: триграммные запросы дороже
  полнотекстовых, а при найденных результатах бесполезны. Непустой ввод, в котором не осталось
  слов (`!!!`), даёт «ничего не найдено» без блока подсказок — сравнивать триграммами мусор
  нечего. Ввод обрезается до `MAX_QUERY_LENGTH` (100) до сборки `tsquery`.
- Страница результатов закрыта от индексации (`noindex, follow`): адресов с произвольным
  запросом в поиске быть не должно, но найденные карточки ведут на настоящие страницы архива.
  Карточки поиска переиспользуются как есть; для людей добавлен
  `templates/catalog/partials/person_card.html` со стилем общей `.entity-card`,
  и `display_name` в него не попадает никогда — только `public_name`.
- Группа выдачи показывает до `GROUP_LIMIT` (20) карточек и общий счётчик; при обрезке
  под сеткой стоит подпись «Показаны первые N из M». Пагинации на странице результатов нет:
  она обзорная, а не список.
