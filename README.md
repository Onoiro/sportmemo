# SportMemo

Публичный архив спортивных фотографий. На старте — бейсбол в России: детские, юношеские и
ветеранские команды, личные бумажные архивы игроков, тренеров и болельщиков.

Пользователи оцифровывают свои архивы (бумажные фото, сканы, газетные вырезки) и публикуют их
в общий архив с атрибуцией: кто на фото, команда, событие, год, источник.

- Домен: [sportmemo.ru](https://sportmemo.ru)
- Репозиторий: [github.com/Onoiro/sportmemo](https://github.com/Onoiro/sportmemo)

## Модель данных

Ключевые решения (подробности — в [плане этапа 1](.koda/plans/foundation-and-data-model.md)):

- **Архитектура мультиспортная, продукт одномспортный.** В схеме есть `Sport`, в UI выбора
  вида спорта нет. Специфика вида спорта — в `attributes` (JSONB), а не в колонках.
- **`Person` ≠ `User`.** Человек на фото — публичная сущность без аккаунта. Пользователь —
  приватный аккаунт, опционально связанный с `Person` («это я»).
- **Оригинал фото не перезаписывается.** Обработанная версия — производная в отдельном поле.
- **Дубликаты сливаются, а не удаляются.** `merged_into` + `merge_into(target)`, операция
  идемпотентна, связи переносятся.
- **Slug уникален в пределах вида спорта** для `Team`/`Event`; у `Person` — глобально, с
  числовым суффиксом при коллизии.
- **Фамилии несовершеннолетних не публикуются** — управляется `Person.name_visibility`,
  публичный контекст использует `Person.public_name`.
- **Soft-delete:** объект с `deleted_at` исчезает из публичных выборок (`Model.public`),
  но сохраняет связи и историю.
- **Всё значимое логируется:** `django-simple-history` на содержательных моделях плюс журнал
  решений модератора (`ModerationAction`).

## Запуск

### Локально (без Docker)

Нужны Python 3.12+ и PostgreSQL 17 (или поднимите только БД через Docker).

```bash
uv sync                       # установить зависимости
cp .env.example .env          # настроить окружение
make migrate                  # применить миграции (создаст вид спорта «Бейсбол»)
make superuser                # создать администратора
make run                      # сервер разработки на http://localhost:8000
```

- Сайт: http://localhost:8000
- Админка: http://localhost:8000/admin/
- Проверка работоспособности: http://localhost:8000/healthz/ → `{"app": "ok", "db": "ok"}`

### Docker Compose

```bash
cp .env.example .env
make up                       # db, redis, minio, web, worker
make ps                       # статус сервисов
make logs                     # логи
```

Консоль MinIO: http://localhost:9001 (`minioadmin` / `minioadmin` в dev).

> **Внимание.** MinIO закрыл публичную раздачу образов (сентябрь 2026), поэтому в
> `docker-compose.yml` используется переупаковка `elestio/minio` с зафиксированным digest.
> Перед деплоем нужно выбрать целевое решение — см. риск R-1 в [бэклоге](.koda/backlog.md).

**Тема.** Светлая сепия по умолчанию и тёмный вариант. Переключатель — в навигации, выбор
хранится в `localStorage`, при первом визите берётся системная схема. Инлайн-скрипт в `<head>`
ставит тему до отрисовки, поэтому при загрузке нет мигания.

**Публичные выборки.** Наружу отдаётся только опубликованное и не удалённое:
`Model.public.published()`.

Общие точки входа в это правило — `apps/core/shortcuts.py`:

- `visible_photos()` — видимые фото (цепочка `public.published()`);
- `archive_stats()` — счётчики архива: команды, фото, годы. Список `/years/` считает годы
  тем же способом, иначе числа на главной и в списке разошлись бы;
- `paginate(request, queryset, per_page)` — единая пагинация; нечисловой или выходящий
  за границы номер страницы отдаёт первую/последнюю, а не ошибку;
- `get_visible_or_404(model, *, request=None, **lookup)` — объект из `public` или 404.
  Неопубликованный объект показывается только автору (`created_by` / `uploaded_by`)
  и модератору: остальным — 404, чтобы черновик не утекал по прямой ссылке. Удалённые
  и слитые объекты не видит никто. Хелпер принимает модель параметром и не импортирует
  модели приложений, поэтому циклов между `core` и `catalog`/`photos` не возникает.

Черновики, скрытые, отклонённые, удалённые и слитые объекты не попадают ни в один список.

**Права на фото не проверяются сервером.** Отдельных полей заявленных прав и выбора лицензии
нет: ответственность за контент несёт автор, это записано в Пользовательском соглашении
(«Упрощённый UGC», решение 2.1 этапа 3). Поле `Photo.rights_confirmed` осталось историческим
флагом для админки и на видимость не влияет: опубликованное фото показывается независимо
от него. Претензия правообладателя и жалоба «это я» идут через механизм жалоб
(`COPYRIGHT` и `PRIVACY`). Метод `SoftDeleteQuerySet.visible()` удалён: после этого решения
он не фильтровал ничего, а пустая обёртка соврала бы читателю.

**Галерея.** Сетка фото собрана из одного компонента
(`templates/photos/partials/grid.html` + `grid_items.html`) и используется на главной,
на странице года и в htmx-фрагменте. Кнопка «показать ещё» подгружает следующую порцию
в конец сетки без перезагрузки: фрагмент `photos:grid` отдаёт только карточки и контейнер
кнопки, а когда фотографии заканчиваются — пустой контейнер с `hx-swap-oob`, и кнопка
исчезает. Без JavaScript та же кнопка работает как обычная ссылка `?page=N`: на странице
года видна первая порция, вторая открывается обычной навигацией.

Размер порции (24) и порядок карточек общие для страницы года и фрагмента
(`PHOTO_PAGE_SIZE`, `PHOTO_ORDERING` в `apps/core/shortcuts.py`): разойдутся — подгрузка
начнёт пропускать или повторять фото. Страницы, где фильтр не лежит в `request.GET`
(страница года), передают его в галерею явно.

**Фильтры каталога.** Списки команд и событий отбирают по query-параметрам: ссылку можно
сохранить и переслать, JavaScript не нужен. Состояние живёт только в адресе, в `session`
ничего не пишется.

| Список | Параметры | Сортировка |
|---|---|---|
| `/teams/` | `city` — город, `decade` — десятилетие основания (начало: `1980`) | `sort=name` (по умолчанию), `sort=photos` |
| `/events/` | `year` — год, `type` — тип события, `city` — город | `sort=new` (по умолчанию), `sort=old` |

Логика живёт в `apps/catalog/filters.py`, а не в шаблонах и не в представлениях: справочники
вариантов, разбор параметров и адрес `canonical` собираются в одном месте. Шаблон получает
готовую панель (`FilterPanel` с полями `SelectField`) и только выводит её — ни одного
сравнения с `request.GET` в разметке.

- **Справочники считаются по всей публичной выборке**, а не по отфильтрованной: иначе после
  выбора десятилетия из списка городов исчезли бы города, в которых в этом десятилетии команд
  нет, и снять фильтр было бы нечем. Варианты берутся только из опубликованных объектов.
- **Невалидное значение считается неприменённым фильтром.** Опечатка в ссылке (`?year=abc`)
  не должна выглядеть как «ничего не найдено». То же правило, что у фильтра состава команды.
- **Города склеиваются по регистру и пробелам**: «Москва» и «москва» — один вариант,
  подписью служит самое частое написание. Отбор идёт через `city__iexact`, поэтому
  `?city=москва` находит «Москва», а в `canonical` попадает написание из базы.
- **Сортировка не считается фильтром**: «Сбросить фильтры» сохраняет выбранный порядок
  выдачи, а пустое состояние определяется только отбором.
- **`canonical` собирается по нормализованным параметрам** (`page_meta(..., canonical_query=)`):
  мусорные параметры и номер страницы в него не попадают, иначе одна выдача получила бы
  бесконечное число «разных» адресов. Страницы пагинации по-прежнему закрыты `noindex`.
- **Два пустых состояния**: «В архиве пока нет команд» (архив пуст) и «По выбранным условиям
  ничего не найдено» с кнопкой сброса (фильтры активны). Смешать их значит соврать
  пользователю о причине пустоты.
- `django-filter` не подключаем: объём — пять селектов и две сортировки, своя функция проще
  и не тянет зависимость.

**Страница фото.** `/photos/<pk>/` открывается анонимно, если фото опубликовано.
Черновик видит только автор (`uploaded_by`) и модератор — отсев делает
`get_visible_or_404`. Ссылки на команду и событие появляются,
только если те опубликованы: неопубликованные названия выводятся текстом. В блоке «Люди
на фото» имя человека — ссылка на его страницу, если человек опубликован; имя черновика
выводится текстом. Счётчик просмотров растёт при каждом открытии атомарным
`update(views_count=F("views_count") + 1)` — без `save()`, поэтому записи в истории
`django-simple-history` не создаются.

**Страницы команды и события.** Две «страницы-визитки», на которые ведут ссылки из списков,
галереи и мессенджеров.

- `/teams/<slug>/`: эмблема, название, город, год основания, вид спорта, описание,
  атрибуты, «Фотографии команды» (галерея с подгрузкой), «События команды» и состав
  с фильтром по годам.
- `/events/<slug>/`: тип события бейджем, название, подпись дат, место, вид спорта,
  описание, «Итоги» (атрибуты), «Команды-участники» с результатами и «Фотографии события».

**Состав команды по годам.** Архив наполняется по чужим альбомам и газетным вырезкам,
поэтому состав за конкретный год заведомо неполный: известны один-два человека из пятнадцати.
Отдельной страницы «состав года» поэтому нет — она читалась бы как полный список. Вместо неё
на странице команды работает фильтр `?year=1994`: форма GET, состояние живёт в URL, работает
без JavaScript.

- Режим «все годы» — превью до 12 человек (`TEAM_ROSTER_PREVIEW`) и общее число известных
  людей; выбранный год показывается целиком, иначе фильтр был бы бессмыслен.
- Список годов — только те, в которые известен хотя бы один человек: пустой год выглядел бы
  обещанием данных, которых нет.
- Незакрытый период (`year_from` есть, `year_to` пуст) заканчивается последним годом,
  известным по команде (максимум по её членствам и событиям). Иначе человек «размазался» бы
  на все годы до сегодняшнего.
- Один `year_to` без `year_from` даёт единственный год: утверждать, что человек играл раньше,
  нельзя.
- Люди без годов видны в режиме «все годы» с подписью «год не указан» и не добавляют годов
  в фильтр.
- Формулировки не обещают полноты: «Люди в команде, 1994 год» и подпись «В архиве указаны
  не все, кто играл». Отдельная страница с группировкой по годам — идея I-8 в бэклоге:
  вернуться, когда составов наберётся достаточно.
- Логика периодов живёт в `apps/catalog/roster.py` и проверяется unit-тестами без запросов
  к базе; подпись годов (`TeamMembership.years_label`) — в модели, общая со страницей
  человека.

**Страница человека.** `/people/<slug>/` — главное фото, публичное имя, годы жизни,
биография, атрибуты, «Команды и роли», «Фотографии» и «Также известен как». Список людей
(`/people/`) намеренно не создаём: попасть на страницу можно только с фотографии или
из состава команды.

- **Приватность имени.** Заголовок, `<title>`, крошки и блок вариантов имён строятся только
  из `public_name`: `display_name` (в нём лежит полная фамилия) в разметку не попадает.
  При `first_name_only` выводится только имя, при `hidden` — нейтральная подпись «Имя
  не указано». Страница `hidden`-человека при этом открывается: иначе фотографии и команды
  потеряли бы связь с человеком.
- **Варианты имён** (`PersonName`: прозвище, фамилия при рождении) показываются только
  при `name_visibility = full` и скрываются в представлении, а не в шаблоне: прозвище
  раскрыло бы скрытую фамилию.
- **Главное фото** — `Person.avatar`, если он видим (`Photo.is_public`); иначе самое свежее
  видимое фото с этим человеком. Фото нет — заглушка-иконка. Свойство
  `Person.is_full_name_public` отвечает на вопрос «можно ли раскрывать полное имя» рядом
  с `public_name`, чтобы правило не жило в разметке.
- **Команды и роли**: команда, роль, годы, амплуа, номер. Команда-черновик остаётся
  в списке, но ссылкой не становится. В составе команды имена людей — ссылки на их страницы.

**Даты события.** `Event.date_label` собирает подпись только из месяцев и годов, без чисел
дня: «Июль 1980», «Июнь — Июль 1988», «Июль 1988 — Август 1989», «1980» (если есть только
год) или «дата не указана». Название месяца берёт `django.utils.formats.date_format` из
активной локали, поэтому отдельных строк для месяцев нет, а английская версия показывает
«July 1980». Свойство живёт в модели: им пользуются карточки событий и фильтры каталога.

**Ссылки на неопубликованное.** Ссылка на команду или событие создаётся, только если объект
опубликован (`is_published`); иначе название выводится текстом. Правило действует во всех
местах: в списках, на странице фото, на странице события (команда-черновик среди участников),
в блоке «События года». Так черновик не утекает по прямой ссылке и не попадает в индекс
поисковиков.

**Плашка «не опубликовано».** Автор и модератор видят черновик, скрытое и отклонённое
с плашкой (`templates/partials/moderation_notice.html`) и пояснением «Видно только вам
и модератору». Остальным тот же адрес отдаёт 404 — пропускает `get_visible_or_404`.

**Атрибуты.** `Team.attributes` и `Event.attributes` — JSONB без фиксированной схемы. Служебный
ключ `demo` не показывается; известные ключи (`stage`, `score`, `result`, `innings`, `teams`)
переводятся через `gettext`, неизвестные выводятся как есть. Списки склеиваются через запятую.
Пары «подпись, значение» готовит `attribute_items()` в `apps/catalog/views.py`.

**Слаг в адресе.** Slug'и хранятся с `allow_unicode=True`, поэтому стандартный конвертер
`<slug:...>` не подходит: он пропускает только ASCII. Свой конвертер `uslug`
(`apps/core/converters.py`) регистрируется в `CoreConfig.ready()`. Без него `reverse()`
падал бы на кириллических slug'ах с `NoReverseMatch`.

## Метатеги и Open Graph

Ссылка на любую страницу архива разворачивается в мессенджере карточкой с картинкой,
заголовком и подписью. Пересылка ссылок в чатах — основной канал, по которому такой архив
расходится, и без карточек его почти не открывают.

**Метатеги собираются в Python, а не в шаблонах.** Функция `page_meta()`
(`apps/core/seo.py`) отдаёт полный словарь `meta`, партиал
`templates/partials/meta.html` только выводит значения. Причина в том, что картинка карточки
зависит от данных страницы (у фото `preview`, у команды `logo`, у человека главное фото),
а правило приватности имени должно жить в одном месте: логика, размазанная по шаблонам,
рано или поздно дала бы утечку фамилии на одной из страниц.

- **Картинка.** Фото → превью 1280 px, команда → эмблема, человек → главное фото, остальные
  страницы → заглушка `static/img/og-default.png` (1200×630, сепия). Адрес заглушки стабилен,
  без хэша содержимого: мессенджеры держат карточку в кэше и ходят за картинкой
  по сохранённому адресу.
- **`og:type`** — `article` для страницы фото, `website` для остальных.
- **`canonical`** — абсолютный адрес без параметра `page`; значимые фильтры (`?year=1994`)
  сохраняются. Страница `?page>1` получает `canonical` на первую страницу и `noindex, follow`:
  иначе каждая страница пагинации объявила бы себя главной.
- **`noindex`** — черновики и неопубликованное, `?page>1`, `/search/`, страницы аккаунта
  (вход, регистрация, пароль, профиль, формы команды), 404 и 500.
- **Приватность имени.** `og:title` и описание строятся только из `Person.public_name`.
  При `first_name_only` и `hidden` фамилия не попадает ни в `<title>`, ни в `og:*` —
  проверяется тестами. Фотография человека со скрытой фамилией в карточке показывается:
  она и так публичная.
- **Дефолт — закрыто.** Контекстный процессор `seo_meta` отдаёт `{"meta": {"noindex": True}}`
  для всего, что не задало свой `meta` явно. Новая страница без метатегов не попадёт
  в поисковики, пока автор не опишет её. Контекст представления перекрывает процессор
  (в `Context.dicts` он лежит выше вывода процессоров).

Страницы аккаунта allauth, 404 и 500 остаются на блоках `{% block title %}`: `head_title` —
блок шаблона, из Python его не видно, а `og:*` этим страницам не нужен. У 500 страницы
`noindex` стоит прямо в шаблоне: Django рендерит её без `request`, и процессор не работает.

## Карта сайта, `robots.txt` и микроразметка

Архив связан слабо: страницу человека видно только с фото или из состава команды, фото —
со страницы года. Без карты сайта половина архива просто не попадёт в индекс, поэтому
её отдаёт Django (`django.contrib.sitemaps`), а не nginx: список адресов должен собираться
из тех же выборок, что и страницы.

- **Карта сайта** — индекс `/sitemap.xml` и пять секций: `/sitemap-pages.xml` (главная,
  команды, события, годы — без `lastmod`), `/sitemap-teams.xml`, `/sitemap-events.xml`,
  `/sitemap-people.xml`, `/sitemap-photos.xml`. Секции берут выборки через
  `public.published()` и `visible_photos()` (`apps/core/shortcuts.py`), поэтому черновики,
  скрытое, отклонённое, удалённое и слитое в карту не попадают.
  `lastmod` — `updated_at` объекта. `i18n = False`: языковых префиксов в адресах нет,
  и `i18n = True` продублировал бы каждый адрес по числу языков.
- **Домен карты** — из `django.contrib.sites` (`sportmemo.ru`, data-миграция), схема —
  из запроса. Не `request.get_host()`: за сайтом стоит nginx, и адрес зависел бы от настроек
  прокси, а не от проекта. Имена маршрутов sitemap — штатные Django: `views.index` строит
  ссылки на секции по фиксированным именам.
- **`robots.txt`** отдаёт представление `robots_txt` (`apps/core/views.py`) с шаблоном
  `templates/robots.txt`, `content_type="text/plain"`. Закрыты `/admin/`, `/accounts/`,
  `/search/`, `/healthz/`, `/teams/new/`, `/teams/mine/`, `/events/new/`, `/events/mine/`.
  Это вежливая просьба, а не защита:
  черновики защищает `get_visible_or_404`, который отдаёт посторонним 404.
- **Микроразметка** (JSON-LD) собирается в Python (`apps/core/schema.py`) по тому же правилу,
  что метатеги: правило приватности имени и выбор картинки живут в одном месте. Тег
  `{% jsonld %}` (`apps/core/templatetags/jsonld.py`) сериализует словарь и экранирует `<`,
  `>`, `&`, U+2028 и U+2029 — название вида `</script>` не ломает страницу. Партиал
  `templates/partials/jsonld.html` подключён в `base.html`; страницы без разметки не задают
  `jsonld_blocks`, и партиал выводит пустоту.
- **Что размечено:** главная — `WebSite` с `SearchAction` (поисковая строка сайта в выдаче),
  команда — `SportsTeam`, событие — `SportsEvent`, человек — `Person`, фото — `ImageObject`.
  `BreadcrumbList` не делаем: крошки уже есть в HTML обычными ссылками, Google их читает.
- **Приватность.** `Person` попадает в разметку при `full` (полное имя) и `first_name_only`
  (только имя); при `hidden` блока нет вовсе. Фамилия в разметку не попадает ни при каком
  варианте — проверяется тестом. Годы жизни не выводим: в модели только год, а `birthDate`
  по стандарту — дата.

## Регистрация и вход

Вход — по email и паролю (`django-allauth`), подтверждение адреса обязательно: без него
пользователя уводит на страницу «Проверьте почту», а не в аккаунт. При регистрации
записываются три согласия (пользовательское соглашение, политика конфиденциальности,
обработка персональных данных) с датами и версией — это юридическая защита проекта,
поэтому галочки обязательные.

**Как посмотреть письма в dev.** Почта уходит в консоль `runserver` (console email backend):
после регистрации в терминале видно письмо с абсолютной ссылкой. В тестах те же письма
складываются в `mail.outbox`.

**Оформление страниц аккаунта.** Штатные шаблоны allauth не копируются: переопределены
layout (`templates/allauth/layouts/base.html`) и элементы (`templates/allauth/elements/*`),
поэтому и наши шаблоны, и штатные страницы пакета (например, список адресов email) получают
navbar, футер и тему сайта. Bootstrap-классы полям ставит миксин `BootstrapFormMixin`
(`apps/accounts/forms.py`) — шаблоны allauth рендерят виджеты как есть, из разметки класс
не добавить. Тексты писем лежат в `templates/account/email/`; строки интерфейса — только
через `gettext`, msgid наших шаблонов русские.

## Профиль

`/accounts/profile/` — своя страница, а не шаблон allauth, поэтому наследуется от `base.html`
и получает крошки. В профиле меняется только `display_name` («как к вам обращаться»);
email и пароль — на своих страницах allauth, рядом с ними стоят ссылки. Сохранение идёт
по схеме POST-redirect-GET: обновление страницы не повторяет отправку формы. Роль показывается
только модератору и администратору. В блоке «Мой профиль в архиве» ссылка на страницу человека
появляется лишь при существующей связи `User.person`, иначе выводится нейтральный текст.
Заявки «это я» нет: без модерации любой мог бы «присвоить» чужую страницу, сценарий отложен
в бэклог.

В шапке у вошедшего — выпадающее меню с «Мои команды», профилем, сменой пароля и выходом;
имя обрезается CSS, чтобы длинное значение не растягивало navbar.

## Создание команды

Первая «пишущая» возможность для зарегистрированных: завести команду. Форма — `/teams/new/`,
свои команды со статусами — `/teams/mine/`, правка — `/teams/<slug>/edit/`.

- Команда создаётся **черновиком** (`status=draft`) с автором в `created_by`. Публикует её
  модератор: до публикации команду видят только автор и модератор, остальным страница отдаёт
  404 (правило `get_visible_or_404`).
- Правит команду автор и модератор, остальным — 404, а не 403: не раскрываем существование
  чужого черновика.
- Правка **опубликованной** команды не сбрасывает статус: изменения автора не должны ждать
  модератора, но всё пишется в историю (`django-simple-history`). Вернуться к повторной
  модерации можно, если появится вандализм.
- **Вид спорта в форме не показывается** — продукт односпортный. Он берётся из
  `default_sport()` (`apps/core/shortcuts.py`): первый активный вид спорта по порядку
  сортировки. Активных нет — форма недоступна с понятным сообщением, а не 500-й ошибкой.
- **Дубликаты названий не блокируются.** «Соколы» есть в разных городах, и решение «дубликат
  или одноимённая команда» принимает человек. Форма ищет команды с тем же названием
  в том же виде спорта (включая чужие черновики — иначе за время модерации появятся три
  одинаковые) и требует чекбокс «Я проверил(а), это другая команда». Настоящие дубликаты
  сливает модератор — механизм слияния уже есть.
- **Slug уникален в пределах вида спорта.** Вторая команда с тем же названием получает
  числовой суффикс (`динамо`, `динамо-2`): иначе страница упала бы на `IntegrityError`.
  Правка названия существующий slug не меняет — URL не должен ломаться.
- **О клубе с несколькими командами.** Если у клуба несколько команд (высшая лига, любительская,
  детские разных возрастов), заводите их отдельными записями: «Русстар», «Русстар-2»,
  «Русстар (юноши 1992 г. р.)». Подсказка об этом есть в форме. Отдельная сущность «клуб»
  с полем `parent` отложена — идея I-9 в бэклоге: навигация в архиве идёт по годам и людям,
  а «все фото клуба» соберёт поиск.
- Модераторам уходит письмо о новой команде; в dev оно печатается в консоль. Ошибка SMTP
  не отменяет создание команды, а отсутствие модераторов — нормальное состояние на старте
  проекта (в лог пишется предупреждение).

## Создание события

Событие устроено как команда: форма `/events/new/`, свои события со статусами —
`/events/mine/`, правка — `/events/<slug>/edit/`. Без этой формы пользователь не мог завести
событие вообще: поле «Событие» в форме загрузки фото требует существующей записи, а создавать
её умела только админка. Теперь в форме фото рядом с полем стоит ссылка «Создать событие»,
и после создания человек возвращается туда же с подставленным названием (`?event=<pk>`).

- Событие создаётся **черновиком** и публикуется модератором: до публикации его видят
  только автор и модератор, остальным 404. Правит автор и модератор; правка опубликованного
  события статус не сбрасывает — всё пишется в историю.
- **Дубликат — то же название и тот же год.** «Кубок России» проводится каждый год,
  и это нормальные разные записи; одинаковые название и год — повод показать список
  найденного и попросить подтверждение.
- **Год** можно указать отдельно, а если оставить пустым — он подставится из даты начала
  (то же правило, что в `Event.save()`). Числа и месяцы в архиве известны редко, а год —
  почти всегда.
- **Slug уникален в пределах вида спорта** и получает числовой суффикс (`кубок-россии`,
  `кубок-россии-2`). До 0.19.0 slug генерировался без проверки: это работало только потому,
  что события заводила админка, где slug правили руками.
- Проверка права на правку общая с командой (`can_edit()`, `get_editable_or_404()` принимают
  модель): правила для двух сущностей не должны расходиться.
- Письмо модераторам уходит так же, как о команде, и так же не отменяет создание при ошибке
  SMTP.

## Комментарии и жалобы

Архив наполняется по чужим альбомам и газетным вырезкам, поэтому ошибки в данных
неизбежны: кто-то на фото назван неверно, у команды перепутан город, у события — год.
Две возможности закрывают это: комментарий с уточнением и жалоба на ошибку.

**Комментарии** — под фото, командой и событием (`/comments/add/`, только вошедшим).
Блок собирается одним партиалом (`templates/comments/partials/list.html`), контекст готовит
`comments_context()` (`apps/comments/services.py`): три страницы лежат в разных приложениях,
и собирать список в каждой по-своему — верный способ получить разные правила видимости.

- **Публикуется сразу.** Премодерация всех комментариев — редкость, её держат
  на чувствительных ресурсах; для архива спортивных фото правильнее реактивная модерация.
  Плохой комментарий модератор убирает в админке (скрыть / отклонить / мягко удалить).
- **Премодерация включается переключателем.** `CommentSettings` — singleton-настройка
  (одна строка, создаётся data-миграцией), страница «Настройки комментариев» в админке.
  Добавлять и удалять записи нельзя, список сразу ведёт на форму правки: две строки настроек
  означали бы, что неизвестно, какая действует. Настройка кешируется и сбрасывает кеш
  при сохранении — переключатель действует сразу.
- **Что кто видит.** Аноним и вошедший — опубликованное; автор — дополнительно свой
  комментарий в `draft` с плашкой «на проверке». Скрытое, отклонённое и удалённое не видит
  никто, включая автора: это решение модератора, а не черновик. Ответ скрытого корневого
  комментария не показывается — он висел бы без контекста.
- **Ответы одноуровневые.** Ответ на ответ прикрепляется к корневому комментарию: дерево
  требует рекурсии в шаблоне и в разметке читается хуже плоского списка.
- **Белый список целей** (`apps/comments/targets.py`): фото, команда, событие. Generic FK
  сам по себе цель не ограничивает — без списка через форму можно было бы создать
  комментарий к пользователю или к жалобе. Объект берётся через `get_visible_or_404`:
  к тому, чего пользователь не видит, комментарий не «прицепится».
- **Защита от дублей.** Тот же автор, та же цель и тот же текст в пределах 10 минут —
  второй комментарий не создаётся. Двойной клик и «отправил, обновил страницу» — частый
  случай, а не спам. Троттлинг по IP отложен (P2-17).
- **Работает без JavaScript.** Форма отправляется обычным POST с редиректом назад; с htmx
  блок комментариев перерисовывается целиком (`hx-swap="outerHTML"`), а `comments.js`
  добавляет только `aria-busy` и сообщение в `aria-live`.

**Жалоба на ошибку** — отдельная страница `/reports/add/`, доступная анонимно. Отдельная
страница, а не модальное окно: работает без JavaScript, и ссылку можно переслать. Ссылка
«Сообщить об ошибке» стоит на тех же трёх страницах, что и комментарии.

- Форма: причина (из `ReportReason`), необязательное пояснение и поле-приманка `website`
  (honeypot). Заполнена приманка — показываем благодарность и ничего не записываем: отвечать
  боту отказом значит подсказывать, что его раскусили.
- Повторная жалоба того же вошедшего пользователя на тот же объект с той же причиной
  в пределах суток не создаётся. Анонимов не проверяем — их не за что зацепить.
- Письмо модераторам уходит только о жалобах. О новых комментариях не пишем: при выключенной
  премодерации это поток писем. Ошибка SMTP логируется и не отменяет жалобу — она уже записана.
- Страница закрыта от индексации (`noindex`), `/reports/add/` добавлен в `robots.txt`.

**Общая часть писем модераторам** живёт в `apps/core/emails.py`: адресаты нужны и каталогу,
и модерации. `apps/catalog/emails.py` и `apps/moderation/emails.py` — тонкие обёртки
с текстом письма; `notify_moderators()` никогда не поднимает исключение.

**Кнопок модерации на публичных страницах нет.** Админка — одно место для решений, и каждое
попадает в `ModerationAction` и в историю. Правка текста комментария модератором тоже
происходит там же и записывается в `django-simple-history`.

## Демо-данные

Наполнить базу вымышленным архивом можно management-командой `seed_demo`: команды, люди,
события, источники и фотографии с сгенерированными изображениями.

```bash
make seed-demo               # создать демо-архив (по умолчанию 40 фото)
make seed-demo-flush         # удалить демо-объекты вместе с их файлами
uv run python manage.py seed_demo --photos 10   # меньше фото — быстрее
```

Что создаётся: 5 команд, 30 человек, 8 событий, 6 источников и 40 фото. Данные намеренно
«неудобные» — так UI проверяется сразу на крайних случаях:

- команда «Степные орлы» и часть людей и событий — в статусе `draft`;
- у людей встречаются все три значения `name_visibility`, включая несовершеннолетних
  (`first_name_only`) и скрытые имена (`hidden`);
- у трёх фото `rights_confirmed=False` — они остаются черновиками: правило «без прав
  не публикуется» отменено, а показывать в демо-архиве опубликованное фото без прав
  бессмысленно;
- у двух событий нет дат (только год), у одного нет ни года, ни даты;
- часть фото без команды и события, у событий заполнены `attributes` (счёт, этап).

Изображения генерируются Pillow: сепийный градиент с зернистостью, рамка, название и год
текстом. Размеры разные (ландшафт, портрет, квадрат). Генерация воспроизводима — повторный
запуск даёт те же файлы.

**Идемпотентность.** Повторный запуск обновляет демо-объекты, а не создаёт дубли: ключи —
`(sport, slug)` у команд и событий, `slug` у людей, `(kind, title)` у источников,
`(title, uploaded_by)` у фото.

**Демо-пользователи.** `demo@example.com` (автор контента) и `demo-moderator@example.com`
(публикует объекты), пароль `demo-password-12345`. Домен `example.com` заведомо ненастоящий —
письма наружу не уйдут.

**Только для разработки.** Команда отказывается работать при `DEBUG=False` без явного
`--force`, потому что `--flush` физически удаляет данные. Демо-объекты помечены
`attributes={"demo": true}`, поэтому их легко найти и не переносить на боевую базу.

**Известное поведение.** `--flush` удаляет оригиналы фото, но кэш превью `django-imagekit`
(`media/CACHE/`) остаётся — он безвреден, а чистить весь `CACHE/` нельзя: там превью обычных
фото.

## Поиск

Поиск по архиву двухкомпонентный, и оба компонента живут в базе, а не в приложении:

1. **Полнотекстовый поиск** (`tsvector`, конфигурация `russian`) — «нашёл по части слова»:
   запрос «гром» находит и «Громов», и «Громовцы».
2. **Триграммы** (`pg_trgm`) — устойчивость к опечаткам и «возможно, вы искали»:
   `TrigramSimilarity` выдаёт похожие названия, когда точных совпадений нет. Этим же
   механизмом на этапе 3 будет пользоваться слияние дубликатов.

**Расширение и поля.** Миграция `apps/search/0001_pg_trgm.py` включает `CREATE EXTENSION
pg_trgm`, миграции `catalog/0003` и `photos/0002` добавляют поле `search_vector`
(`SearchVectorField`) и GIN-индексы: по `search_vector` — для полнотекстового поиска,
`gin_trgm_ops` — по «сырым» текстовым полям (`Team.name`, `Team.city`, `Event.name`,
`Event.city`, `Person.first_name`, `Person.last_name`, `PersonName.value`, `Photo.title`).

> **Требуется PostgreSQL.** `tsvector` и `pg_trgm` есть только там. Тесты поиска помечены
> `skipif` по вендору базы: на SQLite они пропускаются с понятной причиной.
> `CREATE EXTENSION` требует прав суперпользователя — на боевом сервере это отдельный
> пункт чек-листа деплоя (этап 4).

**Что попадает в индекс.** Текст собирает `build_search_text()` (`apps/search/indexing.py`):

| Модель | Состав текста |
|---|---|
| `Team` | название, город, описание, значения `attributes` (кроме служебного `demo`) |
| `Event` | название, город, страна, тип, описание, значения `attributes` |
| `Person` | `public_name`, имя, отчество, биография; при полной видимости имени — ещё фамилия и варианты имён (`PersonName`) |
| `Photo` | заголовок и подпись |

**Приватность индекса.** При `name_visibility = first_name_only` фамилия и варианты имён
в текст не попадают, при `hidden` текст пустой: индексировать подпись «Имя не указано»
значит находить всех скрытых людей по слову «Имя». `display_name` (в нём лежит полная
фамилия) в индекс не входит никогда — правило живёт в одной функции и проверяется тестами.
Триграммный индекс хранит «сырую» фамилию, и скрытие там обеспечивает фильтр запроса:
выдача идёт через `public.published()` и учитывает `name_visibility`.

**Индекс не влияет на публичность.** Черновики индексируются как обычно: отсев делает
выборка (`public.published()`), а не индекс. Иначе пересчёт индекса пришлось бы делать
при каждом изменении статуса.

**Пересчёт.** Индекс — производное поле, и обновляет его код:

- сигналы (`apps/search/signals.py`) пересчитывают объект при сохранении; сохранение
  или удаление варианта имени (`PersonName`) пересчитывает индекс человека;
- `make search-reindex` (`python manage.py search_reindex [--model team|person|event|photo]`)
  пересчитывает всё — нужен после появления поля, после массовых правок мимо сигналов
  и после изменения правил сборки текста. Команда идемпотентна.

Запись идёт через `queryset.update()`, а не `save()`: `save()` писал бы запись
в `django-simple-history` и сдвигал `updated_at` при каждом пересчёте, а `updated_at`
попадает в `lastmod` карты сайта. «Объект изменился» и «индекс пересчитан» — разные события.

**Запрос.** Ввод пользователя превращает `build_search_query()`: слова чистятся регулярным
выражением (символы `&`, `|`, `!`, `:` — часть языка `tsquery`, и сырой ввод с ними уронил бы
страницу), а к каждому слову добавляется префикс `:*`. Без префикса частичное слово
не находится: русский словарь приводит «Громовцы» к «громовц», а запрос «гром» — к «гром».
Ввод обрезается до 100 символов (`MAX_QUERY_LENGTH`): длинный запрос иначе породил бы
гигантский `tsquery`.

### Страница результатов

`/search/?q=...` (`search:index`, код в `apps/search/views.py` и `apps/search/services.py`)
показывает выдачу четырьмя группами в фиксированном порядке: **Команды**, **События**,
**Люди**, **Фотографии**. В каждой группе — до 20 карточек (`GROUP_LIMIT`) и общий счётчик;
если нашлось больше, под сеткой стоит подпись «Показаны первые 20 из M». Пагинации нет:
страница результатов — обзорная, а не список.

Карточки переиспользуются как есть: команды и события — из списков каталога, фото —
из галереи. Для людей добавлен `templates/catalog/partials/person_card.html` со стилем
общей `.entity-card`; `display_name` в него не попадает никогда — только `public_name`.
Шаблон карточки лежит в самой группе (`SearchGroup.template`), поэтому партиал группы
не ветвится по типу объекта.

**Состояния страницы.** Пустой запрос поиск не выполняет: страница показывает форму
и подсказку, что можно искать. Непустой ввод, в котором не осталось слов (`!!!`), даёт
«ничего не найдено» **без** блока подсказок — сравнивать триграммами мусор нечего.

**«Возможно, вы искали».** До 5 подсказок (`SUGGESTION_LIMIT`) и только при полностью
пустой выдаче: триграммные запросы дороже полнотекстовых, а при результатах бесполезны.
Порог похожести — 0.3 (`SIMILARITY_THRESHOLD`), регистр приводится к нижнему с двух сторон
(`pg_trgm` регистрозависима). Кандидаты дедуплицируются по объекту: у человека подсказка
может прийти и по имени, и по варианту имени — остаётся наиболее похожий вариант.

**Приватность подсказок.** Сравниваются только безопасные поля: у команды и события —
название и город, у человека — `first_name` всегда, `last_name` и варианты имён
(`PersonName.value`) только при `name_visibility = full` (условие `Case/When`, а не фильтр:
человек с `first_name_only` должен остаться в подсказках по имени). Люди со скрытым именем
исключены вовсе. Триграммный индекс хранит «сырую» фамилию, поэтому правило живёт
в `services.py` и проверяется тестами.

**Публичность выдачи.** Поиск — публичная выдача: черновик не показывается никому, включая
автора и модератора. `get_visible_or_404` здесь не применяется: автор увидел бы свой
черновик по случайному запросу и не понял бы, почему у остальных его нет. Люди берутся
из `Person.public.published()` без `hidden`, фото — из `visible_photos()`.

**`noindex`.** Страница результатов закрыта от индексации (`noindex, follow`): адресов
с произвольным запросом в поиске быть не должно. Ссылки при этом обходятся — найденные
карточки ведут на настоящие страницы архива. `/search/` уже закрыт в `robots.txt`.

## Обработка фото

Подэтапы 3.1 (фундамент обработки) и 3.3 (Celery-пайплайн): файл принимается
и превращается в нормализованную версию для показа. Публичные страницы берут превью
из `display`, а не из оригинала; пайплайн идёт фоновой задачей и не задерживает запрос.

**Порядок операций фиксирован** (`apps/photos/services.py`):

```
оригинал (storage)
   │ extract_exif()                 # до транспонирования
   │ exif_transpose()               # Orientation из EXIF
   │ thumbnail до 2500 px           # рабочая копия против OOM
   │ apply_rotation(0/90/180/270)
   │ apply_crop(crop_data)
   │ make_display() → JPEG ≤1280, без EXIF
   ▼
display в storage, width/height, phash, exif, processing_status=processed
```

Нарушение порядка даёт сдвиг кадра на телефонах: координаты кропа приходят в системе
«как видит пользователь», то есть после EXIF-ориентации, и применённые к «сырым» пикселям
они вырежут не тот участок.

**Три слоя.** Разбор EXIF — `apps/photos/exif.py`, чистые функции (PIL in → PIL out) —
`apps/photos/processing.py`, пайплайн и работа с моделью — `apps/photos/services.py`.
`processing.py` не импортирует модели и настройки хранилища: это даёт быстрые unit-тесты
без базы и одну реализацию для команды, воркера и формы.

**`display` — единственный источник превью.** `thumbnail` (400 px) и `preview` (1280 px) —
это `ImageSpecField(source="display")`. Пользователь кроит и поворачивает кадр, и в галерее
он должен видеть результат, а не исходный файл. Фото без `display` показывает заглушку,
а не падает: `{% if photo.thumbnail %}` в карточке. `og:image` и JSON-LD тоже строятся
только от `preview` — откат на оригинал отправил бы в мессенджер файл с EXIF и GPS.

**Кроп — инструкция, а не новый оригинал.** `Photo.crop_data` — `JSONField`:
`{"version": 1, "x", "y", "width", "height", "rotate"}`. Пустой словарь — «без кропа»,
это нормальный путь, а не ошибка. Мусор в данных (не словарь, чужая версия, отсутствующие
координаты, кроп меньше 100 px) обрабатывается как «без кропа» с предупреждением в лог:
сервис обязан не падать на вводе из браузера. Координаты клампятся по границам изображения.

**EXIF по белому списку.** Хранятся только `Make`, `Model`, `Software`, `Artist`,
`Copyright`, `ImageDescription`, `XResolution`, `YResolution`, `ResolutionUnit`,
`Orientation` и параметры съёмки (`DateTimeOriginal`, `DateTimeDigitized`, `ExposureTime`,
`FNumber`, `ISOSpeedRatings`, `FocalLength`). **GPS IFD не читается вовсе** — домашний
адрес ветерана в JSONB был бы реальной утечкой. `Artist` и `Copyright` остаются: это
бесплатная подсказка модератору, а не проверка прав. Год берётся только из
`DateTimeOriginal` и только в диапазоне 1850 — текущий год (`taken_year()`); значение
идёт в поле формы, а не в базу: у скана бумажного снимка EXIF принадлежит сканеру.

**Лимиты** (в `apps/photos/processing.py`, кроме Django-специфичных):

| Параметр | Значение | Почему |
|---|---|---|
| `MAX_UPLOAD_BYTES` | 25 МБ | Скан A4 600 dpi в JPEG q90 — 12–18 МБ |
| `Image.MAX_IMAGE_PIXELS` | 60 Мпикс | 48 МП телефон + запас; скан A4 600 dpi — 35 Мпикс |
| `MIN_SIDE_PX` | 300 px | Меньше — не архивный снимок |
| `MAX_SIDE_PX` | 10 000 px | Защита от панорам 20000×100 |
| `WORK_COPY_MAX_SIDE` | 2500 px | Рабочая копия: 48 Мпикс в RGB — ~144 МБ на декодирование |
| `DISPLAY_MAX_SIDE` | 1280 px | Размер версии для показа |
| `DATA_UPLOAD_MAX_NUMBER_FILES` | 12 | Задел под пакетную загрузку (10 + запас) |
| `CELERY_WORKER_CONCURRENCY` | 2 | Воркер по числу ядер падал бы по OOM на VPS с 4 ГБ |

**Имена файлов — UUID.** `photos/original/2026/10/<uuid>.jpg`, так же для `display`
и `processed`. Исходное имя не используется: оно бывает кириллическим, повторяется у разных
людей и раскрывает содержимое альбома. Имя автора хранится отдельно —
`Photo.original_filename` (для поиска в админке; при бэкфилле не восстанавливается).

**Перцептивный хеш.** DCT-II на `numpy` (без `scipy` и `imagehash`): 256 бит в hex,
64 символа (`PHASH_HEX_LENGTH`). Считается от `display`, потому что дубликаты ищутся
по тому, что видит человек. Битность поднята с 64 до 256 в 3.5: медиана расстояния
между разными фото выросла с 37 % до 41 %. `hamming_distance()` в Python; хеши разной
длины (старый 16-символьный и новый 64-символьный) считаются максимально далёкими —
XOR по ним дал бы случайное число бит. После смены алгоритма нужен
`uv run python manage.py photos_backfill --rehash`.

**Известное ограничение хеша:** монотонные цветовые заливки он не различает. У однотонной
картинки энергия DCT есть только в нулевой частоте, остальные биты получаются из шума
округления, и красная с синей заливкой дают 16 из 256 — меньше порога «вероятный
дубликат» (32). Порог не снижаем: пережатый JPEG того же снимка даёт до 40 из 256
и перестал бы находиться. Для архива ограничение не важно — заливок в нём нет,
а решение всё равно принимает человек.

**Ложные срабатывания на демо-базе — артефакт генератора.** Команда `seed_demo`
рисует все картинки по одному шаблону (сепийный градиент + рамка + подпись),
seed меняет только 500 точек зернистости. На демо-архиве 40 файлов
~4 % разных пар попадают в «вероятный дубликат» (расстояние ≤ 32 из 256);
пиксельная корреляция ближайших пар — 0,997–1,000. Это свойство генератора,
а не порога: между реальными разными снимками расстояние не меньше ~122.
Командные фотографии (одинаковая форма, одинаковый стадион) не дают ложных
срабатываний — разница в силуэтах, позах и количестве людей даёт расстояние
значительно больше 48 бит. «Похоже» — подсказка, а не приговор,
решение всегда принимает человек.

**Ошибка не выходит наружу.** Любое исключение (битый файл, отсутствующий оригинал,
превышение лимита пикселей) даёт `processing_status=failed` и короткий текст
в `processing_error`; стек уходит в лог через `logger.exception`. Иначе один битый файл
уронил бы проход бэкфилла.

**Бэкфилл.** `make photos-backfill` (или `manage.py photos_backfill`): по умолчанию берёт
фото с пустым `display` или пустым `phash`, флаги `--only-missing`, `--limit N`,
`--dry-run`. Флаг `--rehash` берёт все фото с `display`, включая те, у кого хеш уже есть:
он нужен после смены алгоритма или битности хеша, потому что старый хеш с новым несравним
(см. «Похожие фото»). Ошибка одного фото не прерывает проход, в конце — сводка «обработано /
пропущено / ошибок». Команда вызывает тот же `services.process_photo()`, что и обычная
обработка: второй реализации пайплайна быть не должно.

**Зависимости подэтапа.** `numpy` (BSD-3-Clause) — DCT для хеша; `pillow-heif`
(BSD-3-Clause) — регистрация HEIC в Pillow, иначе iPhone-снимки не открывались бы. HEIC
регистрируется в `PhotosConfig.ready()` под `try/except ImportError`: отсутствие пакета
не должно ломать проект. `opencv-python-headless` в 3.1 не ставится — ни одной операции,
которой он нужен, здесь нет (поворот, кроп, ресайз и DCT-хеш делаются на Pillow + numpy).
Вернётся вместе с автоуровнями/CLAHE после 3.6.

### Celery-пайплайн (3.3)

Обработка идёт фоновой задачей: запрос загрузки не ждёт, пока посчитается `display`
и перцептивный хеш. Человек сразу видит фото в кабинете со статусом «Обрабатывается»,
а результат появляется сам — кабинет закрыт `@never_cache`, и «Обновить» показывает
новое состояние.

```
браузер                    Django                    Celery worker
  │ шаг 1: файл             │                            │
  ├────────────────────────►│ PhotoFileForm              │
  │                         │  проверки файла, EXIF      │
  │                         │ Photo(draft, uploaded)     │
  │                         │ enqueue_photo_processing ──┼──► process_photo_task
  │ ◄── 302 на шаг 2        │                            │    processing
  │                         │                            │    exif_transpose →
  │ шаг 2: данные           │                            │    поворот → кроп → display
  ├────────────────────────►│ PhotoDetailsForm           │    width/height/phash
  │ ◄── 302 в кабинет       │                            │    processed | failed
```

**Одна точка постановки задачи.** `enqueue_photo_processing(photo)`
(`apps/photos/tasks.py`) вызывают только представление первого шага и действие админки
«Обработать заново». Представление не знает, как ставится задача: иначе один путь
обработки стал бы синхронным, а другой фоновым, и поведение зависело бы от того, откуда
пришёл запрос.

**Статусы `processing_status`.** `uploaded` (файл сохранён, задача поставлена) →
`processing` (задача начала работу) → `processed` (готово) или `failed` с коротким
текстом в `processing_error`. `processing` ставится в начале задачи, иначе фото
«залипло» бы в «Обрабатывается» навсегда после падения воркера, и никто не отличил бы
работающую обработку от брошенной. Запись идёт через `update()`, а не `save()`: служебная
пометка не должна попадать в историю и сдвигать `updated_at` (он идёт в `lastmod` карты
сайта).

**Ретраи — только на `StorageUnavailable`.** Временная недоступность хранилища
(MinIO/S3) — единственный случай, который повтор что-то исправит: битый файл и превышение
пикселей от повтора не изменятся. `max_retries=3`, пауза 60, 120, 240 секунд. После
исчерпания попыток задача пишет `failed` с понятным текстом, а не уходит в
`MaxRetriesExceededError`. Прочие исключения сразу дают `failed`: исключение наружу
не выходит, иначе задача повторялась бы бесконечно.

**Повторный запуск.** Задача молча выходит, если фото нет или оно удалено (за время
ожидания в очереди его могли убрать). Повторный `process_photo()` на живом фото
пересчитывает `display` — это нормальный путь для действия админки.

**Действие админки «Обработать заново».** Ставит задачу на выбранные фото и пишет,
сколько поставлено; удалённые пропускает. Это единственный способ починить фото, у
которого обработка упала или «залипла» после падения воркера: кнопки в кабинете автора
нет осознанно — автору достаточно правки данных, а пайплайн чинит модератор.

**Eager-режим.** При `CELERY_TASK_ALWAYS_EAGER` (dev и тесты) задача выполняется сразу
в текущем процессе: Redis для разработки не обязателен, а поведение остаётся тем же.
Тесты не требуют запущенного брокера — это закреплено в `tests/conftest.py`.

**Воркер в Docker Compose.** Сервис `worker` ждёт `minio` (`depends_on`): без хранилища
задача не может прочитать оригинал, и ретраи уходили бы впустую.

## Загрузка фото

Подэтапы 3.2 и 3.3: человек с бумажным альбомом загружает снимок, заполняет данные и видит
его в личном кабинете. Публикует фото модератор — как и команды.

**Загрузка в два шага.** Пока обе роли играла одна форма, выбранный файл терялся при ошибке
валидации, при уходе на создание команды и при возврате: `File` не переживает переход
на другую страницу. Теперь сначала сохраняется файл, потом заполняются данные — файл
в объекте, и второй шаг его уже не касается.

- `/photos/upload/` — первый шаг (только вошедшим): одно поле файла, превью и кнопка
  «Продолжить». Проверяется и сохраняется сразу, задача обработки ставится в очередь,
  человек получает 302 на второй шаг и сообщение «файл сохранён, фотография
  обрабатывается». В кабинет он не попадает: без данных о снимке фото в архиве
  бесполезно, а человек уже настроен их заполнить.
- `/photos/<pk>/edit/` — второй шаг и одновременно правка: заголовок, подпись, год, дата
  съёмки, команда и событие. Все поля необязательные — черновик нельзя блокировать,
  человек вернётся и дополнит позже. Одна страница на обе роли, потому что два маршрута
  с одинаковой формой разошлись бы в правилах доступа.
- Команда и событие вводятся **текстом** с подсказкой из нативного `<datalist>`, сервер
  резолвит введённое в объект: без JavaScript поле работает как обычный текст.
  Неоднозначное название (два «Соколы» в разных городах) не угадывается, а просит
  уточнить — фото не на той команде хуже пустого поля. `help_text` полей говорит прямо,
  что список берётся из архива, а рядом с ошибкой «не удалось найти» стоит ссылка
  «Создать команду «…»» с уже подставленным названием (`?name=` в форме команды).
  Та же ссылка есть для события; после создания человек возвращается на второй шаг
  с подставленным названием (`?team=<pk>` или `?event=<pk>`).
- **Выбранный файл можно снять.** У поля файла нет нативной очистки, поэтому под превью
  стоит кнопка «Убрать фото»: она обнуляет поле и отзывает `objectURL`. Кнопку показывает
  `photo-crop.js` вместе с кропером — без JavaScript её нет. Если браузер не умеет показать
  HEIC, картинка скрывается, но контейнер с кнопкой остаётся: иначе человек не понял бы,
  что файл выбран, и не смог бы его заменить.
- `/photos/mine/` — кабинет автора: свои фото с любым статусом, включая мягко удалённые,
  по 24 на страницу, со ссылкой «Изменить данные» на каждой карточке (кроме удалённых).
  Кнопка «Обновить» — обычная ссылка, страница закрыта `@never_cache`: статус меняют
  модератор и воркер, и устаревшая копия показывала бы «Обрабатывается» после публикации.
- `/rules/` — Правила сервиса: что публикуем, чего не публикуем, как пожаловаться.
  Отдельными пунктами — авторское право (жалоба `COPYRIGHT`) и право на изображение
  (жалоба `PRIVACY`). Ссылка стоит под кнопкой загрузки и в футере.

**Правило статуса — одна точка.** `initial_status_for(user)` (`apps/photos/services.py`)
отдаёт `draft`: загруженное фото ждёт модератора. Функция существует ради P3-10
(доверенный автор): тогда правило поменяется в одном месте, а не в форме и представлении
по отдельности.

**Право на правку — `can_edit_photo(user, photo)`.** Правит автор (`uploaded_by`) и
модератор. Объект берётся из `Photo.public`, поэтому удалённое фото не правит никто,
включая автора. Посторонним — **404, а не 403**: не раскрываем существование чужого
черновика (то же правило, что `can_edit` в каталоге). Правка **опубликованного** фото
статус не сбрасывает: аудит ведёт `django-simple-history`, а модератор проверяет
релевантность и качество заполнения, а не текст (P3-14). `display` при правке данных
не пересчитывается — заголовок, год и привязки не влияют на картинку. Кроп правится
только на первом шаге: перекроп загруженного фото отложен до P3-18.

**Плашки кабинета — семь состояний.** `Photo.upload_state` живёт в модели и возвращает
ключ, `upload_state_label` — переведённую подпись; шаблон ничего не сравнивает. Порядок
проверок идёт от самого сильного признака:

| Условие | Плашка |
|---|---|
| `deleted_at` заполнено | Удалено |
| `processing_status = failed` | Ошибка обработки |
| `processing_status` ∈ {`uploaded`, `processing`} | Обрабатывается |
| `status = published` | Опубликовано |
| `status = hidden` | Скрыто модератором |
| `status = rejected` | Отклонено |
| иначе (`draft`) | На проверке |

Удаление — признак, а не статус публикации, поэтому фото не исчезает из кабинета молча.
Рядом с плашками «Скрыто», «Отклонено» и «Удалено» выводится причина решения модератора,
рядом с «Ошибка обработки» — текст ошибки.

**Лимиты файла** (константы в `apps/photos/processing.py`, проверка —
`PhotoFileForm`):

| Параметр | Значение |
|---|---|
| `MAX_UPLOAD_BYTES` | 25 МБ |
| Форматы | JPEG, PNG, WebP, HEIC — по содержимому, расширение игнорируется |
| `MIN_SIDE_PX` | 300 px |
| `MAX_SIDE_PX` | 10 000 px |
| `Image.MAX_IMAGE_PIXELS` | 60 Мпикс (`DecompressionBombWarning` — отказ формы) |
| `DAILY_UPLOAD_LIMIT` | 50 фото за скользящие 24 часа |

Файл проверяется по порядку: размер, открытие через Pillow, формат по содержимому,
стороны, пиксели, полное декодирование (`load()`) — у обрезанного файла заголовок цел,
и без `load()` он упал бы уже после сохранения. Квота считается по менеджеру `objects`,
а не `public`: удалённое фото квоту не возвращает, иначе лимит обходился бы удалением.

**Год из EXIF — подсказка с сервера.** `PhotoFileForm` и так открывает и декодирует файл,
поэтому `extract_exif()` вызывается там же и результат пишется в `Photo.exif` при создании:
второго парсера EXIF в браузере нет (`exifr` из vendor удалён — 76 КБ ради одного поля
не нужны). Второй шаг берёт `taken_year(photo.exif)` как `initial` поля года, только если
год пуст, и рядом появляется подпись «Год взят из файла — проверьте, пожалуйста».
В базу без подтверждения человеком значение не попадает: у скана бумажного снимка EXIF
принадлежит сканеру. Предпросмотр кадра — `URL.createObjectURL` с обязательным
`revokeObjectURL` при замене файла. Без JavaScript форма работает целиком, только без
превью.

**Публичность.** Загруженное фото — черновик: его нет в галереях, карте сайта и поиске,
прямая ссылка отдаёт 404 всем, кроме автора и модератора. Формы шагов и кабинет закрыты
`noindex`; маршрут правки объявлен **до** `photos/<int:pk>/`, иначе страница фото
перехватила бы адрес.

## Коррекция кадра

Подэтап 3.4: человек сам решает, что попадёт в архив. Обрезка и поворот делаются
**до** загрузки, на первом шаге. Оригинал при этом не меняется ни на байт.

**Кроп — инструкция, а не файл.** В `Photo.crop_data` (JSONB) лежит рамка, а не картинка.
`display` вырезается из оригинала при каждом пересчёте, поэтому «Обработать заново»
в админке даёт другой кадр, не трогая исходник (инвариант № 4). Поле правится только
на первом шаге: перекроп загруженного фото требует отдать браузеру оригинал, а он сейчас
не отдаётся никому — это отдельная задача P3-18.

**Формат.** Версия 1:

```json
{
  "version": 1,
  "x": 1200, "y": 300, "width": 3600, "height": 2400,
  "rotate": 90,
  "source_width": 6000, "source_height": 4000
}
```

- координаты — в системе «как видит человек» (после EXIF-ориентации) и в **полном**
  размере кадра, не в размере холста и не в размере рабочей копии;
- `rotate` — только 0/90/180/270: произвольный угол оставил бы пустые треугольники;
- `source_width`/`source_height` — размер повёрнутого кадра. Сервер их не использует
  для расчётов (берёт реальный размер файла), они нужны рамке в админке;
- пустой словарь `{}` — «без кропа», обычный путь, а не ошибка.

**Правила живут в `normalize_crop_data()`** (`apps/photos/processing.py`): проверка типа
и версии, приведение к `int`, нормализация угла, клампинг по границам, отказ при стороне
меньше `MIN_CROP_SIDE` (100 px). Форма отдаёт её результат в `cleaned_data`, сервис
применяет к тому, что лежит в базе: данные могли прийти из админки или из старой версии.
Мусор — «без кропа» с предупреждением в лог, а не исключение: координаты приходят
из браузера.

**Почему координаты хранятся в полном размере.** `process_photo()` уменьшает копию
до `WORK_COPY_MAX_SIDE` (2500 px) до кропа, иначе 60 Мпикс не влезут в память. Браузер
присылает координаты оригинала, поэтому сервер пересчитывает их на рабочую копию
(`scale_crop_data()`, `factor = рабочая_ширина / source_width`). Если бы `crop_data`
хранил координаты копии, смена `WORK_COPY_MAX_SIDE` сдвинула бы все сохранённые кропы.

**Порядок операций фиксирован:** `exif_transpose` → поворот пользователя → кроп →
`display`. Координаты приходят в системе повёрнутого кадра, поэтому сервер поворачивает
до того, как резать. Нарушение порядка даёт сдвиг кадра на телефонах.

**EXIF нормализует браузер.** `createImageBitmap(file, {imageOrientation: "from-image"})`
разворачивает картинку по тегу, холст ужимается до `CROP_CANVAS_MAX_SIDE` (2000 px) ради
памяти мобильного браузера, координаты пересчитываются обратно в полный размер.
У Cropper `checkOrientation: false`: он не должен поворачивать кадр второй раз — иначе
координаты уедут на 90°.

**Без JavaScript.** Скрытое поле `crop_data` остаётся пустым, форма отправляется как
раньше, фото загружается целиком. `<noscript>`-подпись объясняет, что обрезать кадр можно
только с JavaScript, — иначе человек искал бы кнопку. HEIC, который браузер не декодирует,
показывается прежним превью с пояснением: отправку это не блокирует.

**Рамка в админке.** Readonly-поле `crop_overlay` рисует оригинал с затемнением вокруг
рамки (`format_html` с инлайн-стилями, без отдельного шаблона). Браузер применяет
EXIF-ориентацию к `<img>` сам, поэтому проценты считаются от транспонированного кадра;
рамка повёрнутого фото пересчитывается обратно. При зеркальной ориентации (2/4/5/7)
появляется приписка о неточности: отражение по процентам не выразить. Фото без кропа
и запись без `source_width` дают подпись, а не пустой блок.

**Проверки на трёх сторонах.** Браузер ограничивает рамку кадром (Cropper), форма даёт
понятное сообщение (`MIN_CROP_SIDE`, клампинг), сервис — страховка для данных из админки.


**Возврат после создания команды.** Рядом с полем команды стоит ссылка «Создать команду»
с `next` на второй шаг; `team_create` проверяет `next` через
`url_has_allowed_host_and_scheme` (только свой хост), поэтому открытого редиректа нет.

## Похожие фото

Подэтап 3.5: модератор открывает фото в админке и видит, что такой снимок в архиве уже
есть. Автоматического слияния нет — только подсказка с расстоянием Хэмминга: дубликат
это или два разных кадра, решает человек (инвариант № 5).

**Где это в интерфейсе.** На карточке фото в админке, в блоке «Производные», стоит ссылка
«Показать похожие фото» (`/admin/photos/photo/<pk>/similar/`). Счётчика «найдено N» рядом
нет осознанно: он стоил бы прохода по пулу кандидатов при каждом открытии карточки, а
карточку модератор открывает часто. Кнопка «Слить в это фото» появится на этой же странице
в 3.6: сейчас `Photo` ещё не `MergeableModel`, и страница только показывает.

**256 бит, а не 64.** Хеш считается на DCT 64×64 с блоком низких частот 16×16 — это
64 hex-символа (`PHASH_HEX_LENGTH`). На 64 битах замеры показали, что разные фото
расходятся в среднем на 24 бита (37 %), а однотонная красная и однотонная синяя заливки —
всего на 6 из 64, то есть попадают в «вероятный дубликат». На 256 битах медиана «разных»
стала 104 (41 %), доля ложных пар упала с 3 из 15 до 1 из 66. Цена — DCT 64×64 вместо
32×32 (доли миллисекунды на фото) и 64 символа в поле вместо 16. Поле в базе уже было
`CharField(max_length=64)`, поэтому миграции не понадобилось.

**Пороги — подсказка, а не приговор** (`apps/photos/similar.py`):

| Константа | Значение | Доля от 256 | Подпись |
|---|---|---|---|
| `LIKELY_DUPLICATE_DISTANCE` | 32 | 12,5 % | «вероятный дубликат» |
| `SIMILAR_DISTANCE_MAX` | 48 | 18,8 % | «похоже» |
| `SIMILAR_LIMIT` | 20 | — | сколько кандидатов показываем |
| `CANDIDATE_POOL_LIMIT` | 5000 | — | сколько фото просматриваем в Python |

Откуда числа: то же фото в другом масштабе, после повторного JPEG, с другой яркостью
или контрастом укладывается в 40 бит из 256, кроп 1 % по краям — в 16. Порог 48 накрывает
все варианты «того же снимка», кроме заметного перекропа, а разные фото начинаются
с медианы 104 — запас почти двукратный. Функция `similarity_label(distance)` живёт рядом
с порогами: шаблон не сравнивает числа, он печатает готовую подпись. Страница всегда
показывает расстояние числом — модератор видит, насколько подсказка близка к порогу.

**Отбор кандидатов до расчёта.** Расстояние Хэмминга не выразить в SQL: хеш лежит
hex-строкой, XOR считается в Python. Поэтому выборка сужается заранее: тот же вид спорта,
не удалённые, не само фото, только хеши нужной длины, при известном годе — окно ±5 лет
плюс фото без года (год заполнен далеко не у всех, и дубликат без года иначе не нашёлся бы).
`Photo.public` не используется: черновик и скрытое фото — законные кандидаты, дубликат
могли загрузить дважды и оба оставить черновиками. Статус кандидата показывается на
странице плашкой.

Пул ограничен `CANDIDATE_POOL_LIMIT` последних по `created_at`; при превышении в лог
пишется предупреждение — часть архива осталась непроверенной, и это лучше, чем страница,
которая тянет весь архив в память. Замер на 10 000 строк: `similar_photos()` — 0,16 с,
страница — 0,28 с.

**`similar_photos()` — единственная точка входа** (`apps/photos/similar.py`). Ей пользуются
страница админки и будущая проверка при загрузке: второй реализации отбора быть не должно,
иначе страница и загрузка отвечали бы по-разному. Страница ничего не меняет и не пишет
в `ModerationAction`: просмотр — не решение модератора.

**`--rehash` после смены алгоритма обязателен.** `hamming_distance()` при разной длине
хешей возвращает «бесконечно далеко» (длину большего хеша в битах), а не случайное число:
XOR по 16-символьному и 64-символьному хешам дал бы мусор. Поэтому старые хеши сами
в кандидаты не попадут, и без пересчёта ни одно загруженное раньше фото не найдёт себе
дубликат. Для демо-архива это одна команда, для боевой базы — пункт чек-листа деплоя:

```bash
uv run python manage.py photos_backfill --rehash
```

Флаг пересчитывает хеши у всех фото с `display`, включая те, у кого `phash` уже есть;
без флага поведение команды не меняется. `--dry-run` работает и с `--rehash`.

**Ограничение, которое порогом не лечится.** Монотонные цветовые заливки хеш не различает
(см. выше): красная и синяя дают 16 из 256 при любом размере и сжатии. Для фотоархива это
не дефект — заливок в нём нет, а подпись остаётся подсказкой. Повороты на 90/180/270
тоже не находятся: понадобятся четыре хеша на фото — это P3-19 в бэклоге. EXIF-ориентацию
телефонных снимков это не заменяет: она уже нормализуется в пайплайне.

проверяет и правила, и форматирование; `make format` приводит код к стилю.

Перед коммитом: `make lint && make test`. Перед коммитом также применяется навык
[semver-checker](.agents/skills/semver-checker/SKILL.md) — версия живёт в `pyproject.toml`,
после её изменения нужно выполнить `uv lock`.

Сообщения коммитов пишутся **на простом английском**, понятном не носителю языка: короткие
предложения, простые слова, без идиом. Тело коммита объясняет, **почему** сделано изменение.
Подробнее — в [KODA.md](KODA.md) (раздел «Язык общения»).

### Пошаговое выполнение плана

Подэтап из 10–14 шагов не влезает в одну сессию агента: история растёт, и в какой-то момент
сессия встаёт с сообщением о лимите запросов. Скрипт `.koda/scripts/run-plan.sh` выполняет
план **по одному шагу на сессию**: каждый шаг — отдельный процесс `koda -p`, поэтому контекст
начинается с чистого листа, а после шага остаётся коммит — точка отката.

```bash
make plan-list PLAN=.koda/plans/photo-processing-3.2-photo-upload.md   # что в плане
make plan-dry  PLAN=.koda/plans/photo-processing-3.2-photo-upload.md   # что будет выполнено
make plan-step PLAN=.koda/plans/photo-processing-3.2-photo-upload.md STEP=1
make plan-all  PLAN=.koda/plans/photo-processing-3.2-photo-upload.md BRANCH=feature/photo-upload
```

Модель задаётся переменной `PLAN_MODEL` (по умолчанию `koda-pro`); уровень рассуждений
берётся из `settings.json` — `low` для `koda-pro`, `medium` для `koda-base`. Исключение:
`PLAN_MODEL=koda-base make plan-all PLAN=...`.

Правила, которые скрипт проверяет сам:

- работа идёт только в ветке, отличной от `master` (`--branch` создаёт её от `master`);
- рабочее дерево перед стартом чистое (иначе `--allow-dirty` или коммит);
- шаг без коммита считается провалом, цикл останавливается — план не разойдётся с кодом;
- `[x]` в плане ставится только после коммита; если агент забыл, скрипт отметит сам;
- переписанная история (`git reset` внутри сессии) ловится проверкой предка;
- `git push` скрипт не делает никогда.

Ревью — **после всего подэтапа**, а не после каждого шага: `git log --oneline master..HEAD`
и `git diff master...HEAD --stat`. Откат к любому шагу — `git reset --hard <sha>`.
Логи прогонов пишутся в `.koda/logs/` (в git не попадают).
