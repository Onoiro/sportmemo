# Восстановление SportMemo из бэкапа

Чек-лист на случай настоящей аварии: сервер потерян, база не поднимается,
диск сгорел. Читать сверху вниз, ничего не пропускать. Если что-то не
сходится — остановиться и разобраться, а не «попробовать ещё раз».

Бэкап лежит в **другом облаке**, не у того провайдера, где живёт сервер:
копия у того же провайдера не защищает от его сбоя и блокировки аккаунта.

- Бакет: `<BACKUP_BUCKET>` на remote `cloudru` (параметры подключения —
  в README, раздел «Бэкапы»).
- Дампы БД: префикс `db/`, имя `sportmemo_<ГГГГММДД_ЧЧММСС>.dump`.
- Медиа: префикс `media/` (стейдж, локальный каталог `./media`) либо
  `originals/` и `public/` (прод, из бакетов Yandex).

Ключи доступа и пароли в этом файле не хранятся: они живут в
`~/.config/rclone/rclone.conf` и `.env` на сервере.

## 0. Что понадобится

- Новый сервер с репозиторием и `.env` (значения — из своей защищённой
  копии; секретов в git нет).
- `rclone`, настроенный на remote `cloudru` (`rclone lsd cloudru:`).
- Свободное место: объём дампа + объём медиа + запас. Дамп сжимается
  плохо, потому что уже сжат форматом `-Fc`.

## 1. Скачать бэкап из бакета

Сначала посмотреть, что есть:

```bash
rclone lsf cloudru:<BACKUP_BUCKET>/db/ --files-only
```

Взять **последний** дамп по дате в имени (имя и есть метка времени)
и скачать его в каталог `backups/` — он в `.gitignore` и с правами `700`:

```bash
mkdir -p backups && chmod 700 backups
rclone copy cloudru:<BACKUP_BUCKET>/db/sportmemo_<МЕТКА>.dump backups/
```

Проверить, что файл целый, ещё до всякого восстановления: `pg_restore`
умеет читать оглавление архива и падает на битом файле.

```bash
docker compose -f docker-compose.stage.yml exec -T db \
  pg_restore --list < backups/sportmemo_<МЕТКА>.dump | head
```

Пустой вывод или ошибка — скачать другой дамп. Восстанавливать битый
файл бессмысленно: он даст половину таблиц и молчаливое «почти сработало».

## 2. Поднять базу

```bash
docker compose -f docker-compose.stage.yml up -d db redis
docker compose -f docker-compose.stage.yml ps
```

Контейнер `db` должен быть `healthy`. Пока он не здоров, дальше идти
нельзя: `pg_restore` упрётся в «connection refused» и это будет выглядеть
как битый дамп.

## 3. Развернуть дамп

**Только в пустую базу.** Поверх живой базы разворачивать нельзя:
`pg_restore` без `--clean` допишет данные к существующим, и получится
смесь двух состояний архива, которую потом не распутать.

Если база не пустая (например, осталась от неудачной попытки), её нужно
удалить и создать заново:

```bash
docker compose -f docker-compose.stage.yml exec -T db \
  dropdb -U sportmemo --if-exists sportmemo
docker compose -f docker-compose.stage.yml exec -T db \
  createdb -U sportmemo sportmemo
```

Разворачивание:

```bash
docker compose -f docker-compose.stage.yml exec -T db \
  pg_restore --no-owner --no-privileges -d sportmemo \
  < backups/sportmemo_<МЕТКА>.dump
```

`--no-owner --no-privileges` нужны, потому что роли и владельцы объектов
на новом сервере другие; без них `pg_restore` сыплет ошибками про
несуществующую роль и возвращает ненулевой код при фактически
восстановленных данных.

Предупреждения `role "..." does not exist` при этом флаге допустимы,
ошибки `ERROR:` — нет.

## 4. Вернуть медиа

Файлы и база не согласованы по времени: фото, загруженное между дампом
и копированием, может отсутствовать. Это терпимо — на месте картинки
будет заглушка, архив не рушится.

**Стейдж (медиа лежало в `./media`):**

```bash
rclone copy cloudru:<BACKUP_BUCKET>/media/ ./media/ --transfers 4
chmod -R o+rX media
```

`o+rX` обязателен: nginx работает от `www-data` и читает файлы с хоста.

**Прод (медиа в бакетах Yandex):**

```bash
rclone copy cloudru:<BACKUP_BUCKET>/originals/ yandex:<S3_PRIVATE_BUCKET>/ \
  --transfers 4
rclone copy cloudru:<BACKUP_BUCKET>/public/ yandex:<S3_BUCKET>/ \
  --transfers 4
```

Оригиналы возвращать первыми: они невозвратимы, производные (`display`,
превью) пересчитываются из них командой `make photos-previews`.
Пока `originals` на месте, архив восстановим даже при потере публичного
бакета.

## 5. Запустить приложение

```bash
./scripts/deploy-stage.sh
```

Скрипт соберёт образ, применит миграции, соберёт статику и поднимет
`web` и `worker`. На проде — тот же порядок, отличается только
compose-файл.

## 6. Проверить, что архив жив

1. `curl -fsS https://<домен>/healthz/` — отвечает `ok`.
2. Главная страница открывается и показывает счётчики.
3. Страница любого фото из дампа открывает картинку, а не заглушку
   (заглушка на всех фото — не вернули медиа, см. §4).
4. Поиск находит известную команду: `tsvector` и `pg_trgm` живут
   в дампе, но расширение `pg_trgm` требует прав суперпользователя —
   на новом сервере его может не быть. Проверка: `make search-reindex`
   проходит без ошибок.
5. Счётчики: число фото в кабинете автора совпадает с ожидаемым.

Число фото и команд до аварии известно из журнала бэкапа
(`backups/backup.log` в копии репозитория или из вывода последнего
успешного прогона).

## 7. Чего не делать

- **Не разворачивать дамп поверх живой базы.** Сначала удалить и создать
  заново (§3).
- **Не запускать `scripts/restore-check.sh` на проде.** Он создаёт
  и удаляет базу; на боевом сервере `BACKUP_ALLOW_RESTORE_CHECK` не
  задан, и скрипт откажется работать. Флаг не включать «на минутку».
- **Не копировать медиа через `rclone sync`.** `sync` удаляет в приёмнике
  то, чего нет в источнике: ошибка в источнике станет потерей
  единственной копии.
- **Не восстанавливать старый дамп «чтобы проверить»** на боевой базе:
  потеряются фото, загруженные после него. Для проверки есть
  `restore-check` на стейдже — он работает во временной базе.
- **Не удалять локальные дампы в `backups/` до проверки** восстановления:
  это последняя копия, которая уже на диске.
